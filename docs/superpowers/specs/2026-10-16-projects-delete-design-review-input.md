# Projects delete slice: Codex adversarial review of the chat design (input for the delete spec)

Run 2026-10-16 on the bounded chat design (projects.delete cascade, gap fixes, routes, UI). It moved the slice to a written spec. The wrapper findings (6) are superseded by project audiences (v2.499.533-.546): wrappers no longer borrow visibility. User rulings since: delete hides at once, stops running work, finishes cleanup when idle with a transient deleting mark (option A); deleting the last piece never deletes the project.

Found 20 design defects. Review was read-only; no files changed. Four access edge cases were also confirmed by executing unchanged functions against in-memory storage.

1. **P1 — Deleting a subject can expose surviving records.** [chauffeur/services/subjects.py:176](E:/repositories/Chauffeur/chauffeur/services/subjects.py:176) silently omits missing current and historical subjects; `access._subjects_full` then loses that restriction. **Scenario:** a thread in project B previously referenced private project A, then was retargeted elsewhere. Deleting A leaves the thread and makes its retained A-derived words readable more widely. `_work_missions` does not cover historical subjects or these threads. **Fix:** inventory inbound current/history references and preserve their restrictions or redact their derived content; missing subjects must fail closed during cleanup.

2. **P1 — Asynchronous refresh permits an immediate calendar privacy leak.** [chauffeur/services/access.py:361](E:/repositories/Chauffeur/chauffeur/services/access.py:361) treats a missing program as unrestricted because `practice_hidden(None, …)` is false. **Scenario:** delete a private program while its practice event remains in a daily/custom/global cache; the next calendar or Today read reveals the original title and lesson fields. **Fix:** synchronously remove deleted-program events from every schedule cache before removing the emitter, reject missing-emitter events at read time, and prevent an older refresh from restoring them. Cached project holds likewise need removal, not merely eventual refresh.

3. **P1 — The 409 preflight omits transitive deletion targets.** [chauffeur/services/threads.py:389](E:/repositories/Chauffeur/chauffeur/services/threads.py:389) deletes every origin mission without checking its project or actor; `_work_missions` also reaches missions outside the project. **Scenario:** deleting project A reaches a thread’s mission homed in B, or a B-homed mission about A, which the deleter cannot delete. Checking A’s listed pieces still passes. **Fix:** compute the complete deletion closure first, including origin missions and `_work_missions`, authorize every deleted record before any stopping or mutation, and use that same closure for preview and execution. Apply this to standalone thread deletion too.

4. **P1 — The literal “any piece” 409 rule rejects linked records that should survive.** [chauffeur/services/access.py:182](E:/repositories/Chauffeur/chauffeur/services/access.py:182) supports only registered thread/mission/program kinds; `record_actable('trip', …, 'delete')` returns false. **Scenario:** a project containing an ordinary linked trip or list can never be deleted. **Fix:** apply delete authorization only to the deletion closure; surviving link kinds require no delete permission.

5. **P1 — Delete-preview can disclose hidden piece titles.** [chauffeur/services/projects.py:1070](E:/repositories/Chauffeur/chauffeur/services/projects.py:1070) filters each piece independently because project visibility does not imply piece visibility. **Scenario:** a parent sees a household project containing a thread whose subject excludes that parent. A preview “naming everything” reveals the hidden thread before DELETE returns 409. **Fix:** run the complete authorization preflight before returning titles; return a generic conflict without naming inaccessible targets.

6. **P1 — Resetting a wrapper to `private` does not implement “owner only.”** [chauffeur/services/projects.py:81](E:/repositories/Chauffeur/chauffeur/services/projects.py:81) includes parents in a child owner’s private project. **Scenario:** a child’s wrapper was narrowed by its wrapped record’s private subject; removing that record and assigning `private` exposes the retained title/goal to previously excluded parents. Separate writes also leave a temporary fail-open window at `_wrapped_visible` line 59. **Fix:** preserve an explicit visibility cap on the surviving wrapper, resolving the owner-only/child-parent policy explicitly, and change wrapper policy atomically with source deletion.

7. **P1 — `stop_plan` does not drain running build stages.** [chauffeur/services/planned.py:1073](E:/repositories/Chauffeur/chauffeur/services/planned.py:1073) continues after the already-claimed action finishes and assumes the mission still exists; `_dismiss_rows` deliberately leaves running rows alone. **Scenario:** deletion completes while `propose_program` is curating. It later creates a program, and adoption can create a replacement wrapper after the original project is gone. The runner then crashes reading the deleted mission. **Fix:** exclude new claims, drain or fence active build executions, then rescan their outputs before final deletion. Do not wait while holding the database lock.

8. **P1 — A steer flag is insufficient browser cancellation.** [chauffeur/services/missions.py:830](E:/repositories/Chauffeur/chauffeur/services/missions.py:830) consumes the flag once and does not treat a missing mission as stopped; [browse.py:1650](E:/repositories/Chauffeur/chauffeur/services/browse.py:1650) checks it only between turns. **Scenario:** DELETE returns while a browser turn still acts, or a delayed daemon starts afterward and recreates its screenshot directory. Clearing the flag for “no leftovers” removes its remaining cancellation signal. **Fix:** maintain runtime worker cancellation, treat missing missions as permanently cancelled, recheck before actions, and wait for worker exit before final file cleanup.

9. **P1 — Program approval/resume and lesson generation can write after deletion.** [chauffeur/services/programs.py:1018](E:/repositories/Chauffeur/chauffeur/services/programs.py:1018) creates commitments from a captured row; [program_lessons.py:1161](E:/repositories/Chauffeur/chauffeur/services/program_lessons.py:1161) upserts lessons after a model call without checking that the program survives. **Scenario:** deletion releases commitments and removes lessons, then an overlapping approval creates new commitments/kit work or generation recreates orphan lessons. **Fix:** coordinate these writers with program deletion and enforce parent-existence/cancellation checks atomically at their final writes.

10. **P1 — Delete authority does not imply plan-stop authority.** [chauffeur/services/planned.py:245](E:/repositories/Chauffeur/chauffeur/services/planned.py:245) requires `may_approve`, including subject access; a mission keeper explicitly retains `delete` without that access. **Scenario:** an authorized keeper deletes a mission whose subject excludes them. Reusing `stop_plan` either refuses their legitimate deletion or proceeds without stopping the plan. **Fix:** provide internal cancellation authorized by the successful delete check, independent of plan-approval permission, and check its outcome.

11. **P1 — `release_commitments` cannot support reliable hard deletion unchanged.** [chauffeur/services/programs.py:286](E:/repositories/Chauffeur/chauffeur/services/programs.py:286) catches deletion failures, clears every commitment ID, and reports their count anyway. **Scenario:** one commitment deletion fails; program deletion succeeds, leaving protected time behind. Its title also becomes unrestricted once the emitter disappears (`access.commitment_view`). **Fix:** retain failed IDs, propagate failure, verify removals, and leave the program recoverable until cleanup succeeds.

12. **P1 — Project-row-last does not make child cleanup retryable.** [chauffeur/services/missions.py:1191](E:/repositories/Chauffeur/chauffeur/services/missions.py:1191) returns immediately when the mission is absent, but deletes its row/steps before asks and files. **Scenario:** ask cleanup fails after row deletion; rerunning the project delete gets `not_found` and permanently skips the remaining artifacts. Screenshot removal also ignores failures. **Fix:** make cleanup by ID idempotent even without the primary row; retain cleanup metadata until dependents are removed, and remove each child row last.

13. **P1 — `pieces[]` alone cannot establish that all home records are gone.** [chauffeur/services/projects.py:879](E:/repositories/Chauffeur/chauffeur/services/projects.py:879) writes `project_id` before adding the piece entry; a retry returns early at line 856. **Scenario:** the piece write fails, leaving a thread/program homed in the project but absent from `pieces[]`. The proposed cascade removes the project and leaves that record with a dangling home; `access.restricted(None)` then removes its home privacy gate. **Fix:** scan authoritative `project_id` across all three home kinds and verify no survivors before deleting the project.

14. **P1 — An in-flight watcher can recreate deleted findings and send their words afterward.** [chauffeur/services/findings.py:141](E:/repositories/Chauffeur/chauffeur/services/findings.py:141) inserts findings from an earlier collection without verifying that the source still exists. **Scenario:** a sweep captures a stalled thread, deletion removes its findings/thread, then reconciliation recreates the finding. Missing-source findings pass access checks, and watcher fallback text can still be DM’d. **Fix:** revalidate source existence under deletion coordination at reconciliation and delivery; similarly fence reply notifications that captured a thread before deletion.

15. **P2 — Settling DM cards preserves the deleted history.** [chauffeur/services/missions.py:414](E:/repositories/Chauffeur/chauffeur/services/missions.py:414) keeps the entire ask card, including questions, released values and project details, merely changing its state. Project-start cards and `mission_done` cards are separate copies. **Scenario:** the project disappears but its complete plan/contact questions remain in Argyle DMs. **Fix:** delete attributable message/card copies, including their bodies and completion cards, with provenance sufficient to find every copy.

16. **P2 — Proposal rows and findings’ own asks are outside the cascade.** [chauffeur/services/missions.py:1596](E:/repositories/Chauffeur/chauffeur/services/missions.py:1596) creates independent action-proposal rows; [asks.py:164](E:/repositories/Chauffeur/chauffeur/services/asks.py:164) can attach asks to findings rather than directly to missions/threads. **Scenario:** deleting source findings and missions leaves proposal payload/history and finding-bound ask cards behind; finding-bound asks bypass `_ask_piece_or_404`’s piece check. **Fix:** include source/stage proposals, deleted findings’ asks, and their chat copies in dependent cleanup.

17. **P2 — Clearing current `mission_id` leaves history and app-state references.** [chauffeur/services/missions.py:1373](E:/repositories/Chauffeur/chauffeur/services/missions.py:1373) copies mission summaries into thread history; project steps retain prior missions in `attempts` (`projects.py:621`). `triage_focus` also stores IDs/titles, while steering, watcher-notified and practice-push markers live separately in app state. **Scenario:** standalone deletion leaves the deleted mission’s summary, attempt references and conversation title indefinitely or until unrelated pruning. **Fix:** remove keyed history/attempt references and associated cached fields, purge matching focus/notification/push entries, and physically remove steering keys after workers stop.

18. **P2 — Program commitment dependents survive successful release.** [chauffeur/services/storage.py:2813](E:/repositories/Chauffeur/chauffeur/services/storage.py:2813) removes only the commitment row. Protected exceptions remain keyed by commitment ID, and commitment findings use `subject_type='commitment'` with compound IDs (`watchers.py:704`). **Scenario:** deleting a program leaves negotiated exceptions and historical/active commitment findings despite deleting program-subject findings. **Fix:** expand cleanup through emitted commitment IDs, including exceptions, associated findings and their asks/cards, while preserving unrelated trips/events.

19. **P2 — The kit-thread lifecycle remains unresolved in both directions.** [chauffeur/services/programs.py:1098](E:/repositories/Chauffeur/chauffeur/services/programs.py:1098) trusts a nonempty `emissions.thread_ids` without checking whether those threads exist. **Scenario:** standalone program deletion leaves its kit thread and missions; deleting the kit thread alone leaves a stale emission that prevents a replacement on reapproval. **Fix:** specify kit retention/deletion in the preview and authorization closure, and always remove deleted thread IDs from surviving programs’ emissions. Any retained kit must be explicitly detached.

20. **P2 — Folding every same-project origin mission loses existing access and controls.** [chauffeur/services/situations.py:242](E:/repositories/Chauffeur/chauffeur/services/situations.py:242) forwards only the newest live mission, while [main.py:7246](E:/repositories/Chauffeur/chauffeur/main.py:7246) returns only five historical missions through the thread sheet. **Scenario:** the sixth older mission loses its reachable transcript/delete control; a mission keeper who cannot see its origin thread also loses their standalone card. **Fix:** fold only where an authorized thread surface actually exposes that mission’s permitted actions, and provide complete history access while retaining standalone keeper access.
