# Subjects — a thread or mission stands inside a Chauffeur record

**Date:** 2026-10-14. **Status:** DRAFT for the user's review. Codex adversarial review done (nine findings, every one verified against the code, all folded in below; the review's text is in the v2.499.459→.460 commit message trail). Slice 1 of three (resolver + subject; then staged plans with one approval per stage; then wake conditions).
**Builds on:** `2026-10-10-browse-missions-design.md` (missions, threads, the planner's READ/PROPOSE catalog), the mid-mission steer (v2.499.458), the Programs arc (a goal is a plan that claims the week), family-network S4 (audiences: `services/scope.py`).

## Problem

A mission sees Chauffeur only through the planner's READ tools, and the planner sees those as a flat list of names. "Book dining for the Disney trip" has no path to the trip: there is no trip READ tool at all, and nothing resolves "the Disney trip" to a record. Whatever a mission does read lands in its transcript and scrolls out after 25 steps; a follow-up mission on the same thread starts blind; the record changing after the read is never noticed. A thread knows a counterparty and nothing else. The person's workaround today is to open the trip or occasion, find the thing, and ask about it by name. The goal (the user, 2026-10-14) is the opposite: a vague request during a busy day, and the agent fills in the blanks from what the app already knows.

## Decisions made in this conversation

- **Optional, always.** A free-text goal with no subject keeps working exactly as today. A subject is added when the resolver finds one, when the planner binds one, or when a person picks one. Nothing requires it.
- **The subject lives on the thread; a thread's missions never carry their own.** A thread is the long-lived thing ("Disney trip dining"); its missions come and go and read the thread's subject (`missions.subject_of`). A manual mission (no thread) carries its own. One authoritative place per situation, so the chip, the context and the picker can never disagree (review finding 5).
- **One resolver, every kind.** A single `find_in_chauffeur` tool over trips, occasions, events, members, outside contacts, threads, programs and lists. It returns candidates with ids. The same tool serves Argyle's chat, the planner and the satellite, so "which trip" is answered once, the same way, everywhere.
- **Fresh, not remembered; re-authorised at every read.** The subject's current state is rebuilt from storage, for a named viewer, and put at the top of every planner step and of Argyle's chat prompt while the focus thread has a subject. It never rides in the transcript. Nothing about a subject (title, link, context, chip, back-link) is shown to a viewer the subject's own audience excludes (finding 2).
- **A situation inherits its subject's audience.** A thread or mission about a parents-only occasion is itself parents-only: its transcript, cards, DMs and admin rows go only to members the subject's audience allows (finding 3). Binding never widens who may see the record; it narrows who may see the situation.
- **Retargeting is a guarded operation.** While a tap-only ask (release, submit, verify) is pending or a browse is live, the subject cannot be changed or cleared; otherwise the change bumps `subject_rev` and leaves a note the planner reads (finding 4). The same `subject_rev` is what slice 2's staged approvals and slice 3's wake conditions will check.
- **Out of scope for this slice:** staged plans, batch proposals, wake conditions, write-back of results onto the subject (reservation → POI), fan-out. Each is its own slice and is named here only so the record shapes leave room for them.

## Section 1 — The record

On `Thread` and on the mission row: `subject_kind: Optional[str]`, `subject_id: Optional[str]`, `subject_rev: int = 0`. Kinds in this slice: `trip` (id = the trip's `event_id`, the key `storage.get_trip_metadata` takes), `occasion`, `event` (a cached-schedule event id), `member`, `contact` (an assist contact), `thread`, `program`, `list` (a shopping list). Absent means none. `missions.subject_of(mission)` returns the origin thread's triple when `origin_kind == 'thread'`, else the mission's own.

`services/subjects.py` is the one module that knows the kinds. Per kind, behind one registry:

- `visible(kind, row, viewer, spoken=False) -> bool` — the record's OWN rule, per kind, reused not reinvented (finding 1): trip and occasion `scope.audience_allows(row, kind, viewer)` (defaults: parents); list `audience_allows(row, 'shopping_list', viewer)` (private lists only to their `shared_with`); program the `_program_scope_id` partition (a child, helper or guest sees only their own); thread `situations.can_see`; event the calendar-event audience; member and contact parent/adult only. A viewer of `None` is an anonymous surface and sees only `household` audiences. `spoken=True` additionally requires `spoken_safe(kind, row)`: `audience_allows(row, <the kind's own type>, None)` plus the sensitivity flags `voice_tools.speech_safe` checks. (`speech_safe` itself checks every row as a `calendar_event`, so a trip or occasion with no audience set, which defaults to parents, passes it; this slice does not change `speech_safe`, it uses the type-aware check for subjects.)
- `find(kind, query, viewer, spoken=False) -> list[Candidate]` — `Candidate = {kind, id, title, when (ISO date or ''), score}`. Rows are filtered by `visible` BEFORE matching, so an excluded viewer learns nothing from a miss. Matching is the existing tiers reused: exact title, then substring and first-word, then the sound-folded form `_match_person` already uses, each tier requiring a unique winner before it is trusted. Dates in the query narrow ("the trip in March"). Upcoming and open rows outrank past and closed ones at equal score. Capped at 5 per kind.
- `context(kind, id, viewer, spoken=False, facet=None) -> str | None` — `None` when the record is missing OR the viewer may not see it (the same nothing, finding 2). Otherwise the record's current state in plain words, at most 1,500 characters. Trip: title, where, dates, travellers, accommodations with nights, flights, budget, then the POIs with their scheduled day and time window (scheduled first, unscheduled named), each with its category; capped at 30 POIs with "and N more". `facet='dining'` keeps only POIs whose category or name carries a food word, uncapped within the budget (review question 2: yes, now). Occasion: `occasions.contents` with its linked lists re-filtered by `audience_allows(list, 'shopping_list', viewer)` before they are named (finding 2: `contents` gathers every linked list). Event: title, date, time, location, driver or "no driver yet", passengers. Member: name, role, driver yes/no. Contact: what we call them, relation, helps-with, channels on file (never the numbers themselves when spoken). Thread: title, goal, state, counterparty, next action, last three history lines. Program: title, whose, state, this week's sessions. List: name, item count, the first ten items.
- `link(kind, id) -> str` — the page a person opens for it, used by the chip; the chip itself is drawn only when `visible` for the viewer.

**Trip dates are the calendar's, and the context says how old they are** (finding 8). `TripMetadata` holds draft (mock) dates only; a real trip's dates live on its Google event and are assembled by `/api/trips`, which leaves `storage.set_cached_trips` behind with an `at` stamp. `context('trip', …)` reads dates through one owning function, `trips.trip_dates(event_id)` → `{start, end, source: 'draft'|'calendar'|'unknown', age_s}` (draft → the mock dates; real → the cached snapshot; no snapshot → unknown). The words carry the age when it is over an hour ("dates as the calendar had them 9 hours ago") and say "dates unknown; confirm them before booking" when there is no snapshot. The planner is told that a booking step must not rely on dates older than a day without asking. The context never calls Google per step.

`find_all(query, viewer, kinds=None, spoken=False)` runs every kind (or the named ones) and returns candidates sorted by score then recency, capped at 8. `resolve(query, viewer, ...)` returns the one candidate when the top score is a clear winner (the same margin rule `_match_person` uses between Grandpa and Grandma), else `None` with the candidates, so the caller can ask "which one?".

## Section 2 — The tool and who calls it

One READ tool, `find_in_chauffeur(query, kind='')`, registered in `agent_tools_v2` and added to `missions.READ_TOOLS` and to `voice_tools.TOOLS` (finding 9). Result: `{status, candidates: [...], context: str|None}`; `context` is filled when the result is a single clear winner, so one call both finds and reads.

**Who the viewer is, and what is stored.** In Argyle's chat the viewer is the acting member and nothing is stored. On the satellite the viewer is the verified member (or `None` for household voice) with `spoken=True`. In the planner the viewer is the mission's **audience viewer**: the registry reader (an adult with no id) when the mission has no subject, else a parent of record, because the transcript is readable by everyone the mission's audience allows and no one else (finding 3). What the planner STORES on the transcript step is the candidate list (titles and ids) only; the `context` string is returned to the model for that step and dropped, never written. Pre-existing and left as is in this slice, named for the record: `get_occasion` as a planner READ runs with no viewer today, so an unbound mission already reads every occasion; once a mission is bound its audience closes that gap for its own transcript, and the general fix (every planner READ runs as the audience viewer) is a one-line follow-up after this slice proves the viewer plumbing.

**Argyle's chat.** Router rule, next to the start-a-mission rule: before `start_mission_for` for a goal that names a thing the family has (a trip, a party, an event, a person, a list), call `find_in_chauffeur` and pass the winner as `subject_kind`/`subject_id`; when it returns more than one, ask which. `start_mission_for` grows the two optional arguments. Focus-thread reuse (finding 6): a focused open thread with no live mission is reused only when its subject is absent (it is then set) or equal to the resolved one; a conflicting subject opens a new thread. Dedupe (finding 7): with a subject, "already under way" needs the SAME subject AND the same intent words (the goal's first three content words with the subject's title words removed); a different intent on the same subject launches. Subject-less goals keep today's first-three-words rule.

**The satellite** (finding 9). `voice_tools.dispatch` gains a `find_in_chauffeur` branch (viewer = the verified member or `None`, `spoken=True`) and its `start_mission_for` branch forwards `subject_kind`/`subject_id`. The router's focus injection stays off for voice; the spoken ABOUT block below is injected only when the subject is `spoken_safe`. A runtime test drives the voice rail from lookup through mission creation.

**The planner.** `find_in_chauffeur` is a READ action like any other. A new action `{"action":"subject","kind":"…","id":"…"}` binds the subject: on a manual mission, its own fields; on a thread-origin mission, the THREAD's fields, and only when the thread has none (already bound → a `refused` note: "already about X; a person unlinks it"). The step is a `note` named `subject`. The system prompt tells the planner: when the goal names something the family has and no subject is set, find it first; when a subject is set, its state is above and is the truth, not the transcript's older reading; a `subject_changed` note means re-read before acting.

**Fresh context.** `missions._system_prompt` gains, after the family context, `ABOUT: <kind> "<title>"` and the `context()` text when `subject_of(mission)` is set and visible to the audience viewer. `agent_router` gains the same block under the FOCUS line when the focus thread has a subject visible to the acting member. Both are built per call from storage. Neither is stored.

## Section 3 — Audience, retargeting

**The situation inherits the subject's audience.** `situations.can_see('thread'|'mission', row, viewer)` becomes: today's rule AND, when the row has an effective subject, `subjects.visible(kind, record, viewer)`. `missions_detail`, `/api/missions/admin`, the Threads page list, `list_situations`, `_dm_person` recipients (a parent the audience excludes is not DM'd the ask), and the DM/thread cards all go through it. Parents-only is the default audience of trips and occasions, so a mission about a trip is parents-only unless the trip is shared wider; adults who could read every transcript today read none about a parents-only record. A spoken request about a subject that is not `spoken_safe` gets "That needs your phone."

**Retarget** (`subjects.retarget(kind_sit, sid, new_kind, new_id | None, actor)`): parent/adult; refused while the situation's live mission has a tap-only ask pending or is `browsing` ("finish or stop the pending step first"); otherwise writes the fields, bumps `subject_rev`, and adds a `subject_changed` note (old → new) to the live mission so the next planner step re-reads. Pending `proposal` steps on that mission are dismissed with the same note (a proposal built about trip A is not offered about trip B). Clearing is the same operation with `None`.

## Section 4 — The hand path

- **Chip.** The thread card and the mission card show `About: <title>` (the one card builder, `static/situations.js`, a new slot) linking to `link()`; drawn only when `visible` for the viewer (the view payload carries `subject: {kind, id, title, link} | None`, already filtered). The Threads page and the Missions page draw it the same way.
- **Pick or change it.** Thread card option `_opt('subject', 'Link to something in Chauffeur', {})`, or `'About: <title> (change)'` when bound, parent/adult, verb `subject` added to `VERBS`; the tap uses `promptInput` for the words, posts `POST /api/situations/thread/{id}/act` with `{verb:'subject', payload:{query}}`; a clear winner retargets, else the response carries the candidates and the card asks with `promptChoice`, then posts again with `payload:{kind, id}`. Clearing: `payload:{clear:true}` ("Unlink"). A manual mission's card gets the same option. Argyle's `act_on_situation` verb `subject` with `text` is the same path. The guard in Section 3 answers with its reason.
- **Back-link.** The trip page and the occasion page show one line, "Argyle: <thread title> — <next step>", for each open thread or live mission whose subject is that record, linking to the Threads page. `GET /api/subjects/{kind}/{id}/situations` serves it (parent/adult; `can_see` applied, which now includes the subject's audience).

## Section 5 — Tests (before the code)

`tests/test_subjects.py`: per kind, `find` ranks exact over substring over sound-fold, drops past and closed at a tie, caps; `visible`/`find` filter before matching (a child never sees a parents-only occasion, a private list, or a sibling's program; `None` sees only household; a spoken call never sees a parents-default trip or a sensitive thread; a miss and an excluded row return the same empty list); `context` returns `None` for an excluded viewer and for a missing id alike, lists a trip's dining POIs with windows under `facet='dining'`, stays under the cap, names the linked lists of an occasion only when the viewer may see each, and says how old a real trip's dates are (draft, calendar with age, unknown); `resolve` returns one on a clear margin and `None` plus candidates on Grandpa/Grandma. `tests/test_mission_subject.py`: a bound mission leads every step's system prompt with ABOUT and fresh context (the record edited between two steps shows the edit; Router: the chat prompt carries ABOUT when the focus thread has a visible subject (`test_agent_router_*` neighbour).

## Section 6 — What this does not do (named so the next slices start here)

A subject-bound mission still proposes one change at a time, still dies at finish, still never writes its result onto the subject, still cannot wait for a date. Slice 2 (plans) adds the interview, the plan preview card, stages, and one approval per stage, each approval stamped with `subject_rev`; slice 3 (wake) adds sleeping between stages and the triggers (date nearing, a reply, a program session), each wake re-reading `context()` and refusing on a changed `subject_rev`. Both read the subject through the same `context()` and bind through the same fields, which is why they are three fields and one module rather than per-kind code in the planner.

## Answers to the first draft's open questions

1. `event` stays a kind: a Needs-You finding binds an event for coverage only; "get the team pictures moved" is a mission about an event.
2. Dining gets a facet now (`context(..., facet='dining')`); the 1,500-character cap stays for the general view.
3. The planner may bind, but only the thread (never a thread-origin mission's own fields), and only when unbound; a person changes or unlinks by hand.
