# Chauffeur Solver & AI Scheduling Assistant Capabilities

This document outlines the core logic, constraints, and weighting mechanics of the Chauffeur Scheduling Solver. It serves as the primary context layer for the AI Scheduling Assistant when parsing natural language into `Rule` JSON objects or when providing scheduling optimization advice.

## Core Solver Mechanics (CP-SAT)

The solver formulates the schedule by assigning drivers to events in a way that maximizes the global "weight" (score) while strictly adhering to hard constraints. 

### Baseline Event Weights & Penalties
When evaluating whether to assign an event to a driver or leave it unassigned:
- **Base Assignment Reward:** `1,000,000` (modified by `unassigned_penalty_multiplier` in Theme settings).
  - *Leaving an event unassigned scores `0`. If a driver's total score drops below 0 for an event, the solver will refuse to assign them and leave the event unassigned instead.*
  - *This value is deliberately large so that assigning an event at all outweighs routing preferences. Compare bonuses against each other, not against this base — it is identical for every driver on the same event and therefore cancels out when choosing between drivers.*
- **Priority Scaling Bonus:** `+150` points per rank. (e.g., Priority 1 driver gets `+1350`, Priority 10 gets `+0`).
- **Driver in Event (Attendee):** `+50,000,000` (Massive bonus if the driver is also attending the event. This is the largest term in the model apart from manual overrides, and in practice it decides the assignment on its own.)
- **Primary Driver Bonus:** `+2000` (modified by `primary_driver_bonus_multiplier`).
- **Manual Override:** `+100,000,000` (plus the override's `created_at` epoch seconds, so newer overrides win). Dominates every other objective term, including the saturated load-balancing penalty (≤1.44M at its cap). Every hard ban in the model also carries an `overridden_pairs` escape — `unavailable` rules, `required`-rule bans on other drivers, driver personal-event overlaps, the passenger-overlap constraint, and the trip-assignment bans — so a drag-and-drop override always sticks regardless of any other setting. Before creating the override, the dashboard dry-runs the pair through `POST /api/overrides/check` (`matcher.explain_assignment_conflicts`): if the solver would normally refuse it (driver away on a trip, passengers away on a trip, unavailable/avoid/required-elsewhere rules, the driver's own calendar event at that time, preferred-hours violation), a confirmation dialog lists the human-readable reasons and asks "Override anyway?" — informed consent, never a silent block. The check reads trip windows/entities from `trip_metadata` persisted in the combined schedule cache.
- **Group Bonus:** `+1000` when both events of a `group` rule go to the same driver.
- **Stickiness Bonus:** `+5` points if they drove the same event in the previous run.
- **Passenger Continuity:** Up to `+50,000` points if a driver handles consecutive events back-to-back with the same passenger. This decays linearly to `0` dynamically based on the specific travel gap threshold where a driver would typically have enough time to go home for a layover (e.g., 75+ minutes).
- **Location Continuity:** Up to `+5,000` points if a driver handles consecutive events at the exact same location, decaying linearly to `0` at a 3-hour gap.

**Penalties:**
- **Travel Time:** Scaled heavy penalty (approx `-600` points per 10 minutes) of driving from the previous event's location to the next. This penalty *only* applies if the gap between events is 1 hour or less, to avoid unfairly penalizing drivers for taking completely independent trips separated by long layovers at home.
- **Tolerance Overlap:** Heavy dynamic penalty (`-50,000`) if an event relies on a tolerance rule to be feasible for a primary driver. The penalty comfortably overcomes the primary driver bonus (`+2000`) and group bonus (`+1000`) combined, so the solver prefers a clean secondary driver over a primary driver who has to be late. It does **not** overcome the attendee bonus or a manual override, and it exactly ties the maximum passenger-continuity bonus (`+50,000`) — so at a near-zero travel gap, continuity can cancel it out.
- **Preferred Hours Violation:** `-2,000,000` points if an event falls outside the driver's preferred working hours. At default settings this drives the score below 0 (`1,000,000 - 2,000,000`) so the event stays unassigned. It does **not** hold if the driver is an attendee (`+50,000,000` swamps it) or if `unassigned_penalty_multiplier >= 2.0`.
- **Soft Buffer Violation:** `-2,000` points if an event slightly overlaps a buffer zone.

### Load Balancing Mode (optional)
Toggled by `load_balancing_enabled` in Settings (Config → Drivers tab; default **off**), with a companion `load_balancing_metric` combo box choosing what "load" means. By default the solver has **no fairness term**: per-event driver scores are independent, so the highest-scoring driver (primary group, lowest `priority_index`) absorbs every event they can physically fit ("bucket filling"), and the stickiness and continuity bonuses reinforce that concentration across runs.

When enabled, the solver subtracts a **quadratic penalty on each driver's daily load** (sum-of-squares is minimized by an even split, so each additional event on a loaded driver costs more than the same event on an idle one). The metric sets the per-event load value and penalty coefficient:
- **`events`** — 1 per event, coefficient `10,000`. Fair by count, ignores duration and distance.
- **`driving_time`** — round-trip minutes from the driver's home (falling back to the global `home_location`) to the event, clamped to 240, coefficient `5`; unknown routes cost a neutral 60 so a home-less driver never becomes a free sink. This is a **proxy**: true driving is only known after assignment, and chained events share travel, so back-to-back same-location events each count a full round trip. A driver living at the venue genuinely has zero driving load and will soak up those events — by design.
- **`occupied_time`** (default) — summed event durations in minutes (each clamped to 600), coefficient `1`.

Interaction with other weights (all metrics):
- **Overrules:** the Priority Scaling Bonus (`+150`/rank) and Primary Driver Bonus (`+2000`) — a typical one-event move gains ~10k–40k points.
- **Does not overrule:** Attendee bonus (`+50M`), Manual Overrides (`+100M`), or `required` rules. Tight passenger-continuity chains (up to `+50,000`) also survive unless the imbalance is severe.
- **Never causes unassignment:** each driver's load saturates at a per-metric cap (`AddMinEquality`), bounding the marginal penalty of one more event strictly below the `1,000,000` base assignment reward.
- Balancing counts only solver-assigned driving (including self-driven attendee events); personal calendar events that need no driver are not counted.

### Cars & Vehicle Assignment (C1, v2.47.0 — docs/car_entity_design.md)
Cars are an optional entity (Config → People tab → Cars; `/api/cars`; `Car` in `models/schemas.py`). Each car has: `seat_capacity` (passenger seats, excluding the driver), `allowed_driver_ids`, optional `allowed_passenger_ids` (car-seat restrictions; `null` = anyone fits), optional `default_driver_id` (the "usual" driver), `unavailable_ranges` (inclusive ISO date ranges — loaned out, in the shop), and `is_disabled`.

- **Inert when unconfigured**: with zero cars the solver builds no car variables or constraints — behavior is identical to the pre-car model, and `car_assignments` (4th return value of `solve_schedule`, `event_id → car_id`) is empty.
- **Implicit personal car**: a driver listed in **no** car's `allowed_driver_ids` is untouched by every car constraint. Only "pooled" drivers (listed on ≥1 car) must draw a workable car for each assigned event: the car must permit them, fit the event's passengers (count and, if restricted, identity), and not be in an unavailable range. A pooled driver with no workable car is banned from the event — escapable by manual override like every other hard ban.
- **Contention & handoffs**: a car is never in two places at once. Two different drivers may reuse the same car for nearby events only if the gap covers `travel(e1 → home) + travel(home → e2)` — handoffs happen at home; midday non-home handoffs are deliberately unmodeled. A driver chaining back-to-back events keeps the same physical car (and cannot chain into an event their current car can't serve without time to swap at home).
- **Swap penalty `−2500`**: using a car whose `default_driver_id` is someone else. Above priority deltas (≤ ~1,500) so priority alone never forces a key swap; below a `preferred` rule (`+10,000`) so rules can. Car chips render everywhere driver assignments do: calendar week/day badges (short ≤40-min events use a compact single-row layout: title + pax dots + car + driver, no time line), the calendar Agenda view, admin dashboard schedule columns, PWA family cards, the PWA driver view ("Take the {car}" per drive), and the kid lens ("Dad is driving you in the Minivan" — rides and legs carry a `car` object in `/api/member_day`). Swaps get an amber `⇄` accent.
- **`Driver.max_passengers`** (optional): driver-level passenger cap independent of cars (teen graduated-licensing laws). Applies even with zero cars configured; override-escapable.
- **Diagnostics**: unassignment reasons of type `"car"` — "No car this driver may drive works for this event: …", per-car failure detail (seats, car-seat restriction, unavailable + reason), and the `max_passengers` cap. Static bans only; a car merely claimed by another driver at that hour falls through to the generic conflict/optimization reasons.
- **Agent tool** `manage_car` (v1 registry, bridged to the chat widget): create/update/delete cars and `set_unavailable`/`clear_unavailable` date ranges ("the minivan is loaned to Aunt Sarah through Friday"). Cars also appear in `get_current_state`.
- **Photos** (v2.48.0): cars and family members can carry an `image` — a ~128px square data-URL photo, client-side cropped/resized on upload (Config → People / Cars), stored in the entity document (no file hosting). Photos win over emoji/initials wherever the surface has room: config lists, PWA member switcher and driver header, kid-lens driver chips and the "in the {car}" line, the driver-view Take-the-car chip, family-map markers, chores/routines tiles. Tiny calendar/dashboard chips stay icon+name.
- **Not modeled in the solver**: live car location, cars consumed by a pooled driver's personal (non-solver) events, mileage-based energy math.

## Travel Time Data & Caching
Travel times come from Mapbox's Matrix API using the free-flow `driving` profile (no traffic-aware profile is requested anywhere, and cached reads always report a traffic delay of `0`). Durations are therefore treated as **static**: a cached value for a pair of fixed addresses does not go stale, and the solver reads them without an age check.
- **Priming**: each schedule refresh primes only the location pairs it does not already have. Stale-but-valid pairs are never re-purchased — doing so previously exceeded the 100,000 element/month Matrix allowance.
- **`route_cache_duration_mins`**: defaults to `43200` (30 days). It only needs shortening if a traffic-aware profile is introduced.
- **Unroutable pairs**: when a location cannot be geocoded or the routing APIs fail, the pair is cached as `-1` and reported to the solver as `900` minutes (effectively unreachable). This suppresses retry storms against the API quota, but expires after **24 hours** so that a transient outage cannot permanently poison the cache.
- **Geocode precision & self-healing (v2.56.4)**: geocode-cache rows carry `precision` (`exact` | `city` | `failed`) + `ts`. Exact street-level hits are final; city-fallback and failed entries retry daily (`maps._usable_cached`, `GEOCODE_RETRY_SECS`) — a single bad geocode can never weld an address to the city center permanently (the old code cached the city fallback under the full address forever). Legacy pre-precision rows are sniffed on read (address starts with a house number the display_name doesn't echo → treated as city, retried immediately). Re-saving Home Location purges a non-exact home entry (a user-visible fresh-lookup lever); a *changed* home always purges.
- **The amputation bug (fixed v2.56.4)**: `extract_street_address` dropped the FIRST comma part of any >3-part address as a "business name" even when it was the street line itself — so Mapbox-canonical addresses ("123 St, City, State ZIP, United States") geocoded to the city center, poisoning home, event locations, and every Matrix travel time derived from them. Fixed (a digit-leading first part is kept whole) + one-time startup migration (`migrations.migrate_geocode_amputation_v2564`, app_state-gated): purges sniffably-wrong geocode rows and resets distance/route/schedule caches so durations re-derive from healed coordinates. Tests: `tests/test_geocode_cache.py`.
- **Home-pin transparency**: `/api/cars/stations/nearby` returns `home_label` + `home_precision`; the Config station map's 🏠 pin popup and caption show exactly what the home address resolved to, with an amber warning when it's only city-level — a wrong home pin is VISIBLE, never silent.
- **Travel-time forensics (v2.56.5)**: `GET /api/debug/travel?event=<title substring>` (or `?destination=`, `&origin=` override, `&fresh=true`) answers "why does the app think X is N minutes away": both addresses' cleaned form, geocode result (display name + precision — a wrong venue match is visible), straight-line km, the cached Matrix duration the solver uses, and with `fresh=true` a free-flow vs **driving-traffic** Directions comparison — separating "geocoded the wrong place" from "free-flow profile vs rush hour". Location-less events are reported as the problem instead of routed. v2.56.6 adds a `drivers` section: each driver's ACTUAL routing origin — a driver record's own `home_location` OVERRIDES the global home in the solver's initial edges (matcher.py `driver_default_home`), so a stale per-driver address produces leave-at chips that disagree with the global-home pair; `uses_own_address: true` with a different `resolved_to` is the smoking gun. Remember the standing design choice this tool exposes: Matrix durations are static free-flow (no traffic), so rush-hour drives read optimistic by design.

## Storage Engine
All persistence goes through `services/storage.py`, backed by **SQLite** (`data/chauffeur.sqlite3` locally, `/data/chauffeur.sqlite3` on the HA add-on) as of 2026-07-16. It is a document store — one table per legacy TinyDB table, each row `(doc_id, JSON data)` — accessed via a TinyDB-compatible table API (`services/storage_sqlite.py`), so callers still pass `tinydb.Query` objects. WAL mode; writes are single-row and take ~1 ms (previously TinyDB rewrote the entire 4.8 MB JSON file per write, ~275 ms).
- **Toggle**: `CHAUFFEUR_STORAGE=tinydb` env var is a one-release escape hatch back to the legacy engine; `CHAUFFEUR_DATA_DIR` redirects the data directory (used by tests, which must never touch `data/`).
- **Migration**: first sqlite boot auto-migrates `db.json` + `routes_cache.json` (route geometry now lives in the same SQLite file), preserving doc_ids and deduplicating the distance/geocode caches; originals are kept as `*.pre-sqlite.bak`. Restore-from-JSON = delete the `.sqlite3` file, place a `db.json`, restart.
- **Backups**: `/api/download_db` zips the data dir, snapshotting the SQLite file via the backup API (safe under WAL).
- **`db_lock`**: the coarse process-wide lock in storage.py is still in place (cheap now); removing it is a separate planned cleanup.

## Rule Attributes & Filters
Every rule (Routing Rule or Priority Rule) can filter events using any combination of the following criteria. The solver evaluates these using AND logic across different criteria types.
- **Keywords**: Match substrings in the event title or description. (Match Any or Match All).
- **Passengers**: Match specific passengers who are attending the event. (Match Any or Match All).
- **Days of Week**: Restrict rules to specific days (0=Monday, 6=Sunday).
- **Date Window (`start_date`, `end_date`)**: Restrict a rule to only apply on or after a specific start date (YYYY-MM-DD), and/or on or before an end date. Useful for driver vacations, summer schedules, or holiday-specific rules.
- **Time Window (`time_start`, `time_end`)**: Restrict a rule to a specific time of day window.
- **Location**: Match a substring in the event location.

## Supported Constraints (`constraint_type`)

When generating JSON for the frontend to digest, use the following `constraint_type` mappings.

### 1. Driver Assignment
Controls how the solver treats a specific driver for an event. Each of these is its own top-level `constraint_type` value — there is **no** `"assignment"` constraint_type and **no** `assignment_type` property. `Rule` has no such field, so a rule shaped that way is silently discarded by the schema and does nothing.

All four require `driver_id` to name the driver the rule applies to.

* `constraint_type: "required"` (Hard Constraint)
  * The selected driver MUST be assigned. All other drivers are strictly prohibited. The named driver also receives a `+500` weight bonus.
* `constraint_type: "preferred"` (Weight Bonus)
  * Grants a massive `+10000` weight bonus to the selected driver. They will almost certainly get the assignment unless physically impossible.
* `constraint_type: "unavailable"` (Hard Constraint)
  * The selected driver is strictly forbidden from taking the event.
* `constraint_type: "avoid"` (Soft Penalty)
  * Caps the driver's score at `1` — above `0` (the score of leaving the event unassigned) but below every viable driver. The driver is pushed to the absolute bottom of the priority list yet is still chosen as a "last resort" rather than leaving the event unassigned. A driver already excluded for another reason (e.g. a preferred-hours violation, which yields a negative score) stays excluded; `avoid` never resurrects them.

### 2. Duplicate Event Handling (`constraint_type: "duplicate"`)
For recurring events or overlapping schedules.
* `duplicate_action: "schedule_one"`: The solver will only schedule *one* matching event per `grouping_period` (daily, weekly, monthly, all).
* `duplicate_action: "schedule_all"`: Schedule all occurrences as normal.

### 3. Tolerance - Late Arrival / Early Departure (`constraint_type: "tolerance"`)
Allows an event to be "fudged" to make an otherwise impossible schedule fit.
* `tolerance_mins`: Integer. How many minutes the solver is allowed to overlap.
* `tolerance_type`: `"arrival"`, `"departure"`, or `"both"`.

### 4. Group Events (`constraint_type: "group"`)
Forces the solver to assign the exact same driver to a set of different events.
* Uses the `filter_sets` array instead of standard keyword/passenger filters. Each element in the array represents a distinct event match (e.g., grouping Lily's 8:00am swim practice with James's 9:00am tennis practice).

### 5. Buffer Time (`constraint_type: "buffer"`)
Enforces artificial padding around an event for a driver.
* `buffer_before_mins`: Integer.
* `buffer_after_mins`: Integer.

### 6. Event Attendance (`constraint_type: "attendance"`)
* `attendance_action: "stay"`: The driver must stay at the event for its entire duration.
* `attendance_action: "dropoff_pickup"`: The driver will split the event into a distinct Drop-off (at the start time) and a Pickup (at the end time). The driver is free to do other things during the event duration. The Drop-off and Pick-up are treated as independent events and are NOT grouped together, meaning they can be freely assigned to different drivers.

## Priority Rules (`PriorityRule` objects)
Distinct from standard rules, priority rules allow dynamic modification of the `Base Assignment Reward` (`1,000,000`) on an event-by-event basis. The `weight_modifier` is added to that base verbatim — there is no rescaling or remapping.
- **Why use this?** If the user says "Doctor appointments are the most important thing to schedule," you create a Priority Rule with `keywords: ["Doctor"]` and `weight_modifier: 100000`. This ensures the solver prioritizes finding *any* driver for the doctor appointment before solving other low-priority events.
- **Choosing a magnitude.** The modifier only matters relative to the *other* terms it competes with, since the base is identical across events. Useful reference points: `1000` is a mild nudge (enough to break a tie, roughly 17 minutes of travel penalty); `100,000` outranks the maximum passenger-continuity bonus (`+50,000`); `500,000` is effectively "schedule this before anything else." Negative values deprioritize. Nothing outranks the attendee bonus or a manual override.

## Matching Logic
- **AND vs OR:** Across different criteria types in a single rule (e.g., Keywords AND Passengers AND Days), the solver uses `AND` logic. An event must meet all configured criteria types.
- **Match Any vs Match All:** For criteria that support multiple selections (Keywords, Passengers), the solver defaults to "Match Any" (OR logic). 
  - For example, if two passengers are selected, the rule matches if *either* is an attendee.
  - This behavior can be toggled using the `keywords_match_all` and `passengers_match_all` boolean flags. When set to `true`, the solver switches to "Match All" (AND logic) for that specific criterion, requiring all listed keywords or passengers to be present on the event for the rule to match.
- **Filter Sets (Groups):** For grouped rules with multiple `filter_sets`, the evaluation across sets is an `OR` logic (matches if it hits Group A OR Group B).

## Best Practices for AI Recommendations
1. **Never use "Avoid" to completely block a driver.** If the driver absolutely cannot do it, use `unavailable`. Only use `avoid` if the driver should be a last resort.
2. **Use Group Events sparingly.** Grouping large chains of events can drastically reduce solver feasibility (making it "too sticky").
3. **Recommend Tolerance for tight schedules.** If the user complains that events are going unassigned due to 5-10 minute overlaps, recommend adding a `tolerance` rule to allow minor late arrivals.


## User Interface Architecture
- The Rules tab is divided into two sub-tabs: 'Routing Rules' and 'Priority Rules', controlled by Alpine.js state.
- Rule creation forms are located at the top of each sub-tab, before the respective rule lists.
- **Kiosk Mode (`?kiosk=true`)**: A streamlined display state that hides the triage inbox and header chrome while maximizing schedule visibility. In kiosk/read-only mode, driver columns with no real events for a day are hidden; background-trip banners (which are injected into every column for context) do NOT count as real events, so rule-unavailable or trip-absent drivers stay hidden on trip days. The regular editable dashboard always shows every real driver column so events can be dragged onto them. Ghost columns are identified by the exact `ghost_` id prefix (a bare `g` prefix check once hid real drivers whose ids start with "g" on their empty days). Driver columns are ordered: primary group first, then secondary, then `priority_index` within each group (1 = highest, first), alphabetically by name within the same priority; ghost columns always sort last. The event modal shows details only — the Matched Rules / Diagnostics tabs (including unassigned-reason diagnostics and suggestion actions) are suppressed in kiosk mode. The standard bottom-center Argyle chat box remains the single chat entry point (the old floating chat FAB/popup was removed from the dashboard — it survives only in the PWA `app.html`, where it is the mobile chat surface).
- **HA Theme (`?theme=ha`)**: Supports Home Assistant integrations via CSS variable propagation without overwriting the core Tailwind configuration palette. State is persisted across navigation views.
- **Identity colors (single source of truth)**: a person's color everywhere (event bars, passenger pills, driver columns/chips) is the family member's `color_code`. - **Voice via Home Assistant Assist ("Hey Argyle")**: `POST /api/v2/converse` accepts `{text, language, conversation_id?}` and returns HA conversation-agent JSON. When HA supplies a `conversation_id` (stable across follow-up turns of one voice session), the endpoint threads history through the same conversation store as `/api/chat` (ids prefixed `voice-`, titled 🎙️ from the first utterance — no LLM naming call), giving voice multi-turn memory; replies also mirror onto the `/api/v2/chat/stream` SSE bubbles. The agent loop (max 3 iterations; models come from the **free-tier model pools** (`services/model_pools.py`, v2.30.0): the interactive tier walks the flash-lite pool (`gemini-3.5-flash-lite`, `gemini-3.1-flash-lite` — 500 req/day each, seconds per answer; `gemini-2.5-flash-lite` 20/day tail) then overflows into the gemma pool (`gemma-4-31b-it`/`gemma-4-26b-it`, 14,400/day each but 44-180s/call measured 2026-07-30); the scarce 20/day `gemini-*-flash` models are reserved for the heavy tier and never burned on chat turns. A 429 cools the model down — until midnight Pacific when the error names a per-day quota, else 2 min — so the next turn skips straight to a model with quota left; max 4 candidates per call, 60s read timeout on fast models and 90s on gemma, keeping worst case inside the HA 120s budget. Pools overridable via `model_pool_lite`/`model_pool_flash`/`model_pool_gemma` comma-separated settings keys, no UI; the old `agent_primary_model`/`agent_fallback_model` keys are retired) **early-exits after a round consisting only of successfully completed action tools** (assign/trip/route mutations that return their own spoken confirmation) instead of making a concluding LLM call — timing data showed that extra round re-issued the same action instead of concluding; identical repeated tool calls are also deduped (result reused, never executed twice). Query tools (`get_calendar_events`, `get_my_route`) always loop so the model can use the data; `get_calendar_events` includes each event's `assigned_driver` (name, joined from `assignments` + `ghost_assignments`; null = unassigned) so the agent can answer per-driver schedule questions — without it the model saw events with no drivers and reported empty schedules. Every agent prompt is injected with `CURRENT DATE & TIME` (weekday, YYYY-MM-DD, HH:MM, server tz) plus an instruction to resolve relative dates before calling tools — without it the model cannot resolve "tonight"/"this week" and guesses wrong date ranges; `assign_driver_to_event_fuzzy` also accepts 'tonight'/'this evening'/'tomorrow night' directly, matching `_parse_fuzzy_date`'s handling for route tools. Keep single-action commands to ONE LLM call: the HA conversation component aborts at 120s, so a 2-call run risks the spoken "couldn't reach Chauffeur" while the server still completes the action. Voice always runs the admin toolset (no source/driver_id). ## Free-Tier LLM Model Pools (services/model_pools.py, v2.30.0)

Every Gemini call in the app routes through quota-bucket pools so same-ability models combine their free-tier daily limits (each MODEL has its own quota; caps as of 2026-08-02):

- **lite** — `gemini-3.5-flash-lite` (500/day), `gemini-3.1-flash-lite` (500/day), `gemini-2.5-flash-lite` (20/day tail) → ~1,020 fast requests/day.
- **flash** — `gemini-3.6-flash`, `gemini-3.5-flash`, `gemini-3.1-flash`, `gemini-3-flash`, `gemini-2.5-flash` (20/day each) → ~100 quality requests/day.
- **gemma** — `gemma-4-31b-it`, `gemma-4-26b-it` (14,400/day each) → ~28,800/day, but 44-180s per call.

Tiers map work onto pool chains: **interactive** (chat widget, @argyle, PWA driver chat, HA voice, prep-kit suggest, refine button, v1 loop, conversation auto-naming) = lite → gemma — the user is waiting, and scarce flash is never burned on chat; **background** (email ingest, chat-suggestion classifier) = gemma → lite — nobody is waiting, burn the huge gemma quota first; **heavy** (massive trip generation incl. accommodations/flights/date suggestions, philosophy → rules, override-pattern analysis) = flash → lite → gemma — rare, quality-critical. A 429 puts the model on cooldown (until midnight Pacific when the error body names a per-day quota, else 2 min for per-minute limits; unknown-model 404s cool 6h and log loudly) so subsequent calls skip straight to a model with quota left — this is what makes pooling additive instead of retrying a dead model. `call_pool_json` walks up to 4 candidates per request; `pooled_or_direct` is the drop-in at provider-branched call sites (ollama keeps its single configured model, untouched by pools); `resolve_model(tier)` serves call sites with their own request code (v1 `agentic_chat_loop`, which feeds 429s back via `note_failure`). Pools are overridable without a code change via `model_pool_lite`/`model_pool_flash`/`model_pool_gemma` comma-separated settings keys (no UI). The `llm_gemini_model` setting now only affects the config-page connection test and ollama-parity defaults; the old `agent_primary_model`/`agent_fallback_model` keys are retired. Cooldown state is in-memory (resets on add-on restart — worst case one wasted 429 round-trip per model).

## PWA Driver Chat (driver-context agent)
The driver PWA (`app.html`) chat posts to `/api/chat` with `source: 'pwa'` and the logged-in `driver_id`; `handle_chat` forwards both into `agent_router.process_agent_request`. When the driver id resolves to a real driver, the Gemma router switches into **driver mode**:
- **Prompt**: identifies the driver by name, mandates brief mobile-friendly replies, and injects the driver's TODAY schedule (titles, locations, times, drive statuses) directly into the system prompt — zero extra LLM requests.
- **Driver tools** (registered only in driver mode; `driver_id` is injected server-side at dispatch, never taken from the LLM):
  - `get_my_route(target_date)` — the driver's assigned events (real + ghost assignments from the combined schedule cache) with per-event drive status.
  - `start_route(event_name)` — fuzzy-matches an event on the driver's day and marks its drive legs `in_progress` (same `drive_status` store as the PWA's Start Drive button).
  - `complete_route(event_name, action)` — records a TelemetryEvent (`picked up`/`dropped off`/`arrived`/`completed`, mirroring the Mark Completed button) and marks the legs `completed`.
- **Leg-id convention**: the PWA constructs drive-leg ids client-side (`init_{ev}[_1|_2]`, `route_{ev}_1..3`, `final_{ev}`); the tools mark the whole id family so timeline pills light up regardless of route layout. Unused ids are inert.
- The admin/dashboard chat (`source: 'admin'`) never sees driver tools. The v1 stack (`agentic_chat_loop`) has its own PWA prompt branch but is NOT the live path for the chat widget or PWA — both go through agent_router/agent_tools_v2.

- **v1→v2 tool bridge** (`agent_tools_v2.get_bridged_v1_tools` / `BRIDGED_V1_TOOLS`): the v2 pipeline natively covers messaging, chores, trips and driver overrides, but the scheduling-core (`add/delete_routing_rule`, `add/delete_priority_rule`, `run_solver`, `get_current_state`), the errand domain (`add/update/delete/get_errand`, `add/delete_errand_rule`), `update_memory`, `search_places`, and deep trip planning (`generate_trip_plan`, `add/edit_trip_accommodation`, `edit_trip_poi`) live only in the v1 handler table. ## Family Chat Agent (`@argyle`)
The family chat (chat_channels/chat_messages) is a vector of action, not just messaging. When a member posts a message containing `@argyle` (case-insensitive) to `/api/channels/{id}/messages`, `send_message` fires a background task (`_run_argyle_mention`) that routes the message to `agent_router.process_agent_request(source='family', acting_member=<sender>)` and posts the reply back into the same channel as the **Argyle system member** (`storage.ensure_argyle_member`, fixed id `argyle`, `role='assistant'`, `system=True` — excluded from the human roster and the agent's family-name list, but resolvable as a sender name for rendering).
- **Known identity, no asking**: `acting_member` injects the speaker's name/role into the system prompt so the agent resolves "me/my/I" and passes `from_member`/`member_name` automatically — the authenticated in-app member IS the identity layer (no PIN/DM guessing).
- **Role scoping**: `bridge_ok = (not driver) and (acting_member is None or _is_admin_member)`; only parents/adults get the admin scheduling tools (routing/priority rules, solver, errands). Children and helpers keep the everyday family-hub tools (reads, messaging, their own chores) but the admin tools are withheld both from the offered toolset AND the dispatch guard (a hallucinated tool name can't execute). Legacy callers (admin dashboard, HA voice) pass no `acting_member` and are unchanged.
- Argyle never re-triggers on its own posts (guarded by `sender != ARGYLE_MEMBER_ID`). Runs off-request because an agent turn can take tens of seconds; the reply arrives via the same SSE/push fan-out as any message.

### Interactive action cards (propose → approve)
Schedule-changing requests in the family chat are not executed silently — the agent proposes them as an interactive card a parent approves with one tap (`services/chat_actions.py`, `agent_action_proposals` table).
- **Agent tool** `propose_family_action(action_type, summary, payload)` (offered to the family chat): creates a typed proposal and returns a `card` the router surfaces onto Argyle's reply (`ChatMessage.card`). The family-chat prompt steers all mutations (reassign driver, mark unavailable / routing/priority rules, add errand) through this tool; reads/messages/chore claims stay direct.
- **Typed actions** (`ADMIN_ACTIONS`, each executed via the same tested handler the agent would call directly): `reassign_driver` (→ `assign_driver_to_event_fuzzy`), `clear_assignment` (→ `remove_override_for_event_fuzzy`), `add_routing_rule`/`delete_routing_rule`, `add_priority_rule`/`delete_priority_rule`, `add_errand`/`update_errand`/`delete_errand`/`add_errand_rule`, and `create_event` (→ `calendar.insert_event` on `settings.default_calendar_id`). Cards carry a human `action_label` (`ACTION_LABELS`) rendered as a badge. **`create_event` normalizes the LLM's datetimes (v2.28.7)**: the model reliably emits NAIVE ISO strings and Google 400s any `dateTime` without a zone ("Missing time zone definition") — which surfaced as a bare "the calendar rejected the event" AFTER the parent approved. `_create_event` now attaches the server's local offset to naive datetimes (zoned ones pass through), bumps a same-day all-day end to Google's exclusive convention, and returns specific messages for unparseable times / end-before-start / the calendar-rejection fallback (which now names the target calendar). **Named timezone stamping (v2.28.8)**: an offset-only `dateTime` is a correct instant but Google pins the event to a fixed "GMT-05:00" pseudo-zone, which looks broken in the Calendar edit UI — `calendar.get_calendar_timezone(calendar_id)` (calendars.get, process-lifetime cache, None on failure → field omitted) supplies the calendar's real IANA zone, stamped as `start/end.timeZone` on timed inserts in BOTH creation paths (intake `approve_proposal` and chat `_create_event`). Tests: `tests/test_chat_actions.py::scenario_create_event_normalizes_datetimes`.
- **Approval is the gate**: `POST /api/action-proposals/{id}/act` with `{act: approve|dismiss, member_id}`. Approve enforces the parent/adult scope (a child's tap is refused, the proposal stays open), executes the action, flags `schedule_dirty`, and Argyle posts the outcome + updated card back into the origin channel. Proposals are single-use (re-approving a resolved one errors).
- **Card lifecycle**: `proposed` (Approve/Dismiss buttons) → `approved` (✓, static) or `dismissed`. Frontend renders `m.card` in `app.html`; the Argyle system member is filtered out of member pickers/passenger lists but resolved as a sender name in-thread.

### Implicit detection funnel (opt-in)
When `settings.chat_suggestions_enabled` is on (toggle: Config → **Family Chat Assistant → Proactive Chat Suggestions**, off by default), a non-`@argyle` family-chat message runs a tiered funnel (`chat_actions.run_suggestion_funnel`) so the bot can *offer* help without being asked — but never butts in:
- **Tier 1 — keyword pre-filter** (`suggests_action`, deterministic, in `send_message`): high-precision phrases only ("can't drive", "we're out of", "reschedule", …). Ordinary chatter never reaches the agent. High-recall by design; precision comes from the next tiers.
- **Tier 2 — fail-closed classifier** (`classify_actionable`): one cheap single-shot LLM call returning `{actionable, confidence}`; any error / missing key → `actionable:false`. Must clear `SUGGESTION_CONFIDENCE_THRESHOLD` (0.6).
- **Tier 3 — agent + card gate**: runs the agent as the sender and posts a suggestion **only if it produced a concrete proposal card**; otherwise stays silent (never posts plain chatter). The surfaced card is an ordinary Layer-2 `action_proposal` — nothing executes until a parent approves. Suggestion, never action. Start narrow and expand `SUGGESTION_PATTERNS` as real `@argyle` usage reveals the intent distribution.

## Household Status Days (Presence & Status arc P1–P3b, v2.53.0–v2.56.0)
Family day-types ("Chemo Day", "Night Shift", "Trip Day") that answer a kid's scariest question — what state will home be in — BEFORE they walk through the door. Design: `docs/presence_status_design.md`; service: `services/status_protocols.py`; tests: `tests/test_status_protocols.py`.
- **StatusProtocol** (authored once, Config → People → Status Days): `name`/`emoji` (the family's label), `member_id` (the affected member), `need` (`cover` | `help` | `clear_deck` | `give_space`), `kid_message` + `adult_message` (**the family's own words, delivered verbatim** — the system schedules and delivers, it never composes kid copy), `keywords` (calendar trigger words). **StatusDay** is one dated instance (`date`, `protocol_id`, `note` = the one-tap "today's different" nudge, `set_by`, `source` `manual`|`calendar` + `source_detail`). Date-bound BY DESIGN: staleness is structurally impossible — yesterday's status never lingers.
- **The calendar knows (P2 sweep)**: every 30 min (quiet-hours gated, marker-first), `status_protocols.auto_set_from_calendar` scans the cached schedule window (7 days, errands excluded) for protocol keywords in event title/description and AUTO-SETS matching days (`source='calendar'`) — the set-burden lands on nobody, which is the point (the affected parent is least able to tap on their worst day). Safety is the beat design, not a permission prompt: the family authored the keywords deliberately, adults are DM'd immediately naming the matched event and how to undo, and kids only ever hear today/tomorrow — an advance auto-set has a built-in adult review window. Clearing a calendar-set day writes a 30-day tombstone (`app_state.status_auto_dismissed`) — a parent's dismissal is final, the sweep never re-sets it. Same protocol+date is idempotent.
- **Solver needs (P2)**: in `refresh_schedule_logic`, status days with `need` `cover` (they're resting/at treatment) or `help` (they're being cared for) become synthetic one-day `constraint_type='unavailable'` Rules for the affected member's driver (`status_protocols.unavailable_driver_dates`, today→+14d) — the existing matcher bans + "marked unavailable" diagnostics do the rest. Immune to the standard/AI rule enable toggles (a chemo day is not a routing preference). `clear_deck`/`give_space` never touch driving. Status-day/protocol mutations truncate the schedule caches like rule mutations, so the solver always sees current days.
- **Setting a day** (`POST /api/status/days`, the My Day quick-set for parents/adults, or the `set_household_status` agent tool in BOTH stacks — v1 handler bridged to the v2 router): kids get an Argyle DM with the family's words (today/tomorrow only — announcing Thursday's chemo day on Monday just moves the dread up; further-out days wait for the D-1 digest; kid quiet hours SKIP), and the other adults ALWAYS hear it (logistics message + need + who set it; the setter is excluded). Same protocol + same date refreshes note/setter instead of stacking. **Clearing announces too** — "never guessing" runs both directions (kids get the relief for today/tomorrow; adults always).
- **Surfaces**: status lines LEAD the kid evening digest and kiosk strip (`_build_kid_digests` — and a status day includes EVERY kid, overriding the "nothing means nothing" omission), a banner tops My Day (`member_day` returns `status_days`; kids see `kid_message`, adults see `adult_message` + need + ✕ clear armed two-tap), and the K4c dismissal push carries the status line on the SAME push (one push, not two) — and on a status day fires even with no ride/bus ("💙 About today"), breaking the silence rule for that day only.
- **Trip timeline (P3 spans)**: `StatusDay.end_date` turns an instance into a multi-day span (a trip, a hospital stay) — set via Config (date "to" date), the agent (`end_date` on `set_household_status`: "Dad's away Tuesday through Friday"), or the sweep (which collapses cached `_slice_N` trip slices back to their real event so a 5-day trip becomes ONE span, exclusive-midnight ends handled). Surfaces are day-position aware (`day_pos`/`day_count`/`is_home_day`): day 1 speaks the family's full message, middle days go light ("🧳 Work Trip — day 2 of 4"), the last day is the excited home beat ("🏠 Dad — home day! 🎉"); the set-announcement gives kids the whole span up front (home day + call ritual — "never guessing" includes when it ends). `StatusProtocol.call_time` adds a SOFT nightly call window on away nights ("📞 Around 7:30 PM — call with Dad") — worded "around", never on the home day, never a streak; a missed call reads as "catch you tomorrow". The mid-span clear announces as the home-early moment. Solver: one `unavailable` Rule spans the whole range.
- **Beat timelines (P3b, v2.56.0 — the general model)**: `StatusProtocol.beats` is a list of family-authored `(when, who, what)` beats — `anchor` (`start`|`end`) + `offset_days` (negative = before), `audience` (`kids`|`adults`|`affected`|`everyone`), `message` (verbatim), optional `need` override. This is what the fixed positional model couldn't express: **a one-day chemo event whose hard days come AFTER it** — day+1 rest-day words with `need=cover`, day+3 recovery words with `give_space`, care logistics to the co-parent, a "the schedule's covered, don't look at it 💙" note to the affected member. Resolution: a date is a status day if the span covers it OR a beat reaches it (`MAX_BEAT_REACH_DAYS` 45 bounds the query); an authored beat's words REPLACE the default line for that day per audience; a beat's `need` wins for that date (relaxing a span's cover mid-trip, or extending a ban past a one-day event — but a message-only beat outside the span never silently extends a driver ban). The solver feed is therefore per-date (`unavailable_driver_dates` emits one-day rules). Delivery: kids beats ride the existing surfaces ONLY (digest previews tomorrow's beat, My Day banner, dismissal push — no new pings); adults/affected beats DM once per (instance, beat, date) via `send_beat_dms` in the 30-min sweep, `adults` excluding the affected member. Beat-less protocols keep the P3 positional behavior byte-identical. Authoring: Config → Status Days → Timeline beats rows — the offset renders as an explicit [N] × [day(s) before | on the day of | day(s) after] × [the start | the end] control (v2.56.1; storage stays a signed `offset_days`, negative = before — prep days like start−2 were always expressible, the signed-number UI just hid it). The agent still never authors protocols.
- **Coverage report (P3 plan-assist — the arc's crown jewel)**: for every upcoming/ongoing `cover`/`help` instance, the OTHER adults get one Argyle DM showing the span's schedule as the solver re-solved it without the affected driver — every event with its resolved driver, "⚠️ needs a driver" flags, and an open-count footer. `status_protocols.send_coverage_reports` runs in the 30-min sweep; it SKIPS while the post-invalidation re-solve is pending (marker set only after a successful build, so it retries instead of going silent) and sends once per instance (60-day pruned marker). Never sent to the traveler; give_space/clear_deck days generate none.
- Rules of calm: never nag/streak, quiet hours gate all kid sends (skip, never defer), the correction path is mandatory, and protocol authoring belongs to the family — the agent can set/read/clear days but never creates day types.

## Presence — Moments (Presence & Status arc Slice 4, v2.57.0–v2.58.0)
Whoever IS at an activity posts a photo/clip moment into the event's chat (the event-modal button is named **Moments**); it reaches everyone the schedule kept away. Design: `docs/presence_status_design.md` (Slice 4); service: `services/presence.py`; tests: `tests/test_presence.py`.
- **The capture prompt is the feature** (`presence.run_capture_prompts`, 2-min cadence in `push_notification_loop`, marker-first): within the FIRST 20 min of a live ≥30-min event (i.e. the opening minutes — typically 0–2 min after start), present ADULTS get "📸 You're at {title} — send the family a moment", deeplinked `open_channel={id}&compose=moment` (the PWA arms the 📷 button with a pulse — browsers won't open a file picker without a gesture, so it's still one tap to the camera). Once per event per day; only when someone is actually kept away (no audience → no ask). Present = assigned driver (base + split-leg assignments, ghosts excluded) + every passenger-bound member via the My Day four-way binding — adults with passenger profiles count.
- **Prompt worthiness (`presence.prompt_worthiness`, v2.58.0)** — no blind nudge on every event: (1) `PRIVATE_KEYWORDS` hard-block (appointment/doctor/infusion/funeral/…) — medical/solemn events NEVER prompt; (2) status suppression — an event matching any StatusProtocol keyword, or one where the affected member of an active status is present, is owned by the inversion below, never the outward ask; (3) `MOMENT_KEYWORDS` allowlist (games/meets/recitals/concerts/parties + common kid sports & arts) — only these prompt; everything else stays organic (the thread still accepts moments, Chauffeur just doesn't ask). Extend the lists in `presence.py`.
- **The thinking-of-you INVERSION (`presence.run_thinking_of_you_prompts`, v2.58.0)** — the chemo example runs the other way: on a `cover`/`help` status day, everyone EXCEPT the affected member (helpers excluded) gets "💙 Chemo Day — Mom today. Send a little something to let them know you're thinking of them", deeplinked into that member's own DM with the affected member, camera armed. Once per (instance, date, member); after 9am; kids gated by quiet hours (skip to a later sweep the same day, never lost); `give_space` days generate nothing (the family said space) and `clear_deck` isn't absence.
- **Access ≠ push**: the event channel stays household-wide-minus-helpers (access family-wide, thread anchored to the event); the PUSH for a moment routes ONLY to kept-away adults (`presence.moment_push_audience` in `_fanout_message_notifications`) with 📸 framing — present members suppressed (never ping the parent standing next to the sender), kids never pinged (moments ride their existing surfaces). Plain TEXT in an event channel keeps the normal household fan-out — differentiation is moment-only. Cache-miss (old thread) falls back to all non-helper adults.
- **Attachments live — photos AND video** ("Photos of sports does nothing. Videos are the thing." — family, 2026-08-04). **Photos are media-store FILES (v2.62.0)**: the PWA downscales client-side (~2048px JPEG q0.85) and posts a data URL, which `storage.save_photo_data_url` writes to `data/media/` — the attachment is `{kind:'photo', url:'/api/media/{id}', mime, w, h}`. They used to be stored base64-INLINE on the message, which bloated the DB and dragged megabytes through every message scan; that (not disk space) was what forced the old hard 1280px/1 MB squeeze, so the wire cap is now 16 M chars and the renditions are bigger. Legacy inline photos still render everywhere, and a one-time migration (`migrate_inline_photos_v2620`) files them away byte-for-byte (no re-encode). **Disk guard (v2.68.4) — the real limit is /data, not the cap.** Uploads and transcodes work in `media_scratch_dir()` on the ADD-ON's volume even when media is stored on a share, so a 2 GB clip needs 2 GB on `/data` — which Home Assistant shares, and running it out takes HA down rather than merely failing an upload. `init` refuses with **507** unless `free > size*1.15 + 4 GB reserve`, naming the free space; stale parts are swept after **2 h** (was 24 — at 2 GB a few failed retries fill a small volume long before a daily sweep) and again on every completion; ffmpeg runs at `nice(10)` because a 4K decode takes every core on the box also running HA, and a pegged CPU reads to the supervisor as an unresponsive add-on. `/api/debug/media` reports `scratch_dir`, `scratch_free_gb`, `scratch_reserve_gb` and `scratch_in_use_bytes` — the numbers to check first if HA misbehaves during an upload. **Concurrency + local-first transcode (v2.68.2/.3)**: uploads run **2 at a time** client-side with the rest showing "Queued…" (everything shares one link to the box, so firing five at once divides the same pipe five ways and the set finishes no sooner); the raw upload stays in LOCAL scratch and only the finished clip + poster cross the media root (it used to make three SMB trips for a file about to be deleted), with `media_read_path` checking scratch LAST so a just-sent moment still serves its `.orig` — deliberately not a media root, which the layout migration would walk; chunk writes go through `asyncio.to_thread` (a sync `f.write` in an `async def` blocks every other request, serializing concurrent uploads and stalling the SSE stream); transcodes hold `_TRANSCODE_GATE` (1, held only around ffmpeg so a queued clip does not burn its timeout budget) and posters `_POSTER_GATE` (2) — three moments landing together otherwise launched three ffmpeg processes each taking every core on the box serving the uploads still in flight. The uploading bubble extracts its own frame when none was passed (Send pressed before the staged extraction finished, or a Retry), swapping the `<video>` for an `<img>` so it is never a black rectangle for the length of an upload. **Send-then-upload with an in-thread progress ring (v2.68.0)**: picking a video STAGES it (nothing leaves the phone); pressing Send drops an optimistic bubble into the thread immediately — the local `URL.createObjectURL` preview under a dark scrim with an SVG arc sweeping 0→360° and a percentage — and the transfer runs behind it, so the composer is usable again straight away and a 2 GB clip never blocks typing a caption. `sendWithUpload` is deliberately NOT awaited by the submit handler. On success the bubble is dropped and `refreshThread` renders the real message (only if you are still in that channel; otherwise just the strip refreshes). On failure the bubble KEEPS the File and offers ↻ Retry, so a failed send costs one tap instead of finding the clip in the camera roll again. `renderThread` re-appends `uploadingBubbles` after every render — it rebuilds the list wholesale from the server, so an SSE tick mid-upload would otherwise make the clip you are watching upload vanish. **Resumable upload + 2 GB cap (v2.67.0)**: `POST /api/moments/upload/init {size, mime}` reserves an upload and validates the size BEFORE a byte moves (too big costs one round trip, not a full transfer that fails at the end); `PUT /api/moments/upload/{id}?offset=` appends a 5 MB chunk and a MISMATCHED offset returns **409 carrying the server's true `received`**, so a client that lost track resyncs in one round trip instead of restarting; `GET /api/moments/upload/{id}` is the resume point; `POST .../complete` hands the assembled file to `finalize_media_upload` and refuses a short file rather than storing a truncated clip. The client retries each chunk with backoff and re-reads the server's offset between attempts — a few seconds of bad signal at a game no longer costs minutes of 4K60 upload. Abandoned parts are swept after 24 h. Cap raised 500 MB → **2 GB** now that `media_root` can point at real storage and the transfer is resumable (the old cap bounded a single-shot upload onto the add-on's own volume; both halves are gone), and the ffmpeg budget scales with input size (`min(3600, max(600, mb*3))`) — a flat 600 s silently failed long 4K clips, and a transcode timeout KEEPS THE ORIGINAL, so the file that most needed shrinking was the one stored at full size. **The pre-upload wait on iOS is not ours**: picking a video that lives in iCloud makes the OS download and often transcode it before the `change` event fires and before `file.size` exists, so no client check can pre-empt it — the generous cap exists so that wait rarely ends in a rejection. **Video (v2.58.0, transcode pipeline v2.59.0)**: clips upload as FILES to the family's box — legacy one-shot `POST /api/moments/upload` still works (STREAMED to disk in 1 MB chunks — never whole in RAM; mp4/webm/mov/m4v), attachment `{kind:'video', url:'/api/media/{id}', mime}` validated against the store, served by `GET /api/media/{id}` with EXPLICIT byte-range support (iOS Safari refuses rangeless video; Starlette's FileResponse can't be trusted for it across versions). **Every clip transcodes in the background to H.264 720p mp4** (`storage._transcode_media`; Dockerfile ships ffmpeg) — phones record HEVC .mov that Chrome-based wall panels cannot decode, and 720p is ~10x smaller. The upload returns the FINAL .mp4 id immediately; the original serves via the `.orig` fallback until the atomic swap lands on the same id/URL; a failed transcode stores the original as-is (the moment is never lost); no-ffmpeg dev envs store-as-is under the native extension. One-time migration (`migrate_moment_clips_v2590`) retranscodes pre-pipeline clips and repoints their attachments. **Poster frames (v2.62.0)**: `storage.generate_poster` extracts a still (`{stem}.jpg`, seek 1 s with a frame-0 fallback) after every transcode AND on demand when a poster is requested but missing — so old clips heal themselves. Every TILE across the app (rail, gallery, PWA strip) is now a plain `<img>` of that poster plus an SVG play badge: `<video preload=metadata>` painted a black box and made a grid of clips stream video just to draw thumbnails. A poster miss NEVER falls through to the `.orig` video bytes. **Two guards against empty tiles (v2.62.1)**: `poster_url` is only advertised when the poster exists OR ffmpeg is installed to make it (`storage.poster_available`) — otherwise the payload points at the clip itself; and every thumbnail carries `data-fallback` + `onerror="momentThumbFallback(this)"`, which swaps a failed `<img>` for a `<video>`. Without both, a box whose add-on was restarted rather than REBUILT (no ffmpeg) renders every clip tile blank. **`GET /api/debug/media`** reports `ffmpeg_ok`, clip/poster counts, clips missing posters, and photos still stored inline — the first thing to check when thumbnails misbehave. All `<video>` src URLs are RELATIVE (like api fetches) so HA ingress paths work. Retention: a pruned moment deletes its clip AND any transcode working files (`storage._delete_media_for_messages`). One composer input accepts both (`accept="image/*,video/*"`); threads render `<video controls playsinline>`; caption rides in `body`. The design's reference-and-render fork was revised at build via its own escape clause (no external store to reference; share-link kills one-tap).
- **Reactions** (first-class primitive, chat-wide): `ChatMessage.reactions` `{emoji: [member_id]}`, toggled via `POST /api/messages/{id}/react` (≤8-char emoji, member-validated, empty lists pruned). Quick-react row (👍 ❤️ 😂 👏 🎉 💪) + toggle pills under every bubble. Reactions NEVER push — the sender at the game is fire-and-forget; they accumulate silently over the SSE ring only. Threaded replies deliberately not built (v1).
- **In-app moment pop (v2.63.0)** — a moment landing while the PWA is OPEN gets the kiosk's warmth instead of a badge bump: `send_message` attaches a small preview (`presence.moment_stream_meta` — id, kind, media/poster URLs, caption, sender, event title; URLs only, never bytes) to the message SSE event, and the client pops the same full-screen overlay the strip/thread use, with an "Open chat →" button. Guards: never your own moment, only when `visibilityState === 'visible'` (a backgrounded app already got the push), never stacked over an open overlay, and silent if you're already viewing that thread. EVENT channels only — a DM moment (thinking-of-you) never pops. Deliberately does NOT resolve who was at the event (that needs the cached schedule on the send path); the sender guard is the exclusion that matters, and full kept-away routing still governs the background PUSH.
- **HA event bus hook (v2.58.1)**: every EVENT-channel moment fires a deliberately payload-free `chauffeur_moment` event on the HA bus (`ha_api.fire_event`, POST /api/events/{type}) — automations react (browser_mod popup, cast, chime) and nothing sensitive rides the bus; the popup shows Chauffeur's own rendering via the standalone **`GET /moment`** page (hearth-style, zero dependencies, iframe-ready, newest moment by default / `?message_id=` pins one). Private DM moments (thinking-of-you) NEVER fire the event — nothing private pops on a shared panel. Example automation: trigger `event_type: chauffeur_moment` → `browser_mod.popup` with an iframe card pointing at `{chauffeur}/moment`, timeout ~30s.
- **Moments surfaces**: `GET /api/presence/moments?hours&limit` (`presence.recent_moments` — event-channel moments only, sender/event/channel_id enriched, DMs never leak; caps 720 h / 200 for the gallery, small defaults for the hearth). The PWA Messages tab shows a 📸 **Moments strip** (recent thumbnails; play badge for clips); event channels list with a 📸 avatar. **Tapping a strip thumbnail opens the thread AND the moment full-screen** (v2.62.2) — `openChannel(id, obj, focusMessageId)` scrolls that bubble into view and calls `openMomentById`, so dismissing the lightbox leaves you in the conversation around it. The lightbox handles photos AND clips (autoplay + controls, poster-backed; ✕ / backdrop dismiss, since tapping video would otherwise fight the controls) and resolves a moment from the loaded thread, falling back to the strip's own row when the moment is older than the thread's 100-message window.
- **Where the archive LIVES — media root + sharding (v2.66.0)**. Media defaulted beside the database on `/data`, which is the wrong disk for a family shooting 4K60 at two games a week: `/data` is a VM's virtual disk, and growing it means touching the VM (HAOS's "move data disk" is all-or-nothing and cannot relocate media alone). New `media_root` add-on option points the archive elsewhere; `config.yaml` now maps `media:rw` + `share:rw`, so an HA network-storage mount (Settings → System → Storage; lands under `/media/<name>` or `/share/<name>`) puts the bytes on a NAS or the host's big drive **without resizing the VM or moving the installation**. **Changing `media_root` never orphans the archive (v2.66.2)** — every root the media has lived in is persisted (`media_roots_seen`) and stays in `_media_roots()` forever. Without that, RENAMING a share dropped the old path out of the lookup, so the whole back catalogue stopped resolving *and* stopped being seen by the migration, while new uploads kept working — the archive appears to vanish with no error. `storage.adopt_media_root` + `POST /api/debug/media/adopt {path}` recover a root that changed before history was recorded: it registers the path (files resolve immediately) then relocates them. The migration only ever moves files matching `^[a-f0-9]{32}(\.tmp)?\.(mp4|webm|mov|m4v|jpg|png|webp|orig)$` — a media root can be a share with other content, and relocating everything found would rearrange somebody's documents into `ab/cd` buckets on their NAS. **The root is NEVER created (v2.66.1)** — a media root is a MOUNT, and `os.makedirs`-ing it turns a typo'd mount name (HA mount `LOCAL_STOARGE` vs `media_root: /share/LOCAL_STORAGE`) into a plain directory beside the real mount that then passes every other check, quietly writing the archive onto the exact volume the option exists to escape, with no error anywhere. One level is created only when the PARENT is itself a mount (`_is_separate_filesystem`, `st_dev` vs the database's), which is the only legitimate not-yet-there case. A root on the same filesystem as the database still works but logs a WARNING and reports `media_root_is_mount: false`. The layout migration ALWAYS logs, including no-ops — gating it on moved-or-errors made "found nothing to do" and "never ran" identical from the log. `POST /api/debug/media/migrate` re-runs it without a restart, and `/api/debug/media` reports `files_by_root` with a flat-vs-sharded split so "are my files actually on the share" is answerable in one request. A root that is missing or unwritable is REFUSED, not adopted — it logs and stays on the legacy location where the older files actually are, rather than writing into a path that vanishes when the mount reappears (`GET /api/debug/media` reports `media_root_configured` vs `media_root_active` so a silently-refused root is diagnosable). **Layout is hash-sharded** `ab/cd/{id}` from the id's OWN leading hex (`storage._shard`) — not by date, deliberately: the id is already in every stored `attachment.url`, so a file's bucket is derivable and **nothing in the database is rewritten**. ~27k files (15 seasons) land across 256 buckets instead of one flat directory. Siblings (`.orig`/`.jpg`/`.tmp.mp4`) share the stem and therefore the bucket. Three helpers replace every direct join: `media_write_path` (active root, sharded, parents made), `media_read_path` (finds a file sharded OR flat, active root OR legacy — the legacy lookup stays FOREVER, being two `isfile` calls on a miss, and is what makes relocating onto a network mount safe to interrupt), and `media_scratch_dir` (always beside the DATABASE, never the media root). **ffmpeg and uploads write to local scratch and move the finished file across** (`media_move_into_place`, `os.replace` with a cross-device fallback) — a multi-minute encode straight onto CIFS is slow and fails badly, and a 500 MB upload should not hold a mount open for the whole transfer. `migrate_media_layout` (run last in `run_all_migrations`, NOT app-state gated since the root is a setting that can change again) relocates in the background; nothing 404s while it walks, and an interrupted run just leaves the archive partly moved. Consequence to be deliberate about: media outside `/data` is no longer in HA add-on backups — the DATABASE still is, and the database holds the curation (event grouping, captions, reactions, who posted) that phones cannot restore.
- **Undoing a misfire — delete + edit (v2.64.0)**. `DELETE /api/messages/{id}` (body `{member_id}`) removes a message OUTRIGHT — no tombstone, deliberately: this exists so a wrong photo can be taken back, and "X deleted a photo" only advertises the thing you were undoing. Permission (`main._may_delete_message`): your own always; plus `role='parent'` for anything in a SHARED channel (`event`/`group`). **`parent` is not `adult`** — a grandparent or a sitter is an adult with no moderation power — and DMs stay sender-only so nobody reaches into a private thread. `storage.delete_chat_message` calls `_delete_media_for_messages` before dropping the row: moments are exempt from the retention cap, so nothing else would EVER collect the clip/poster/transcode working files and the row alone would leak them forever. `PATCH /api/messages/{id}` (body `{member_id, body}`) is deliberately NARROWER — **sender only**, because a parent clearing a shared channel is moderation but a parent rewriting a kid's words puts words in their mouth. It stamps `ChatMessage.edited_ts` (surfaces render "· edited"), never touches the attachment (swapping media is delete-and-repost), and refuses a blank body unless an attachment still carries the message (otherwise it is a delete in disguise; clearing a moment's caption is fine). Both push `_push_message_event` so open threads refresh over SSE. **Best-effort by nature**: a push already on a lock screen cannot be recalled and a kiosk mid-overlay keeps the bytes it loaded; the hearth rail drops it on its 60 s poll. PWA surfaces a `⋯` menu (Edit/Delete) on messages the viewer may act on and a Delete button inside the moment lightbox; the kiosk gallery stays read-only (no signed-in identity — the reaction-pill precedent). `presence._moment_row` now carries `sender_member_id` so the strip's lightbox can decide without re-fetching. The PWA also gained its OWN `promptConfirm`/`promptInput` (same names/contract as `components/control_center.html`, which app.html does not include).
- **The Moments gallery (`GET /moments`, v2.60.0; event-grouped + endless v2.61.0)** — the wall-panel surface for looking BACK, and a first-class nav tab (desktop + mobile menu + `?tabs=moments` slug) alongside Schedule/Calendar/Map. **Two levels**: a card per EVENT (cover = newest moment, count badge, who posted, when) → tap for that event's own grid → tap a tile for the full-screen lightbox. **Getting back up a level (v2.63.1)** is a STICKY `#event-back` bar deliberately outside `#moments-header`, so neither `?title=none` (which hides that header) nor scrolling a long event grid can strand you one level deep; it carries the event title only when the header isn't there to show it. Both levels PAGE (24 events / 30 moments) via `GET /api/presence/moment-events` and `GET /api/presence/event-moments?channel_id=`, loaded by an IntersectionObserver on scroll, and every thumbnail loads lazily **by URL** (`GET /api/moments/{message_id}/media` — decodes an inline photo to real image bytes, redirects a clip to the media store) so opening the gallery costs the same after ten seasons as after one. Read-only reaction pills (a wall panel has no signed-in identity to attribute a tap to — reacting lives in the PWA). ## Errands Scheduling Logic
- **Errands Inbox**: A dynamic management UI allows users to add errands using natural language.
- **Errand Rules Engine & Routing Rules Integration**: Errands intelligently respect global Routing Rules (Event Rules) dynamically. If a driver is marked "Unavailable" or "Avoid" for a specific time window or day, the global errand solver evaluates these constraints against the exact proposed `start_time` of each scheduled gap to accurately prevent assignment. Furthermore, errands support advanced native options (Driver Assignment, Passenger Constraints, Time of Day, Day of Week Restrictions, Buffer & Tolerance, Grouping) configured via the Errand Rules Engine or directly on the Errand.
- **Global Heuristic Errands Solver**: `matcher.py` intelligently places errands into gaps across the entire 7-day schedule, including **intra-event gaps** inside scheduled events (e.g., between a drop-off and pickup). It targets a specific scheduling window based on the errand's `created_at` date and its `recurrence_rule` to prevent over-scheduling. It then finds the single gap across all valid dates that requires the least detour time without violating the master route structure or any Errand Rules constraints.
- **Past Due State**: Errands that exceed their estimated scheduled time without being completed are placed in a `past_due` state. The solver safely ignores them so they stop auto-scheduling and wait for manual intervention.
- **Recurrence**: Errands can be set to recur Daily, Weekly, or Monthly upon completion. When marked complete, a new pending errand is generated automatically, which will reset the `created_at` anchor date, starting the cycle anew.
- **AI Agent POI / Category Search**: The AI agent is capable of looking up Points of Interest (POIs) such as gas stations, coffee shops, and groceries, and routing them based on the proximity of a driver's existing route stops. It leverages Mapbox's Category Search and Forward API with independent rate limiting.
- **Place search relevance** (`maps.search_places`): the source of every POI/accommodation address, coords, and OSM extratags (wikidata, opening_hours, website, phone, cuisine). **Mapbox Search Box is authoritative** for name/address/coords — it is proximity-biased and won't return the vacation-rental listings that OSM free-text search surfaces for landmark queries (an Airbnb whose name embeds "…near Disney, Magic Kingdom…" must never outrank the actual park). Nominatim (OpenStreetMap) runs alongside purely to supply extratags, which are backfilled onto the matching Mapbox result by coordinate proximity (≤300 m — same place, so a landmark keeps its real wikidata/hours while shedding the junk). Nominatim results are also junk-filtered (`_looks_like_rental_listing`: rental OSM types apartment/chalet/guest_house/hostel/caravan, names >70 chars, or ≥2 listing keywords like "2BR", "free wifi", "gated community") so the Nominatim-only fallback (Mapbox disabled/unavailable) stays clean too. Real hotels (`type=hotel`) are NOT filtered, so accommodation search is unaffected.
- **Scheduling ownership (CRITICAL)**: the trip **itinerary's** scheduled state (`pois[].is_scheduled/scheduled_start/scheduled_end/event_id`) is owned SOLELY by the trip page's CP-SAT scheduler (`trip_scheduler.schedule_pois_bulk`), triggered explicitly by the user (Schedule / Rebuild). The daily **family** solver must NEVER reset or write back trip-POI scheduled state — it used to reset every trip POI to unscheduled on each live schedule and reschedule them via the errand matcher, which clobbered the user's itinerary (and, once calendar-backed reservations existed, dropped them) on every background refresh / page revisit. The daily solver's bounded-errand placement of trip POIs is now display-only (family dashboard, in-memory), never persisted. Calendar-backed reservations are re-anchored to their real event time by the get_trip_api sync if anything wipes them.
- **Trip POIs as Bounded Errands**: Trip Points of Interest (POIs) act as specialized dynamic errands. They are automatically constrained strictly to the date range of the Trip event and can enforce Day of Week Restrictions to schedule around crowds or closures. The solver schedules them opportunistically within the trip's time window, correctly adapting and localizing logic to the trip's destination timezone. It uses intelligent slot-scoring to prefer geographically close POIs on the same day (using Mapbox travel times), and applies strict Meal Block constraints for `food` POIs (Max 1 Lunch from 11-14, Max 1 Dinner from 17-21 per day), while intelligently treating desserts/sweets as flexible, highly-scored adjacent events. The bulk scheduler uses **hard day-of-week filtering** when clustering regular POIs to background anchors: if a regular POI has `valid_days_of_week` set, it will never be assigned to a background anchor whose `valid_days_of_week` doesn't overlap, preventing mismatches when multiple background POIs exist at the same location on different days (e.g. EPCOT Day 1 vs Day 3).
- **Live Pricing Integration**: The UI can fetch real-time "Live Prices" for flights and accommodations within a trip using the SerpApi via the `/api/trip/{trip_id}/live_pricing` endpoint. These fetched prices are marked with `is_live_price = True` to render a "Live" badge and provide accurate trip budgeting without repeatedly depleting free-tier API quotas. If the user hits their 250 requests/month SerpApi limit, the system gracefully falls back to Deep Links to Google Flights and Hotels.

## How this household eats (Meals arc M11, v2.84.0 — services/meals.py, models.schemas.MealRule)
- **The rules engine, and why the earlier refusal was wrong.** M9 shipped with "if three or more conditional wants accumulate, that is the signal to generalise". The family then named four in one go — meat about once a week, takeout occasionally, three kinds of beans cooked in big batches and worked through 2–3 days at a time, beans as the everyday protein. None are properties of a dish, so `always_with`/`only_with` cannot express any of them. They are **rhythms**, and they are what makes a plan feel like this family's.
- **Two kinds only**, both drawn from what was actually said, following the solver's `Rule`/`ErrandRule` precedent (named, listable, individually switchable): `frequency_cap` (at most N of a matched set per M days) and `batch_cycle` (one member is the open pot; it keeps coming for `dwell_days`, then the group advances to whoever has gone longest without). Not a general predicate language.
- **A tag is nearly always ALMOST right (v2.85.0)**: the bean rotation is black/red/pinto, but the `beans` tag drags in baked beans, which are not part of that cycle at all. `exclude_dish_ids` subtracts, and **an exclusion beats every other clause** — including an explicit dish list, because "not this one" is never conditional. Without it the only escape was enumerating every dish by hand.
- **One picker, multi-select EVERYWHERE (v2.85.1, completed v2.85.2)**: the rules form inlined two long chip lists and became a wall of controls. Both now open the **same dish dialog** used everywhere else on the page, modelled on the trip page's *Link Existing Event*: picking lifts a dish OUT of the list into a pill at the top, so chosen and remaining are never the same visual thing; Done commits. v2.85.1 left "add a dish to a night" in a single mode that closed on the first click — so the normal case, a main **and** a side, cost two open/pick/reload rounds. There is now no mode at all: `pickerFor` — `{kind:'night'|'rule'|'pairing', …}` — says what is being answered and only the commit differs. The night's commit POSTs each chosen dish then reloads the week **once**, and the list hides the union of what is already on the night and what is sitting in a pill.
- **`beans -baked` works (v2.85.1)**: a leading minus in the tag field subtracts by word, matching name, short name or tag. Resolved to real dish ids **at save**, never stored as syntax, so the rule means the same thing to the server, the agent and anyone reading it later. Deliberately not the advertised path — the "…except these" picker is — but it is three lines and the people who reach for it are right that it should work.
- **Dishes are PICKED, never typed (v2.85.0)**: the first form had one "applies to" box that guessed whether a word was a tag or a dish name, compared only against the FULL name (so a dish whose display name differed never matched), and **silently fell back to a tag when it missed** — so naming three beans produced three meaningless tags and a rule that governed nobody, reported only as "matches no dish yet". The form now has a dish chip list, a separate clearly-labelled tag field, an "…except these" row that appears only when a tag or takeout is doing the selecting, and a **live preview** computing what the rule would catch before it is saved.
- **Selectors are ANDed, empty clauses ignored, and an entirely empty selector matches NOTHING** — a half-written rule must not become a household-wide ban. `sources=['ordered']` is structural and needs no tagging, which matters because *"meat" is not a field* while takeout effectively is. A rule matching zero dishes is reported rather than silently governing nobody.
- **The bug that only simulation caught**: the first `batch_cycle` compared *time since last served* against the dwell. A batch is eaten EVERY day, so that gap is permanently one day and the window slid forever — a 14-day plan sat on black beans for all 14. The dwell must count **servings**, so `compose_week` now threads a `runs` counter beside the M6 `served` overlay. A skipped night (takeout) deliberately does not zero it — one takeout evening does not empty the pot — and a fresh pot starts a fresh count, or the incoming bean inherits the outgoing one's run and rotates straight back out.
- **Caps are enforced everywhere dishes enter a plate**, including M9 pairings — otherwise a paired side smuggles meat past the cap.
- Surfaces: **"How we eat" panel** on Shopping & Meals (v2.84.1 — M11 shipped with an API and agent tools and NO UI, so there was nowhere to see or add a rule). Each rule shows its plain-English description, what it currently **covers**, plus **edit**, pause/resume and delete (edit added v2.84.2 — before it, changing "once a week" to "twice" meant deleting the rule and rebuilding it from memory); a rule matching nothing is bordered amber and says it is not doing anything, because that is the silent failure this whole surface exists to prevent. The add form switches its questions on the kind — "how often" and "one at a time" ask genuinely different things — and **"applies to" is one field**: the family types a word and whether it resolves as a tag or a dish name is the app's problem, not theirs. **One PATCH carries both** a one-field pause and a whole-rule edit, normalised exactly as creation is — an edited rule behaving differently from an identical created one is the divergence that surfaces months later as "it works if I delete it and add it again". "Applies to" round-trips back OUT of a saved rule (the list endpoint returns `dish_ids`/`tags`/`sources` for that reason), or editing would silently drop what the rule applied to and turn a working rule into one governing nobody. Also `GET`/`POST`/`PATCH`/`DELETE /api/meals/rules`, and `set_meal_rule` / `get_meal_rules` in both agent stacks.
- *Known limit, stated rather than hidden*: a dish row remembers only its most recent serving, so history granularity is one data point. Caps are exact for the composed horizon and for "once per window" (what families actually say); "twice a week" cannot see a third helping from last Tuesday.

## A night that is spoken for (Meals arc M10, v2.83.0 — services/meals.py)
- **Most of this already existed**: M6's hold-still rule pins any edited plate and `prune_plates` only ever drops PAST dates, so a dinner set weeks out already survived. Three things were genuinely missing.
- **`locked` is not `edited`.** Editing is "we swapped a side" and a bulk repropose is entitled to sweep it away; locking is "this is Mom's birthday dinner" and must survive one. `reset_plate` now refuses a locked night unless `force=True` — the per-day Reset passes it (a deliberate act on that night), the bulk repropose does not and skips locked days entirely.
- **`_persist_plate` rebuilds the record from scratch**, so the lock and its note are explicitly carried forward. Without that, an ordinary edit — or the week approval, which re-persists every night — would have silently unlocked the birthday and dropped its reason.
- **`note` makes an empty night a plan.** A locked plate with no dishes and "Grandma is bringing dinner" cooks nothing, shops for nothing, and no longer reads as a night nobody got round to.
- **Reaching the date**: the week strip only covers up to the next shop, and the API always accepted any date — there was simply no way to reach one. A date field plans a specific night and drops straight into the dish picker.
- Surfaces: `POST /api/meals/plate/lock`, `force` on the reset; lock toggle + note per day on the strip; `plan_specific_dinner` / `unlock_dinner` in both agent stacks ("steak on Monday, it's Mom's birthday").

## Dishes that come as a set (Meals arc M9, v2.82.0 — services/meals.py)
- **Asked from real use**: brisket (takeout) arrived with beans and fries (home) once — was that a relationship or luck? **Measured: luck.** Over a fortnight the trio survived **0 of 3** brisket nights. M5 handles coherence as a *soft tag affinity* (+1.5 when the side shares a tag with the entree) — a preference that drifts, and with no shared tags it was not even in play. With the pairing declared: **3 of 3**.
- **Two DIRECTED relations, not a matrix.** `always_with` on a dish means "when this is chosen, these come too" (brisket → beans, fries); `only_with` is the reverse constraint, "never propose me unless one of these is present" (naan → curry). The asymmetry is the entire design: brisket BRINGS beans while beans stay free to appear beside anything else. A symmetric goes-with grid is O(n²) of upkeep a family will never do — precisely why M5 refused to model coherence at all. This is one statement on one dish, declared only for the handful that need it.
- **Hard filters still win**: a pairing is the family saying these go together, not a licence to put an allergen on the plate — an `always_with` partner that fails `_dish_ok` (allergy, portability on a packed evening) is dropped. Cycles are guarded (brisket↔beans is a thing a family will say). Paired sides **fill** the side slots rather than adding to them: two sides asked for, two delivered.
- Surfaces: `POST`/`DELETE /api/meals/dishes/{id}/pairing`, `pair_dishes` / `unpair_dishes` in both agent stacks ("brisket always comes with beans and fries", "the naan only ever goes with the curry"), **and a hand path since v2.86.0** — M9 shipped agent-only, which is the same gap M11 had: anything the agent can state, the family must be able to state too, or the relationship is invisible to whoever didn't say it out loud. Each row under **Our meals** carries its partners as chips — green `with …`, blue `only with …`, each removable — plus **+ comes with** and **+ only with**, which open the shared dish picker (`pickerFor.kind === 'pairing'`) preloaded with the current partners. The dialog states the direction in a line of hint text, because a picker that doesn't is indistinguishable from the symmetric grid this design refused to build. Commit is `replace: true`, so unpicking a pill and pressing Done removes a partner — otherwise the picker could only ever add.
- **This is not a rules engine, deliberately.** What was described is a PROPERTY of a dish, not a rule: properties are declared once where you notice them and need no evaluation order, whereas rules accumulate precedence and become something to debug. Conditional wants ("no slow-cooker on late nights", "fish only on Fridays") are genuinely rules and cannot be expressed this way — if three or more of those accumulate, that is the signal to generalise, and the solver's `Rule`/`ErrandRule` grammar is the precedent to copy.

## Occasion food and the kitchen as a resource (Occasions arc O0, v2.90.0 — `docs/occasion_design.md`)

- **`Dish.scope` (`everyday` | `occasion`, default `everyday`)**. From the family: the food eaten at holidays and parties is not the food eaten day to day, and keeping turkey in the standing pool so that it exists twice a year pollutes every picker for the other fifty weeks. Enforced in **`_dish_ok`** — the hard-filter gate every composition path already runs through (`pick`, `attach`, the sides loop). **Two fields, not one**, and the overlap case is why: mashed potatoes are everyday AND Thanksgiving, so `scope` carries eligibility while `tags` carries *which* occasion; one field cannot say both. `is_active` is unchanged — retired, not seasonal. Deliberately **not** a `MealRule` kind: rules are *rhythms* ("meat about once a week"), and "turkey is not a Tuesday food" is a property of a dish — routing it through the rule engine would turn a narrow, listable thing into the general predicate language its own docstring refuses to be.
- **Scope gates PROPOSAL, never PRESENCE — the trap this feature dies on.** An occasion dish that is a **leftover** bypasses the filter entirely, riding the bypass `_dish_ok` already had for portability (*"it exists, and it is going in a container either way"*). The days right after Thanksgiving are precisely when the turkey must land on an ordinary plate; a naive filter blocks the dish from the days it exists to cover. Hand-picking is likewise untouched — the plate picker and `set_plate_lock` never come through `_dish_ok`, which is the same eligibility-is-not-selection line the arc draws everywhere.
- **Occasion food is invisible to ordinary rule ACCOUNTING**, not merely given rules of its own: `rule_context` builds its member set from everyday dishes only. A turkey carries a `meat` tag like anything else, so without this it burns the week's "meat about once a week" allowance and the family gets a baffling vegetarian weekend after every holiday — and a `batch_cycle` would advance on a day that had no beans in it. Excluding them from the member set fixes both directions at once: serving one never counts, being one never blocks.
- **The kitchen is now declared, not assumed.** Settings `kitchen_ovens` (1), `kitchen_burners` (4), `kitchen_cooks` (1) — Config → General → **🍳 The kitchen**. `_totals_from_dishes` has always been a two-resource model with the capacities hardcoded (cook=1 → hands-on SUMS; equipment=∞ → unattended takes the MAX), and **both constants invert the moment the family hosts**: more hands are available, and equipment becomes the binding constraint. The defaults reproduce today's arithmetic exactly, which is the reduction property the solve must satisfy when it lands.
- **`Dish.equipment` (`none`|`oven`|`burner`), `Dish.oven_temp_f`, `Dish.serves`.** Temperature is the **sharing key**, not decoration: two dishes fit one oven only at the same temperature, and space is the constraint people think of while temperature is the one that actually blocks. `oven_temp_f` is cleared server-side whenever `equipment` moves off the oven, since `None` means "not sent" in `PATCH /api/meals/dishes/{id}` and a stale sharing key would otherwise outlive the oven that justified it.
- **The model fills all of it** (`_DISH_SYSTEM_V5` + `_clean_dish`), same bargain as every other dish field — the human supplies a name or the repertoire never reaches fifteen entries. The prompt is told to choose `everyday` when in doubt, so the pool degrades toward *visible* rather than *missing*.
- **Hand path** (Shopping & Meals → Our meals): a per-dish **occasion only** toggle on each row beside the pairing buttons, and a **`N occasion dishes — Show/Hide`** header. The count is stated in the toggle on purpose: a filter that silently swallows rows is how a family concludes the app lost their turkey. The empty-list message distinguishes "nothing yet" from "everything here is occasion-only". `dishBlurb` now names the equipment and its temperature.
- Tests: `tests/test_meals.py` — occasion dishes absent from a composed fortnight, the leftover bypass, hand-picked-is-never-filtered, rule accounting in both directions, and the parser defaults.
- **Agent (both stacks): `set_dish_scope`** — "turkey is only for holidays", "we only make deviled eggs for parties", `occasion_only=false` to bring it back. The reply deliberately promises PROPOSAL rather than availability ("I won't suggest it on an ordinary night, but it's still there to pick, and leftovers of it still count") — "I've removed the turkey" is neither what happened nor what anyone wants to hear.

## The kitchen scheduler (Occasions arc O0, v2.91.0 — `services/kitchen.py`)

- **`kitchen.totals(dishes, settings, cooks=None)` is now the single source of the three timing numbers** every meals surface reads; `compose()` / `plate_totals()` / `compose_meal()` delegate to it and thread `settings` down (the fit filter runs once per repertoire entry per day — a fortnight is several hundred calls and the capacities are identical for all of them). `compose` also returns `oven_conflicts` and `cooks`, both carried out through `/api/meals/plate` and the week payload.
- **Reduction is the contract, and it is a test, not a hope**: one cook, one oven, no temperature clash → byte-identical to the sum/max the app shipped with. The pre-existing `scenario_timing_aggregates_hands_on_but_not_the_oven` passes unchanged on the new path, which is the assertion that matters. Where the two disagree — two oven dishes at different temperatures — the old arithmetic was wrong in the optimistic direction.
- **Analytic, not CP-SAT — a deliberate departure from the design brief.** The brief reached for `AddCumulative`, which remains right for the run-sheet (real clock times, on demand, one hosting plate). It is wrong here: `compose` runs once per composed day, so a 14-day week plan would pay for fourteen solves on every render. These spans are parallel-machine makespans over ~10 jobs with closed forms, and closed forms are exact, instant and testable.
- **The three spans.** `prep_ahead_mins` / `finish_mins` are `_makespan(jobs, cooks)` — the classic pair of lower bounds (no machine beats the longest job; no schedule beats the work divided evenly), which at `cooks == 1` is the plain sum. `unattended_mins` is `equipment_span` = the longer of the oven span and the burner span (they run concurrently), floored by any slow-cooker dish on neither.
- **Ovens: temperature is the sharing key, rack space is deliberately unmodelled.** Dishes at one temperature share an oven freely; each distinct temperature is an indivisible block, and the blocks queue for however many ovens exist. A dish with no stated temperature is its own block — an unknown temperature is not evidence of a match, which is also what keeps every pre-existing dish (no `equipment`, no temp) behaving exactly as before.
- **Burners hold their ring through the hands-on finish**, not just the simmer: a stir-fry is 25 minutes of somebody standing at the stove and the ring is occupied throughout. Modelling only `unattended_mins` would mean burners were never contended for precisely the dishes that contend for them.
- **An already-made dish leaves the model entirely** rather than contributing zero — a reheated casserole must not book the oven it does not need. `compose` filters leftovers out before calling `kitchen`.
- **Conflicts are named, not just priced in.** `oven_conflicts` lists each temperature block (longest first) with the dishes in it, surfaced on the Tonight plate as *"One oven, 2 temperatures — roast beef at 325°, apple pie at 425°. They have to take turns, which is already in the time above."* A total that quietly grew explains nothing, and "these two want the oven at different temperatures" is the most useful sentence this model can say.
- Settings: `kitchen_ovens` / `kitchen_burners` / `kitchen_cooks` (Config → General → 🍳 The kitchen). The `cooks` argument overrides the household default per call, which is how a hosting plate will raise it without changing how the family cooks on a Tuesday.
- Tests: `tests/test_meals.py` — reduction, legacy dishes unchanged, two temperatures queueing (and a second oven dissolving it), a second pair of hands halving the finish, burner contention, and leftovers releasing the oven.

## Hosting a night (Occasions arc O0, v2.92.0)

- **`Plate.serving_for` and `Plate.cooks`.** `serving_for` is the WHOLE headcount, not the extra guests — "we're having twelve people" is what somebody says, and making them subtract their own family first is arithmetic the app should be doing. `cooks` is hands available that night; absent means the household `kitchen_cooks`, because someone offering to help on Saturday is not a statement about how the family cooks on a Tuesday.
- **Hands-on scales; the oven does not** (`kitchen.scaled`). Four times the potatoes is four times the peeling and not four times the roasting — heat does not work that way, and a tray that genuinely needs materially longer is a *bigger thing* rather than more of the same. That is the line M4 already drew when it made roasted and mashed potatoes separate dishes: a twenty-pound turkey is its own entry with its own times, not a chicken with a multiplier. **Scaling down is refused outright** (`max(1.0, …)`): cooking for fewer people than a dish serves does not make it faster, and it is the one direction that is pure fiction.
- **The factor is per DISH**, off each dish's own `serves` — a main that serves four and a salad that serves eight are not stretched by the same amount. Deliberately unmodelled: that four trays may not fit one oven. Rack space is unmodelled throughout `kitchen.py`, and inventing a batch count here would be the single place it was guessed.
- **`set_plate_hosting` does NOT set `edited`.** Saying how many are coming is a fact about the evening, not a decision about what to eat; pinning the night on the strength of it would freeze whatever happened to be proposed at the moment somebody answered the door question. Both `_persist_plate` and `set_plate_lock` now carry `serving_for`/`cooks` forward — the identical rebuild-from-scratch trap that once silently unlocked Mom's birthday would otherwise reset a twelve-person night to a family of four on the next side-swap.
- **`plate_totals` reads the stored plate** when the caller does not override, so a night marked "twelve people, two cooking" says so on Tonight, on the week strip, and anywhere else that renders it — not only where it was typed.
- Surfaces: `POST /api/meals/plate/hosting` (`serving_for: 0` clears; `None` means "leave alone" — two different statements, so they cannot share a representation), a **👥 Cooking for…** button on the Tonight plate that fills amber with the headcount once set, and `set_hosting` in both agent stacks. The agent answers with the CONSEQUENCE, never a confirmation — how long the evening now takes, plus the oven-clash warning if the plate has one, because that is the reason anybody said it out loud.
- Tests: scaling multiplies hands not oven, per-dish `serves`, hosting surviving an edit and a lock, reaching the week strip, and the agent reply naming the cost.

## The run sheet (Occasions arc O0 — COMPLETE, v2.93.0 — `kitchen.run_sheet`)

- **"Start at 11:00 to eat at 16:00", then clock times per dish.** This is where CP-SAT belongs and `totals()` is where it does not: the run sheet is computed on demand for ONE plate, while totals runs once per composed day (a fortnight would have paid for fourteen solves per render).
- **The objective maximises the first task's start, not a minimised makespan.** "When do I have to begin?" is the question a run sheet exists to answer, so the number that falls out should be that one. A **second weighted term maximises every finish start**, and it is not decoration: the first version optimised only the earliest start and cheerfully scheduled the gravy five hours before dinner — technically before serving, completely useless. Pushing each task as late as its resources allow is what a cook actually does. `begin` still dominates (weight `len(dishes) * horizon + 1`).
- **The model**: per dish, `prep → unattended → finish` chained with `<=` rather than equality (a dish may legitimately wait for a free ring, and pretending otherwise makes the sheet lie); `AddCumulative` for cooks over prep+finish and for burners over the held ring; ovens by pairwise thermal exclusion under an explicit oven assignment (`AddExactlyOne` per dish), one temperature sharing freely, an unknown temperature never sharing. 3s cap, 4 workers.
- **The behaviour that proves it**: a 4-hour turkey at 325° and potatoes at 425° in ONE oven produce "turkey in at 11:10, potatoes in at 15:10, turkey carved at 15:35" — the bird rests on the counter while the potatoes take the oven, which is the actual move and the thing sum/max could never have said.
- **Fails open, never blank**: no ortools, or a solver that gives up, degrades to `_sequential_sheet` (one dish after another — pessimistic but never wrong) and the payload carries `exact: false`, which the UI states plainly. A sheet that silently degrades is worse than one that admits it.
- **Serve time comes from the family's own sitting** — the EARLIEST one on a split evening, because the food has to be ready when the first person eats; cooking to the last one is how the kids in the car get nothing. Falls back to the start of the dinner window, never to a guess.
- **Shown, never pushed — and this reverses the design brief.** The brief planned to emit these as `PrepStep`s. Two reasons it was dropped: `PrepStep` models work OUTSIDE the cook window, per dish, opt-in, and it fires reminders — wrong entity for a dated computed schedule inside the window; and the meals arc's taskmaster rule governs absolutely ("start the rice at 3:40, pack two at 4:50" every evening is a stream of orders, and the promise is removing load rather than issuing it). Surfaces are a **🕐 When do I start?** toggle on the Tonight plate, `GET /api/meals/plate/runsheet`, and `get_run_sheet` in both stacks — all pull.
- Tests: counting back from the sitting, the oven handover, finishing work landing against serve time, the sequential fallback, both stacks, and an empty night answering plainly instead of inventing a schedule.

## Prep that happens outside the cook window (Meals arc M8, v2.81.0 — services/meals.py)
- **From real use**: some foods need work on a DIFFERENT DAY. Soaking rice the night before is cognitive load precisely because nothing about cooking dinner prompts it, and forgetting it silently invalidates the next day's plan. `Dish.needs_ahead` already existed — a closed enum (`thaw|marinate|slow_cooker`) with **no time attached that reminded nobody**, i.e. exactly the half that does not help. `PrepStep` is the half that fires.
- **"The night before" is a HUMAN MOMENT, not an offset.** Soaking rice for a 6pm dinner is something you do at ~9pm the evening before; `dinner − 12h` is arithmetically correct and behaviourally useless (it lands at 6am on the cooking day). So `when` is an enum — `night_before` fires at `prep_reminder_time` (20:30) on the PREVIOUS day, `morning_of` at `prep_morning_time`, and only `hours_before` counts back from the first sitting. Encoding it purely as a number gets the arithmetic right and the behaviour wrong.
- **Opt-in per dish, never inferred**: whether rice gets soaked is a fact about this household, not about rice — the same reasoning as `MealIngredient.kind`. Legacy `needs_ahead` deliberately does NOT auto-create reminders. Restating the same action edits that step rather than stacking a second; clearing with no action named clears all of that dish's prep.
- **Sweep** runs every cycle (not the 30-min beat) because a night-before nudge is only useful in a narrow window; `PREP_GRACE_MINS` (90) suppresses a stale one, since "soak the beans" three hours late is just noise. Markers set FIRST, per (dish, night, step). Horizon is 2 days — a sweep that only ever looks at today can never tell you to soak anything. Already-made dishes are skipped. Quiet hours are deliberately NOT applied: the evening prep time is late on purpose and a family that set 20:30 asked to be told at 20:30.
- **Surfaces**: prep chips in the repertoire editor (`+ prep ahead`, two questions rather than a form); `POST`/`DELETE /api/meals/dishes/{id}/prep`; `GET /api/meals/prep`; and `set_dish_prep` / `clear_dish_prep` / `get_prep_ahead` in both agent stacks ("we soak the rice the night before", "anything I need to do tonight?").
- *Known and accepted*: reminders fire for unpinned future days too, so a plate that later recomposes could mean a needless soak. A missed soak is worse than a spare one, and approving the week pins it anyway.

## Shopping & Meals kiosk (arc K1, v2.80.0 — templates/shopping.html)
- **The kiosk used to hide Meals wholesale** (`x-show="!isKiosk"` on the whole section), so the week was absent from the one surface the family walks past. The board is the read-only twin of the week strip: same `/api/meals/week` data, no editing, today's block ringed.
- **Images are for the kids, which decides everything about them.** A generated picture of "spaghetti" tells a literate adult nothing the word doesn't — but a child who cannot read fluently learns what is for dinner from the picture, and that is the only argument that justifies carrying images at all. It makes *accuracy* the requirement, so: the family's own photo outranks a stock one and is **never** painted over by a backfill (and since v2.106.0 there is finally a way to *add* one — see below); stock comes from Unsplash with a query biased to a plated cooked dish (`"<name> food dish cooked meal"`), deliberately NOT the Wikidata/Wikipedia chain the trip backgrounds use, which answers "chicken thighs" with anatomical diagrams. **Generated art is not used** — slowest, priciest, and least accurate, and an uncanny dish defeats the only case that justified the picture.
- **Pictures fill themselves in (v2.80.3)**: the board stayed picture-less on an install that *did* have an Unsplash key, because `image_url` is only ever written by a backfill and nothing ran one — the endpoint existed and the button came later. - **The block shows WORK, not the window (v2.80.1)**: every block read "180 min", because it printed `cook_window_mins` — free time available, clamped to `PREP_HORIZON_MINS` (180) — so every unconstrained evening showed the identical ceiling and the board looked broken. Blocks now show hands-on + oven time, and the window appears **only when it pinches**. A cook window of 0 is ambiguous on its own (it is what an unsolved day reports AND what a genuinely impossible evening reports), so the week payload gained **`has_cook`** to separate them: with a cooking adult considered, 0 means "nobody free to cook" (a first-class M2 finding); with none, the board stays silent. Warning on both extremes would put an identical scary number on every block, which is how a real warning gets ignored.
- *Known M2 quirk, deliberately not changed here*: the cook window measures the prep horizon back from the end of a free SPAN rather than from when food is needed, so a wide-open morning reports a full 180 even though it ends hours before dinner. That is why an ordinary evening pegs the ceiling.
- **Board legibility (v2.80.2)**: `?kiosk=true` forces the HA theme, and `body.ha-theme .text-white` is rewritten to the HA **primary text colour** — dark on a light dashboard. Board text over a dark photo therefore came out grey and unreadable. These blocks are always dark, so their ink is pinned by dedicated `.board-ink*` classes with their own text-shadow, never Tailwind's theme-swappable colour classes. Any future overlay-on-image text must do the same.
- **Grid tracks the VIEWPORT, not the number of days (v2.80.2)**: sizing columns by `week.length` rendered a 4-day window as two enormous half-screen blocks on a wall panel. Now `1 → 7` columns across breakpoints, portrait cards, sides capped at 3 + "+N" so a five-side plate cannot push the dish name out.

The heading is now the action, the chips carry a `+`/`✓` and read as buttons, and the list below finally has a heading naming it and its count — on kiosk the page's own title is hidden, so it had been unlabelled text.

Bought-before items outrank recipe staples; staples still seed the grid on a fresh install, since otherwise the shortcut is empty exactly when there is no history to learn from.

## Walmart cart (arc W1, v2.79.0 — services/walmart.py)
- **The two halves have wildly different costs, and keeping them apart is the design.** *Add To Cart is not an authenticated API at all* — it is a URL (`walmart.com/sc/cart/addToCart?items=ID_QTY,...`), documented as available "whether they are onboarded to Impact Radius or not". So once an item has an itemId, one tap builds a real Walmart cart with **no credentials, no approval and no quota**. Resolving a NAME to an itemId needs the Affiliate product API (consumer ID + private key), and localized per-store price/availability is the **OPD tier**, gated behind Impact Radius *and* an approved partnership request Walmart says it may never answer. Nothing here depends on that tier.
- **So the mapping is the product and search is the accelerator.** A `walmart_items` table maps a NORMALIZED family word → itemId, written once and reused by every future list (meal-sourced, photo-sourced or spoken). Same premise as the dish repertoire: a family buys roughly the same fifty things forever, so the map does not rot. Pasting a product URL fills it in (`item_id_from_url` — `/ip/<slug>/<itemId>`), which needs no API access; search fills it in faster when credentials exist. Normalization is deliberately gentle (whitespace + case only) — a clever normalizer collapsing "green beans" and "green bean paste" would be worse than none.
- **Auth**: Walmart I/O signs `WM_CONSUMER.ID`, `WM_CONSUMER.INTIMESTAMP`, `WM_SEC.KEY_VERSION` — sorted by header name, each value newline-terminated — with RSA-SHA256, base64. Credentials resolve add-on options → env → file beside the app (the Mapbox pattern); the private key never leaves the server and no endpoint returns it. Tested by **verifying against a locally generated key pair**, so the test proves the signature is correct rather than merely unchanged.
- **The unmatched half is never dropped.** `cart_for_list` returns every item it could not match, by name, and returns **no URL at all** rather than an empty cart — a list of 30 becoming a cart of 27 with no explanation is the same silent-skip failure the "+ List" dialog already had to be fixed for once. Quantity stays free text and is never parsed for meaning: only a bare count becomes a cart quantity, because ordering 2 of a 2-lb pack is a worse error than ordering 1.
- **`walmart_check.py`** is a standalone probe: credentials, signature, a live search, and a credential-free cart URL. It deliberately distinguishes a **401** (signature/key version wrong) from a **200 with no results** (credentials fine, account has no product-API access yet) — different problems that look identical from the UI.
- Separators stay literal (`safe=',_'`) exactly as the ATC docs show them. Percent-encoded commas would very probably work; "very probably" is not a thing to discover in a pickup bay.
- **NOT YET BUILT — more than one retailer.** W1 is Walmart-only because that is where this family shops, which is a reason to start there and not a reason to stop there. The two halves generalise cleanly: *resolve a name to a store's product id* and *build a cart URL from ids* is the same shape at every retailer, and the name→id map is the durable half. What does **not** generalise as written is the storage: `walmart_items` has no store column, so a second retailer is a schema change rather than a new service module — worth knowing before anyone starts.
  - **Whole Foods is specifically impossible**, checked 2026-08-06 (asked, and worth recording so nobody re-derives it). Ordering runs through Amazon; AWS states it provides no Amazon Fresh or Whole Foods API. The nearest analogue, PA-API 5.0's Add To Cart form (`ASIN.n`/`Quantity.n`/`AssociateTag`), addresses Amazon.com retail ASINs rather than store-fulfilled grocery **and was deprecated 15 May 2026** in favour of the Creators API. That leaves scraping, which is refused on the same grounds `cart_for_list` refuses a partial cart: a basket that quietly drops items is worse than no basket.
  - **Instacart is the strongest candidate, and it is not close** (checked 2026-08-06). The Developer Platform's *Create shopping list page* (`POST` to `connect.instacart.com`, dev server `connect.dev.instacart.tools`) takes an array of line items where **a product name is the minimum** and returns a shareable URL: the family picks a store, the cart is prefilled, they check out. Two consequences worth stating plainly:
    - **It deletes the hard half of W1.** `walmart_items` exists solely because Walmart's ATC needs an `itemId`, so every ingredient has to be resolved by search or a pasted URL first. Instacart resolves names itself. A list-of-strings → URL integration is roughly the size of `cart_for_list` with the mapping layer removed.
    - **One integration, many retailers** — the reason to prefer it over another per-store build like Kroger.
    - It needs an API key (unlike Walmart's credential-free ATC), and Instacart pricing generally carries fees and markup over store-direct pickup. So this **adds a fulfilment target, it does not replace Walmart** — and the two barely overlap anyway, since Walmart is not an Instacart retailer.
  - **Therefore the right abstraction is a FULFILMENT TARGET, not a store.** A target takes the list and returns a URL. Walmart's needs a name→id map to do it; Instacart's does not. Building `walmart_items` into a generic "store items" table would be modelling the wrong thing — the id map is one target's implementation detail, not a shared concept.
  - **Kroger** remains a valid per-store fallback (real public API, OAuth, cart-add endpoint), but is lower priority than Instacart for the same effort. Unverified terms and coverage.
  - **Restaurant delivery is a genuinely different bet, and weaker** (Uber Eats / DoorDash; *Postmates is not a separate target — Uber absorbed it and retired the app*). Three reasons to hold off, none fatal:
    - **Access is gated.** Uber's Consumer Delivery APIs do cover browse → cart → place order → track, but require written approval. DoorDash's open surface is merchant-side (third-party provider / retail) and Drive is logistics; consumer ordering is not openly offered.
    - **The app knows much less than it does about groceries.** A takeout night is a `source: 'ordered'` dish, which is generic ("takeout pizza") — there is no restaurant and no menu item to hand over. The honest cheap version is a deep link to a search, not a placed order, and a deep link needs no API at all.
    - **It fits the quieter nights, not the busy ones.** This family's constraint is eating in the CAR between activities; delivery to a fixed address at a fixed time is close to the opposite. Which does not make it useless — it makes the value concentrated on the evenings nobody is driving anywhere, and that is a smaller set than it first appears.
  - **The survey is still the first task**, and it is bigger than groceries: which retailers *generally* expose product search plus a cart-add URL or endpoint. The Walmart ATC discovery — a real cart with no credentials at all — is the precedent worth hunting for elsewhere.

## The week ahead (Meals & Provisioning arc M6, v2.77.0 — docs/meal_week_design.md, services/meals.py)
- **Deciding and provisioning are the load, and neither can be done on the day.** M1–M5 answered "what's for dinner tonight" and could not answer "what do I buy". The family's real routine — plan the week a day or two before a standing grocery run, so the list is solid before the trip — is now one **"how does this look?"**: approve or edit, and the shopping list falls out of it.
- **The one bug that made a horizon meaningless**: `_rank` measured recency from wall-clock `_now_ts()` no matter which day was being composed, and `last_served_at` only moves on a real serve — so seven future days all ranked against identical values and returned **the same entree seven times**. Fixed by `_as_of_ts(date)` (a plate ranks from midnight of its OWN date) plus a **`served` overlay** carried day-to-day through `compose_week`, so taking a dish Monday pushes it down Tuesday's ranking exactly as serving it would. Measured: **7/7 distinct entrees with the overlay, 1/7 without**; both halves asserted so the failure cannot return silently.
- **Which day to shop is DERIVED, not guessed (v2.77.1)**: the first cut hardcoded Saturday as the default — precisely the day a family with weekend activities has least room for a 90-minute trip, and it was my invention, not a family fact. `grocery_weekday` now defaults to **unset**, meaning "work it out": `grocery_day_candidates` walks every adult's `at_home` spans (the same `member_spans` primitive the cook window uses — a gap spent parked at a game is not a gap you can shop in) over three weeks and ranks weekdays by their **worst** occurrence, because a standing shop day has to work most weeks, not on average. `suggest_grocery_weekday` caches daily and carries the reason; `GET /api/meals/grocery-day` exposes the full ranking, and Config shows it as tappable chips with real free-time figures so the choice is arguable. An explicitly chosen day always wins — this is advice, not automation. Still not the final answer: the *right* home for "when do we shop" is a recurring grocery errand the solver places, which needs the list→errand link.
- **One line per skipped ingredient (v2.77.1)**: rice used by four dishes produced four identical "assumed on hand" lines, which reads as a broken list rather than one judgement about rice. `consolidate_skips` groups by (ingredient, **reason** — "staple" and "already on the list" are different statements about the same word, and only the first is overridable) and names every dish, with the night attached across a week. The **Add** override now flips the ingredient on EVERY dish that wanted it: "rice is not a staple for us" is a statement about rice, and fixing one of four dishes would leave the other three skipping it next week.
- **The window is the shop, not "7 days"**: `plan_window` derives it. Within `grocery_plan_lead_days` of `grocery_weekday` → `planning` mode, shop day → +6 (what this trip must cover); otherwise → `current` mode, today → the day before the next shop (what is LEFT of what was already bought for). Settings take all three touches (schema, config load *and* save, reader) per the v2.56.2 lesson.
- **Hold-still extends across the horizon, plus one rule: shopping for a dinner commits to it.** Untouched future days stay fluid and recompose as the schedule moves (Thursday becoming a 20-minute night *should* change Thursday); editing pins; approving pins. A day that recomposed after its ingredients were bought would have spent the family's money on a meal they are no longer having. Pinned days still feed the rotation overlay or the plan repeats around them. **`prune_plates` was deleting every plate dated before the one being written** — invisible while only tonight existed, but it would have wiped Mon–Wed when Thursday was pinned; now prunes relative to today.
- **Argyle brings it**: `propose_week_plan` on the 30-min sweep, ONCE per shopping cycle (keyed on the grocery date, marker set first), quiet outside the lead window and on an empty repertoire. Delivered as an `approve_week_plan` action proposal to the family channel + approvals banner, exactly like the car stop. **The nights ARE the message** — a card saying "a plan is ready" is just a second trip to go and look at it. Approval **recomposes rather than replaying the payload**, because the family may have swapped a night between the card and the tap.
- **Approving** pins every night and drains the whole span through `dishes_to_shopping`, so staples/already-made/duplicates skip with the same reasons the "+ List" dialog explains — now carrying the **night**, since chicken on Monday and Thursday buys once and that is only legible if you can see which night a skip came from.
- **Repropose was a no-op for three versions (fixed v2.87.0)**, and it took a bug report to notice. It reset every **pinned** night and reloaded — but `compose_plate` is deterministic, so an untouched night recomposes to precisely what was already on it, and untouched is the normal case. The button only ever worked as an undo for edits; pressing it on a week nobody had edited was *guaranteed* to return the same week. The reported symptom was "it does nothing when a night is locked", but the lock was incidental — skipping locked nights was already correct, and the family simply had nothing else pinned.
  - **What makes it move is a remembered refusal, not randomness.** `Plate.rejected` records the dishes a night has been offered and turned down; `repropose_week` writes it for every unlocked night and recomposes. Randomness was rejected outright: unpinned nights recompose on **every page load** and on a 15-minute timer, so a random composer would deal the family a different week each time they looked.
  - **Refusals are ORDERED and weighted, not filtered.** A filter needs a fallback for an exhausted pool, and a fallback needs to know *which* pool ran out — which the caller cannot see. Instead a refusal is a `-1000 × recency` rank penalty (dominating every term in `_rank`, which tops out near 100): a never-refused dish wins outright, and once everything has been refused the one turned down **longest ago** comes back first. A refused dish moves to the back of the queue. Two entrees therefore alternate forever instead of sticking on the top-ranked one, and no night can ever be left with no dinner proposed.
  - A rejections-only row carries `edited=False`, so it neither pins the night nor holds dishes still, and it is pruned with every other plate — a refusal expires with the night it was about. The per-day Reset deletes the row, which clears the refusals too: starting that night over means starting over. Locked nights are skipped entirely, refusals included — a night that is not being proposed has nothing to refuse.
- **Surfaces**: a week strip under Tonight on Shopping & Meals (chips per night, add/remove in place, per-day reset, pin marker, Repropose, one approve button); `GET /api/meals/week`, `POST /api/meals/week/approve`, `POST /api/meals/week/repropose`, `POST /api/meals/plate/pin`; and `get_week_dinners` / `approve_week_dinners` in **both** agent stacks, dispatched by `agent_router` and both terminal. *Repropose has no voice path yet* — it is the one week action the family cannot ask for out loud.
- **Deliberately not built**: nutrition/macros, recipes and steps (the repertoire is a filter, not a recipe box), auto-approval (a plan nobody agreed to, that spends money), breakfast and lunch.

## Plates composed from typed dishes (Meals & Provisioning arc M5, v2.76.0 — services/meals.py)
- **The repertoire is DISHES, and a plate is a RULE.** A family does not eat 15–20 unrelated meals; they eat combinations of ~25 dishes. M4 stored the combinations (`Meal.slots`), which was lossy (the number of sides froze at whatever was typed) and misleading (one "meal" standing in for a dozen dinners). Now `Dish.type` is `meal|entree|side|dessert` with `side_type` `vegetable|starch|salad|other`, and tonight is composed: a `meal` dish alone, or an entree + N sides, plus a dessert if the family keeps them.
- **Compose → adjust, not assemble.** The composer proposes; the family edits. That is the same propose→approve grammar the intake queue and car stops use, and it is what keeps this from being a nightly assembly chore — the objection that kept a meal-builder out in the first place applies to *mandatory* assembly, not to optional adjustment on top of a proposal.
- **Settings**: `sides_per_meal` (default 2) and `include_dessert` (default true) — a starting proposal, not a rule. "Only one veg tonight" / "we want three" are per-evening edits, which the frozen slot count could not express.
- **Already-made is a TOGGLE** (`POST /api/meals/leftovers/toggle`, or "the rice isn't made after all" via `clear_leftovers` with a dish name). The first cut only ever added, so undoing meant removing the dish from the plate and adding it back. Un-marking one dish out of a multi-dish note strips just that one and leaves the others; an emptied per-dish record is deleted rather than left behind. **Removing a dish from the plate also clears its mark** — it only means something while the dish is ON the plate, and leaving it behind made a re-added dish come back struck through.
- **`Plate`** is a dated record like `Leftover`: absent = compose fresh, present+`edited` = the family touched it and it holds still. `POST /api/meals/plate/{add,remove,reset}`; `GET /api/meals/plate` returns the dishes plus the aggregate timing and the M2 plan lines.
- **Choosing**: hard filters are allergies and (for a packed evening) portability; ranking is leftovers (+100 — already made is the obvious answer), soft tag affinity to the entree, effort, and rotation on `last_served_at`. Side variety is a **preference, not a filter** — filtering by `side_type` first meant an already-made dish of the "wrong" kind never entered the running, so leftover potatoes lost to a fresh vegetable. A `meal` dish must rank strictly ABOVE the best entree to take the plate, because everything ties on a fresh repertoire and `>=` let one-dish meals win every night.
- **Coherence** is a soft tag affinity to the entree rather than a modelled "goes with" relation: an occasional odd pairing costs far less than making a family maintain a compatibility matrix, and swapping a chip is one tap.
- **Extraction got simpler**: `add_dishes_from_text` returns a flat list of typed dishes — no slots, no option pools, and "veggies x 2" is explicitly ignored as a *plate* quantity rather than a dish property. Every alternative is its own dish ("beans (black, red, or pinto)" → three).
- **Migration**: `POST /api/meals/migrate-dishes` (`meals.migrate_slot_meals`) types M4's dishes from their legacy `role` and deactivates the slot-meals. Nothing the family entered is lost — only the frozen grouping.
- **Agent tools in both stacks**: `get_tonights_plate`, `change_tonights_plate` (add/drop one dish for one evening — the repertoire is untouched), `add_dishes`. Talking to Argyle is the intended path; the chips are the fallback.

## Dishes — the unit of work (Meals & Provisioning arc M4, v2.75.0 — models.schemas.Dish)
- **A DISH is the unit of cooking work, and a meal is a composition of dishes.** Roasted and mashed potatoes are different jobs with different times and different shopping, so M3's one-set-of-numbers-per-plate was the same "one number cannot express a weeknight" mistake the four-number split already fixed once, made a level down. `Meal.slots` is a list of `MealSlot`, each filled by exactly ONE of its `dish_ids` — a fixed part is simply a slot with one option, so there is no fixed-vs-substitutable distinction to maintain. **Combinations are never persisted**: 3 beans × 2 vegetables is 6 dinners, not 6 rows.
- **Slot identity is `MealSlot.id`, never the label.** "veggies x 2" produces two slots labelled the same, and keying choices/swaps off the label made them collide: one pick moved both, one chip refused to cycle, and when both resolved to the same dish the duplicate render key dropped a chip. Labels are display-only and may repeat; ids are backfilled onto pre-existing rows on first read and persisted. Two slots sharing a pool never pick the same dish (siblings' picks are excluded from both auto-choice and cycling), so "x 2" really is two different vegetables. Swapping one chip PINS the whole plate for the day — untouched slots choose automatically by avoiding what is taken, so without pinning, moving one vegetable shuffled the other under the family's hand.
- **A chip names the OPTION, not the category.** Three potato varieties all carry `short_name` "potatoes", so every chip read the same and you could not tell which was selected. `meals._chip_label` shows the words that distinguish a dish from its pool siblings, keeping the family's own noun when it is genuinely part of the name and preserving word order: "roasted red potatoes" among red/russet/yellow → "red potatoes"; "steamed carrots" with `short_name` "vegetable" → "carrots" (never "carrots vegetable" — the short name is often a category, not the food); "grilled chicken thighs" vs "baked chicken breast" → unchanged, because the shared noun sits mid-name. Single-option slots keep showing the family's own word.
- **Dish REUSE matches exactly** (`storage.find_dish_for_reuse`), never on substring. `find_dish_by_name` stays fuzzy so the agent can resolve "the potatoes", but reusing on a substring would let a later generic "potatoes" silently bind to "roasted russet potatoes" and inherit its times, ingredients and flags. Rice is rice; rice is not fried rice.
- **Options in a slot are all-or-nothing on `needs_detail`.** They are variants of one thing, so a lone "?" among clean siblings is model noise — "roasted potatoes (red, russet, yellow)" gives both the method and the varieties and is fully specified. If any sibling is clean, the flag clears across the slot; a genuinely unspecified single dish still asks. The rule runs on the RESOLVED slot (not just freshly extracted dishes) and is also applied on READ — because dishes are reused, a row saved with the flag before this existed came back flagged on every re-entry and no amount of re-typing the meal cleared it.
- **Dishes are reused across meals.** The rice in two meals is one `Dish` row (matched on name/short_name at creation), which is also what makes per-dish leftovers exact.
- **Composition** (`meals.compose_meal`): hands-on time **sums** (one cook, one pair of hands) while unattended time takes the **max** (the oven runs while the rice sits); `holds_well` is an AND and `portability` the weakest link — a plate travels only as well as its worst dish; `needs_ahead` takes the strongest requirement. Choice order per slot is explicit pick → anything already made → least-recently-served, so pools rotate with no maintenance.
- **Per-dish leftovers are EXACT** — `Leftover.dish_ids`. Because a dish carries its own minutes, "the rice is already made" subtracts the rice's real time instead of M3's proportional-by-component-count guess (which is now the legacy path only, for meals with no slots). An already-made dish inside a pool is also the obvious pick for that slot.
- **Vague dishes are guessed, flagged, and refinable — never a gate.** "Potatoes" says neither which kind nor how cooked, and both change the timing and the shopping line. The model GUESSES a sensible version, sets `needs_detail` + a single `detail_question`, and entry proceeds; the family sharpens it later via `POST /api/meals/dishes/{id}/refine` (chip `?` button, or the `refine_meal_dish` tool), which re-derives times and ingredients. Interrogating at entry time is how a repertoire never reaches the size that makes the filter decisive.
- **Shopping buys one plate's worth** (`POST /api/meals/plate/to-list`, one request for the whole plate), skipping staples, already-made dishes, `source='ordered'` ones and anything already open on the list. **Every skip carries its reason and its dish**, and the result opens a dialog naming them in plain language ("assumed on hand — bought in large quantities") — a silent skip is indistinguishable from a bug, and was reported as one. Staple skips get an **Add** button that flips that ingredient to `fresh` permanently (`POST /api/meals/dishes/{id}/ingredient`) AND puts it on the list, because whether beans are a pantry staple is a judgement about THIS household: bulk buyers restock them, others assume the cupboard. A dish with no ingredients recorded says so rather than passing over in silence.
- **Chip UI** on `/shopping`: each dish is a chip — tap the name to cycle that slot's pool (a same-day preference in `app_state`, pruned on write, never a permanent edit), ✓ to mark it already made, `?` to answer what the model was unsure about. REST: `GET /api/meals/dishes`, `PATCH`/`DELETE /{id}`, `POST /{id}/refine`, `GET|POST /api/meals/repertoire/{id}/plate`. Deleting a dish prunes it from every slot and drops any slot it emptied, so a meal never points at nothing.
- **Still no steps, ever.** A dish is (name, times, ingredients, portability). "Roasted russet potatoes" is a dish; how to roast them is not this app's business. Falls back to the flat M3 entry when the model is unavailable, so a typed meal is never lost.

## The Meal Repertoire (Meals & Provisioning arc M3, v2.72.0 — services/meals.py, models.schemas.Meal)
- **Fit, not method — a repertoire is NOT a small recipe collection.** A recipe answers "how do I make this"; a `Meal` answers "can we have this today", which is a scheduling question and the only kind Chauffeur stores. **There are no steps, ever** — that is the line between this and a recipe box; `notes`/`link` cover the twice-a-year meal nobody remembers, and `link` is the on-ramp if the family ever wants Mealie/Tandoor.
- **Four timing numbers, because one cannot express a real weeknight.** `prep_ahead_mins` (detachable work, schedulable into ANY earlier gap), `finish_mins` (must happen near eating), `unattended_mins` (oven/slow-cooker; does NOT count against the cook window — that is the whole point of the roast), `needs_ahead` (`none|thaw|marinate|slow_cooker` — lead time, not work). A 90-minute roast with 8 minutes hands-on FITS a 20-minute window; a 25-minute stir-fry that is 25 minutes at the stove does not.
- **`portability` (`none|handheld|utensils_ok`) is matched against the slot's `dining_level`** from M2: `utensils_ok` food needs a family willing to eat a full meal there, `handheld` only needs handheld tolerance, `none` never leaves the table. `holds_well` is required for a split dinner. The binding slot is the most restrictive one anyone actually has — if someone eats in the car, the roast is out for everyone.
- **Ordered food is ORDINARY, not an emergency.** `source` = `prep|ordered|hybrid` with `vendor`/`vendor_location`/`order_lead_mins`/`fulfillment`. "Thursday is pizza from the usual place" is a planned meal that happens to need a stop; the panic case is the same meal chosen late. This is why the arc has no standalone "bail-out" phase.
- **A component plate is ONE meal, not six.** "Chicken, rice, beans (black/red/pinto), veggies, salad" is a single entry whose parts substitute — the first schema could only express a fixed dish. `MealIngredient.options` means "any ONE of these satisfies this line", so separate lines are AND (rice *and* salad) and options within a line are OR (rice *or* potatoes); that one primitive covers both readings and no component/ingredient split is needed. `role` ('protein'/'starch'/…) is display-only and `optional` marks the salad nobody minds skipping. The drain writes ONE list item per line with the alternatives in its note ("black, red, or pinto"), and an option already open on the list satisfies its category — matching the bare option AND the option combined with the category name in both orders, since the family writes "black" but the list says "black beans".
- **Leftovers are a dated OVERRIDE, not a field on the meal** (`models.schemas.Leftover`, `services/meals.py` `apply_leftovers`). Chili is chili whether it is simmered fresh or reheated, so this attaches to the OCCASION and expires on its own instead of being a flag someone must remember to clear (`prune_leftovers` drops anything before today). A whole-meal leftover is exact — prep/unattended zeroed, `finish_mins` = reheat, `needs_ahead` cleared, and **nothing bought**. A PARTIAL leftover ("the rice is already made") cannot be exact because the schema deliberately has no per-component times, so the remaining hands-on is scaled by the share of components still to make and flagged `leftover_exact: false`; the made parts are skipped for shopping. Leftovers are applied BEFORE the window check — the whole point is that the app stops holding time for work nobody is going to do — and they **replace** cook-window pressure in the summary rather than adding to it, because manufacturing stress about work nobody is doing is the failure mode. A plain "we have leftovers" with no repertoire entry is a complete answer that outranks everything. Tools in both stacks: `mark_leftovers`, `clear_leftovers`; REST `GET/POST /api/meals/leftovers`, `DELETE /{id}`.
- **Ingredients are classed `staple` vs `fresh`** (`MealIngredient`), never quantity-parsed. Only fresh lines drain to the M1 shopping list (`meals.ingredients_to_shopping`, `added_via='meal'` + `source_meal_id`); an `ordered` meal contributes nothing at all and a hybrid only its prepped part. The classification is a property of the DISH, stable forever — that is how this recovers most of inventory's value while tracking item **class** rather than item **state**, with nothing to maintain and nothing to rot (design principle 2).
- **Entry takes the family's OWN WORDS, not a pre-digested title.** `create_meal(description)` accepts a bare name ("tacos") or a whole plate written the way they say it ("chicken, rice, beans (black, red, or pinto), veggies (carrots, green beans, broccoli), potatoes, salad") and the model derives a SHORT display name plus the components; the raw text is kept in `Meal.description` so the family can check it was read correctly. A "short name" longer than what they typed is rejected as an echo. Meal names are renameable inline in the editor (`PATCH /api/meals/repertoire/{id}`) — corrections are the editor's whole purpose, so the guessed components and the original wording are both shown there.
- **Population is where the phase dies if it dies: the human supplies the WORDS, the model supplies the rest.** `meals.suggest_meal_metadata()` makes ONE interactive-tier LLM call turning "tacos" into times, portability, tags and a staple/fresh ingredient split; the family corrects afterward. Entry cost must be one sentence or the repertoire never reaches the ~15 entries that make the filter decisive. **A failed or key-less enrichment still saves a plain entry** — failing to save a meal someone just named is worse than saving a rough one.
- **Dietary constraints on `FamilyMember`, mirroring the solver's grammar**: `dietary_avoid` is HARD (a meal tagged with it is removed entirely whenever that person is eating — allergies), `dietary_dislike` is SOFT (demotes in ranking, never removes). Ranking also weighs rotation (`last_served_at`, capped at three weeks), `effort`, and a small penalty for meals that wanted a head start.
- **`meals.meals_that_fit()` returns `fits` AND `blocked`, each blocked entry carrying its `why`** — nothing vanishes without explanation. An empty repertoire and a repertoire where nothing fits are deliberately different answers.
- **`meals.morning_prep_note()`** is the K5-launch-line touchpoint: when tonight's best fit wanted a thaw/marinate/slow-cooker start, it says so THIS MORNING while it is still actionable, and returns None otherwise.
- **Surfaces**: `/shopping` is titled **Shopping & Meals** and reads Meals → Shopping Lists, because meals GENERATE the shopping; a 🍽️ Tonight card (the filter result, with "+ List" and one-tap "We had this" so rotation maintains itself where attention already is) and a collapsed editor for corrections — deliberately **not** a browsable meal library; if people start browsing it, it has become a recipe box and failed. REST: `GET/POST /api/meals/repertoire`, `PATCH`/`DELETE /{id}`, `POST /{id}/served`, `POST /{id}/to-list`, `GET /api/meals/suggestions`. Agent tools in **both** stacks: `suggest_dinner`, `add_meal_to_repertoire`, `add_meal_ingredients_to_list`, `mark_meal_served`.
- Tests: `tests/test_meals.py` (74 scenarios, M2–M5) and `tests/test_shopping.py` (18, including three STATIC page checks: every `this.x()` and every markup handler resolves to a defined method, dialog helpers are called with both title and message, and no fetch skips `apiBase`). Every UI bug in this arc was invisible to the backend suite — a dead confirm dialog, an unreachable editor, and a call left pointing at a function a refactor deleted — so those three checks exist to catch that class rather than more backend coverage.

## The Day's Eating Plan (Meals & Provisioning arc M2, v2.71.0 — services/meals.py)
- **Eating is per-person and all-day, not a household cook window at 6pm.** Meals get prepped in pieces across the day and eaten in the car between activities; everyone-home-at-dinner is the degenerate case. `meals.member_spans()` derives each member's free spans from the cached schedule (commitments via `presence.members_at_event`, split legs collapsed), and `meals.eating_slots()` clips them to the meal windows they can serve. **Read-only over solver output — it writes no schedule state** (same discipline as trip-scheduling ownership).
- **A passenger eats during a leg; the driver does not.** The assigned driver of the NEXT commitment loses that leg's travel off the end of their gap, so a 20-minute gap against a 15-minute drive is a real slot for the kid and nothing for the parent. That one asymmetry, read straight off the manifest, is the structural reason the driving parent is the one who does not eat — and `no_slot` / `nobody_can_eat` are **first-class outputs**, not empty results (they are the honest trigger for suggesting food on the route, replacing any clock heuristic).
- **All-day presence is NOT physical occupation** (the same rule the passenger double-booking pass follows). All-day events and `event_type == 'background_trip'` run midnight-to-midnight, so counting them as commitments swallowed the whole day and reported everyone as having no gap to eat — the bug two kids on a trip surfaced. All-day markers ("Spirit Week") are skipped as commitments and leave the evening free. A **background trip means the member is AWAY**: `meals.away_on_trip()` scans the trip's whole date range (trips span days, so the event does not start on the day being planned) and `eating_plan` drops those members from the household plan into an `away` list — recorded, never silently omitted — so they are neither given a phantom at-home evening nor reported as trapped. Chauffeur does not plan trip meals.
- **Modality**: `at_home` / `in_car` / `at_venue`. A gap between two different places is only `in_car` when it is barely longer than the drive (`IN_CAR_SLACK_MINS`); a long gap that comfortably fits a round trip home (`HOME_DETOUR_MINS`) is `at_home`, because calling it in-car would tell the family to pack food they could have cooked. Same-location gaps are `at_venue` (bleachers).
- **Spans, never timestamps.** "Between drop-off and about 5:30 — about 20 min", not "eats at 5:10"; the schedule does not support that precision.
- **Household picture** (`meals.eating_plan()`): sittings grouped by **place first, then time** (a kid eating in the car and a sibling eating at home is split service even at the same hour — clipping to the meal window makes start times useless as a discriminator), `split`, `packed_count`/`packed_member_ids`, `packed_deadline` (whoever eats away from home needs food BEFORE their slot opens), and `cook_window_mins`/`cook_window_who`. The cook window is computed from **raw, un-clipped spans** trimmed to that deadline and measured back at most `PREP_HORIZON_MINS` — prep happens *before* people eat (you cook at 4:00 for a 4:30 departure), so clipping it to the dinner window would erase exactly the time that matters, and measuring from dawn would report a meaningless eleven hours.
- **`car_dining` / `venue_dining` settings (Config → General, "Where this family eats")**: `none|snack|handheld|full`, **default `full`**. How a family eats is a house rule, not a fact about cars — this family eats full meals with utensils in the car, others never eat in the car at all. Permissive by default because a wrong permission is a suggestion someone ignores in seconds while a wrong restriction hides slots invisibly and the feature just looks useless. `none` removes that modality's slots wholesale; an unrecognized value falls back to permissive, never to blocking. Each slot carries `dining_level` so M3 can match a meal's portability against it.
- **Silence on an ordinary day is a feature** (`plan_summary_lines()` returns `[]` unless the day is genuinely constrained — split, packing, no slot, or a tight window). A comfortable cook window is deliberately NOT the headline; emitting a plan every night is a stream of orders, not a reduction in load.
- **Surfaces**: the tomorrow drive digest (`family_digest.build_drive_digests` → `meal_lines`, appended to each driver's lines), a 🍽️ Tonight strip on `/routines?kiosk=true`, `GET /api/meals/plan?date=&meal=`, and the `get_eating_plan` agent tool in **both** stacks ("do we have time to cook tonight?", "who's eating when?"). Meal windows are module constants (`MEAL_WINDOWS`: breakfast 06:00–09:30, lunch 11:00–14:00, dinner 16:30–20:30), separate from `trip_scheduler.MEAL_ANCHOR` — a vacation dinner at 8:30pm is not a Tuesday.
- Assumption recorded, NOT confirmed by the family: every adult counts as cooking-capable. Tests: `tests/test_meals.py`.

## Shopping Lists (Meals & Provisioning arc M1, v2.70.0 — docs/meal_design.md)
- **Standing lists, bound to errands by TAG.** `ShoppingList` (name, `store`, `errand_tag`, `is_default`) and `ShoppingItem` are their own entities, NOT fields on `Errand`, because a recurring grocery errand regenerates every cycle while the list persists across all of them. `storage.find_shopping_lists_for_errand()` matches `errand_tag` against `Errand.tags` (contract), falling back to `store == Errand.location` (convenience, so a list finds its errand before anyone thinks about tags). `/api/errands` embeds `shopping_lists[{id,name,open_count}]` per errand and the errand card renders a 🛒 chip. This binding is the point of the feature: whoever the solver assigns the grocery run gets the standing list.
- **The app's first shared mutable document.** Two people at the store — or one adding while another shops — is the normal case, so there is **NO whole-list write endpoint for items**. Every mutation is a per-item `PATCH /api/shopping/items/{id}` carrying only changed fields, making last-write-wins correct per item rather than lossy. Checking is **idempotent** (two phones tapping the same row both succeed). Every write bumps `LAST_UPDATE_TIME`, so open list views converge over the existing `/api/stream` SSE.
- **Capture is ungated for everyone, including kids.** A list item costs the family nothing, so it lands directly with attribution (`added_by`, `added_via`) rather than through the proposal queue — approval would be friction with no gate (design principle 4). The kid persona prompt tells Argyle to add "we're out of cereal" immediately and say so.
- **Voice/text is the primary path** (~80% of the value): `add_shopping_items` (splits on commas AND the word "and"), `get_shopping_list_items`, `check_off_shopping_item`, `remove_shopping_item_by_name` — implemented in `agent_tools_v2`, bridged into v1 (`agent_tools.TOOL_SCHEMAS`/`TOOL_HANDLERS`), dispatched in `agent_router`, and marked terminal so no concluding LLM round is spent. Available in every context (admin, PWA driver, family chat, kid) since anyone may add. An ambiguous list name asks rather than guessing.
- **Dedupe applies to OPEN items only.** Saying "milk" twice does not create two milks (case/whitespace-insensitive, and a supplied qty/note merges into the existing row), but re-adding *after* checking it off is a genuinely new need and creates a fresh item.
- **Photo capture (`POST /api/shopping/photo`, `services/shopping.py`)** runs on the **vision** model tier and is aimed at the shots voice cannot do — the open fridge shelf, a pile of empty packages, a handwritten list on the counter (NOT an item you are holding; saying its name is faster). It returns **staged candidates** with `kind` (handwritten/shelf/packages/receipt), per-item `suggested` and `why`, and an `already` flag for things open on the list. That is a picker, not an approval gate: a shelf photo yields a dozen guesses and the family taps which are real. **Nothing is auto-added, and no inventory state is ever persisted** — a shelf photo answers "what should I add", never "here is what we have" (design principle 2).
- **Multi-store** is first-class (`store` per list, chips on `/shopping`); the default list is created lazily on first capture so a fresh install never fails a voice add. `/shopping?kiosk=true` renders read-only with a 60s refresh.
- **Barcode scanning is deliberately NOT built** — Open Food Facts solves the lookup for free with no key, but `BarcodeDetector` exists in no iOS browser, so today it means shipping a WASM decoder for the narrowest-coverage capture path (no produce, no bulk). Deferred to the Capacitor wrapper, which gets native ML Kit scanning for free.
- Tests: `tests/test_shopping.py` (15 scenarios).

## Background Trip Events
- **Trip Passenger Constraint**: If an event overlaps with a background trip and **ALL** passengers on the event are also on the background trip, the solver enforces that non-trip drivers cannot be assigned to it. (Conversely, if at least one passenger on the local event is NOT on the background trip, the event is allowed to be scheduled locally). It also ensures that if a trip driver *is* assigned, the event must be geographically close (within 60 minutes) to the trip's location. A manual override on the exact pair beats both bans (see Manual Override above). The pre-solve passenger filter (main.py) drops away passengers from overlapping events using the SAME 60-minute near-trip radius, and only applies the near-trip escape when the trip has at least one driver (or is 'global') — a kid away alone (camp bus) has no on-trip driver to shuttle them, so their home events are suppressed regardless of distance. The filter resolves each event cid to passenger entities the same way `compute_event_trip_entities` does (cid may be a passenger id OR a raw Google calendar id): events bound by a rule whose `passenger_ids` hold calendar ids used to keep raw cids (the rule-matched branch found no passengers to rewrite them with), leaving the filter blind while the solver still banned every driver. The rule-matched branch now also resolves `passenger_ids` bidirectionally (passenger id or calendar id, mirroring `does_event_match_rule`), so matched events get real passenger ids. Keep the two radii in sync: a passenger kept by the filter but unassignable by the solver renders as a bogus red "Needs driver".
- **Passenger double-booking auto-resolution (v2.46.0, `matcher.resolve_passenger_double_bookings`)**: the passenger-overlap hard constraint (2b) makes two overlapping different-location events sharing ANY passenger mutually exclusive **as wholes** — so a kid's solo recurring event (e.g. Tuesday class) used to knock a co-attended sibling event fully off the schedule every week. A pre-solve pass (main.py, right after the trip filter) resolves the one deterministic case: a kid double-booked between an event where they are the ONLY attendee and one with co-attendees is dropped from the co-attended event (it then schedules for the remaining kids; the solo event needs them or it has nobody to drive). This is default behavior — no setting, no rule type — because no priority concept is needed. Conservative by design, mirroring exactly when 2b bites: both events timed (all-day presence ≠ physical occupation), true time overlap, two different KNOWN locations, exactly one shared kid, resolved via `get_event_passenger_ids` (handles raw calendar-id cids). Two multi-passenger events, or two solo events, are left alone — the unassigned event's diagnostics still offer the manual `prompt_drop_passenger` action, and per-event config attendance / manual overrides remain the escape hatches. Drops are logged server-side and visible as the kid's pill missing from that instance. Tests: `tests/test_pax_conflict_drop.py` (8 scenarios incl. end-to-end solve).
- **Trip window semantics (INTENTIONAL)**: the suppression/ban window is the trip event's own times **padded with home→destination travel time on both sides** — people in transit cannot attend home events, so events overlapping the padded window are deliberately conflicted. Consequently the background trip's calendar times should be the **at-destination window** (arrival to departure), NOT include the travel: the padding re-adds it. Send-off/pickup logistics (camp-bus drop-off) then fall before/after the padded window and schedule normally. An **all-day** trip event starts at midnight, which swallows same-day logistics regardless of padding — give trips real times when boundary-day driving matters.
- **Suppressed events stay visible** (`Event.trip_suppressed`): an event whose passengers are all away is excluded from solving but NOT removed from the UI payload. It renders gray on the Calendar view with an explanatory banner in its details dialog ("Ignored for the driving schedule — everyone attending is away on a trip") — which is also how a mis-timed trip window gets noticed instead of events silently vanishing. The Agenda view renders suppressed events dimmed (50% opacity, gray bar) with a gray "✈️ Trip conflict" chip instead of the red "⚠️ Needs driver" badge. More generally, the calendar feed distinguishes **unassignable vs. merely unassigned**: `compute_diagnostics` now takes `trip_metadata` and emits `trip_conflict` reasons (mirroring the solver's trip-assignment bans), and when EVERY driver has a hard-block reason (any type other than `optimization`) the event is flagged `isConflict` — rendered amber ("⚠️ Conflict" chip on the Agenda, amber modal banner "assigning a driver won't fix it") instead of the actionable red "Needs driver". For split legs, one assignable leg keeps the red badge. The calendar details dialog also carries an **Event Configuration** button that opens an in-page config modal (calendar.html) — a sibling of the dashboard's edit mode using the same `api/events/config/{google_id}` + `api/events` PATCH contracts (passengers with per-passenger times, driver attendees, attendance mode, trip link, time/location overrides, Ignore Event); keep the two forms in sync when config fields change.

## Draft Trips & AI Scheduling
- **Draft-First Creation**: All newly generated trips (whether Exact Dates or Flexible Dates) are securely stored locally as Draft Trips in the backend JSON database, protecting the user's primary Google Calendar from unconfirmed events while iterating.
- **Smart Calendar Analysis**: The agent queries Google Calendar for upcoming free/busy schedules and intelligently cross-references this with destination-specific seasonal heuristics (e.g. avoiding hurricanes) to suggest an optimal booking window via the `/api/trip/{event_id}/suggest_dates` endpoint.
- **Budget Compliance**: For trip plan generation, the backend enforces the `budget_max_usd` property automatically. It intercepts the LLM output, sums the `estimated_price_usd` for all generated POIs, accommodations, and flights, and forcibly injects a warning payload to the chat context if the total exceeds the budget, preventing the LLM from silently ignoring constraints.
- **Strict Day-of-Week Mapping**: The background LLM mapping `valid_days_of_week` uses an absolute Monday=0 index, rejecting relative "Day X" labels to ensure POIs correctly map to absolute dates when solving in a mock calendar future environment.
- **POI counts & request economy** (`generate_trip_plan`): open-ended requests ask for ~3 POIs/night with a stated floor of 90% of that in the prompt's final instruction (10 nights → aim 30, floor 27). The healthy path costs exactly ONE LLM request; top-up CONTINUATION calls (max 2) fire only when the response comes back below the floor. User-specified quantities are always honored exactly and skip top-ups.
- **Flights**: plan generation (`generate_trip_plan`) MUST emit round-trip flights whenever an origin is known — the global `home_location` setting or a departure city stated in the request — unless the user isn't flying (driving/train/cruise) or the destination is within ~4 hours' drive; the per-trip `flight_preferences` field only shapes airline/seat choices, it does not gate whether flights are generated. When no origin exists and the LLM returns no flights, a visible actionable note ("set your Home Location in Settings...") is appended to `budget_warning` instead of silently omitting flights. The agent also has direct flight tools: `generate_trip_flights` / `add_trip_flight` / `edit_trip_flight` / `delete_trip_flight`. A bare "add flights to the trip" request must NOT turn into an interrogation: the agent calls `generate_trip_flights`, a dedicated one-LLM-request generator (`trip_planner.generate_trip_flights`) that uses the home location as origin and the trip's destination/dates to produce round-trip flights (outbound arriving day 1, return departing the last day; flight_number left null — never invented), deduplicates against existing flights by route+departure-date, and adds them as editable estimates. The Smart Planner (planner-mode) intent classifier routes flight requests to the same generator ('flights' intent) instead of misfiling them as POIs. `add_trip_flight` is only for a specific flight whose details the user provided. CRITICAL WIRING NOTE: the main chat widget (`/api/chat`) does NOT use the v1 agent loop — it goes through `services/agent_router.py` (Gemma) with the separate `agent_tools_v2` registry; flights there are exposed as ONE tool, `manage_trip_flights` (action generate|add|edit|delete), a thin wrapper delegating to the v1 handlers, with the router's CRITICAL instruction #3 mandating action 'generate' for detail-less flight requests (never interrogate the user). Any new trip capability must be wired into BOTH stacks or the chat widget won't have it. Times are 1-indexed trip-day ordinals + 'HH:MM' (day 0 = the day before the trip, for overnight outbound legs) — mandatory phrasing on drafts, where mock calendar dates must never surface; absolute ISO datetimes only when the user gave real dates. Guards: arrival must be after departure (rejects with overnight-flight guidance), duplicates (same flight number, or same route with no number, on the same departure date) are rejected toward edit_trip_flight, edit/delete identify by flight_id → flight_number → origin/destination with ambiguity errors instead of guesses, and a hand-edited price clears `is_live_price`.
- **Trip data ingest gate** (`services/trip_validation.py`): everything the LLM or agent produces is UNTRUSTED INPUT — every path that persists trip POIs or accommodations (plan generation, `generate_trip_accommodations`, agent tools `add/edit_trip_poi`, `add/edit_trip_accommodation`, any future importer) must pass through this module before storage. Zero extra LLM requests anywhere. Layers: (1) `reconcile_coords` — every generated POI **and accommodation** carries `approx_lat`/`approx_lng` from the LLM/agent; if the geocode lands more than `COORD_MISMATCH_KM` (60) away, the fuzzy match is bogus ("Burgundy Wine Trail" once matched a spot in Paris): the LLM's regional coordinates win and the matched place's identity fields (hours, website, wikidata, mapbox_id) are dropped. Agreeing geocodes are kept — they're more precise. Accommodation coordinates are the keystone: the scheduler's day→home-base map and geography fence trust them outright. Location *edits* re-ground coordinates the same way (stale coords are never kept for a new location). (2) `anchor_fields` — a single-day `is_background` entry under `ANCHOR_MIN_DURATION_MINS` (180) is demoted to a regular POI; anchors with `days_claimed > 1` or no stated duration keep their flag; the agent gets a note when demotion happens. (3) `repair_accommodation_overlaps` (batch, plan generation) — overlapping stay **date ranges** poison the day→home-base map: zero-night stays dropped, stays overlapping saved stays dropped, "umbrella" stays spanning ≥2 others dropped, remaining overlaps clipped forward. Same-location/same-hotel repeats with non-overlapping dates (return stays) always pass; the name dedup is date-aware. **Stay-night coverage** (`shift_stays_to_trip_start` + `uncovered_nights`, wired via `trip_planner._ensure_stay_coverage` — ZERO extra LLM requests): every trip night in [start, end) needs a stay; `mock_start_date` is already the ARRIVAL timestamp (draft creation computes it from the flight lookup). The generation LLM's persistent bias is starting the stay chain a day late ("overnight flight, arrive next morning"). The original multi-leg prompt pinned BOTH chain ends (first check_in = start AND last check_out = end), which converted that benign off-by-one into forced compression of a middle leg — a real trip's 2-night Riviera leg silently became 1 night. The fix keeps the chain anchored only at the START: the prompts say give every leg EXACTLY the user's nights (a correct allocation ends at the trip end by itself — never stretch or shrink a leg to hit it), and the gate TRANSLATES a late-starting chain back to the arrival day. Leg lengths are user intent and are never resized by code; the anchor is system truth, so translation preserves intent exactly and costs nothing. Translation is skipped when any existing stay is dated (a shift could collide). Nights still uncovered after translation are surfaced as a visible warning appended to `budget_warning` — never silently repaired and never worth a second request. A day-1 gap is uniquely bad: mid-trip gap days inherit the previous night's stay as home base; day 1 has nothing to inherit, leaving it baseless and unfenced. (4) Agent tool stay integrity — `add_trip_accommodation` REJECTS an overlapping or zero-night stay with guidance phrased in trip nights (mock dates never surface); `edit_trip_accommodation` treats the edit as fresh intent and CLIPS neighboring stays to make room (rejecting would deadlock two full-span stays), but refuses an edit that would fully swallow another stay — deleting is never a side effect. (5) `is_misplaced_accommodation` — a POI is reclassified as lodging only when it has a lodging-flavored name ('hotel', 'villa', 'inn', ...) AND no attraction signals (anchor flag, parent link, or category sightseeing/activity/shopping/food). Keyword match alone once hijacked 'Villa Ephrussi de Rothschild' (a garden-estate attraction) into an undated accommodation, silently deleting it from the itinerary; the asymmetry is deliberate — wrongly keeping a hotel as a POI is visible and recoverable, wrongly moving an attraction is silent data loss. (6) `reground_area_anchors` — area-anchor coordinates are re-centered on their children (see the anchor coordinate trust hierarchy under Trip Itinerary Scheduling); works on POI objects and plain dicts so plan ingest, agent tools, and the scheduler share one implementation.
- **Itinerary clear / rebuild / delete semantics** (trip.html + main.py): the trip page separates *planning* items from *fixed* items. A **calendar-backed POI** is one whose `event_id` is a real `cal::id` (committed by Chauffeur, or — planned — a linked external event), versus a fuzzy `draft_poi_` placeholder; `_is_calendar_backed_poi` is the shared test. **Rebuild** (`POST /api/trip/{id}/rebuild`, and the trip-page button) un-schedules only the fuzzy POIs and re-solves them through the trip's own CP-SAT scheduler (`schedule_pois_bulk`) — NOT the daily errand matcher (`schedule/refresh`) the old button wrongly called, which was the source of POIs scheduled with no `draft_poi_` id. Calendar-backed POIs stay put and the solver routes around them via its existing `locked` mechanism. **Per-day Clear** (`clearDay` → `POST /api/trip/{id}/unschedule`) and the **unschedule** endpoint remove items from the timeline WITHOUT deleting anything from the calendar; calendar-backed anchors are never auto-unscheduled. **Delete-from-calendar safety** (`clear_itinerary_api` + `_is_chauffeur_calendar_event`): "Delete from Calendar" only deletes events Chauffeur created, verified by the `poi_id`/`trip_id` stamp in the Google event's `extendedProperties.private` ([calendar.py](services/calendar.py) `create_event` sets these); externally-authored linked events (e.g. a family member's reservation) are ONLY ever unlinked, never deleted, and unknown-provenance events are refused. **POI-centric linked events** (implemented): a Google Calendar event is linked to a trip either from the Schedule page (event config `trip_id`) or from the trip page's **Add Attraction → "Link Existing Event"** tab — a multiselect searchable picker: it lists calendar events within the trip's own date range (±1 day, minus background trips and any already on the trip) — not a fixed days-from-today window. The list is sourced from **raw Google Calendar events** (`/api/calendar/events` → `calendar.fetch_upcoming_events`), NOT the solved/cached daily schedule: the latter's per-day cache can be stale and omit an event booked after that day was last solved (the bug where one dinner was absent from the picker while every other day's dinner showed), filters as you type, each pick becomes a removable pill, and "Link Events" posts all selections to `/api/trip/{id}/link_events` which sets every event config's `trip_id` and runs the POI sync ONCE (`/api/trip/{id}/activity` remains for single link / create-new). Add Activity (itinerary "Add") is create-new-only; its old Link Existing tab moved to Add Attraction. A linked event is reconciled into a **calendar-backed POI** (`is_external_event=True`, `source_event_id` = the `cal::id`, `event_id` = the same real id, `is_scheduled` at the event's real time) by `_sync_linked_events_to_pois` on every `get_trip_api` — created on link, removed on unlink, committed POIs never duplicated. It then renders in the Attractions grid (with a "From Calendar" badge) and the itinerary exactly like any attraction, and the solver's `locked` mechanism routes planning POIs around it (so a fuzzy lunch won't collide with a real reservation). The legacy `meta["activities"]` list is retired.  Calendar-backed POIs are FIXED anchors locked to their real event time: the daily errand solver's write-back never reschedules them or clobbers their cal:: event_id (it skips `is_external_event`/`source_event_id` POIs), the get_trip_api sync re-anchors any that were clobbered (event_id != source_event_id → refetch the event and restore its real time), and `_layout_one_day` keeps their exact time instead of snapping them to a meal anchor. Crucially, Level 2 layout also bumps every flexible POI PAST any fixed reservation's time window (a day-wide check, because the block skeleton's windows overlap — an 11:10 reservation lands in the morning block yet must not collide with a lunch-block POI), so a regular POI can never be laid out on top of a real reservation. Level 1 also counts food reservations via `_is_meal`, so a second meal is never assigned to a meal-block reservation's slot. A locked meal reservation is filed under its MEAL block (breakfast/lunch/dinner by time-of-day) even when its clock time sits just outside the block window (an 11:10 lunch is before the 11:30 lunch block; a 17:25 dinner before 17:30) — otherwise it lands in an activity block, leaves the meal slot open, and a fuzzy meal doubles up next to it. A linked reservation with an opaque name ('Chef Mickey', 'Maria and Enzo') and no enrichment cuisine is recognized as a meal from its start TIME (`_meal_from_iso`: breakfast [6:30,10:45), lunch [10:45,15:00), dinner [16:00,21:00); gaps → not a meal), setting category='food' + meal_type so it reserves its block. Applied at creation and healed for existing external POIs mis-tagged 'other' (one fetch, then it stops). Removing a calendar-backed POI (attractions or itinerary card) UNLINKS it via `POST /unlink_event` (clears the event config's `trip_id`, drops the POI) and never deletes the Google event; `delete_activity_api`'s calendar-delete branch is likewise gated by `_is_chauffeur_calendar_event`.
- **Post-solve sanity audit** (`trip_scheduler.audit_solve`): the last line of the data-integrity defense, run at the end of every `schedule_pois_bulk`. Deterministic haversine checks over the FINAL schedule state (including previously locked placements): any scheduled POI or anchor claim farther than `MAX_BASE_DIST_MINS` from its day's home base, and any day left empty while unscheduled POIs sit near its base (hard keep_clear days excluded), produce warnings. Warnings are printed as `[TRIP AUDIT]` server-side and streamed as a `{"type": "audit", "warnings": [...]}` NDJSON line; trip.html shows them in a "Schedule Warnings" modal so a geographically incoherent result is never presented as clean. Labels use 1-indexed trip days, never (mock) calendar dates.

## Trip Itinerary Scheduling (CP-SAT, services/trip_scheduler.py)
The trip itinerary is built by a two-level scheduler (design: `docs/trip_scheduler_design.md`), replacing the old greedy slot-scanner:
- **Level 1 (global assignment)**: A CP-SAT model assigns every POI to a `(day, block)` slot simultaneously. Each trip day has a block skeleton: `breakfast` 07:30–09:30, `morning` 09:00–12:00 (≤180 active mins), `lunch` 11:30–13:30, `afternoon` 13:00–17:30 (≤270), `dinner` 17:30–20:30, `evening` 20:00–23:00 (≤150). Distances for clustering use haversine on stored `lat`/`lng` — zero Mapbox calls during solving.
- **Level 2 (timing)**: Deterministic code lays concrete clock times onto each day (nearest-neighbor order within blocks, real cached travel times between consecutive stops, meals anchored toward 08:00/12:00/18:30, 5-minute snapping).
- **Meal intelligence**: `meal_type` ('breakfast'|'brunch'|'lunch'|'dinner'|'dessert'|'snack') and `dining_style` ('quick'|'casual'|'fine') on TripPOI drive placement. Fine dining → dinner block. At most one non-dessert meal per meal block per day. Desserts/snacks go in activity blocks, with a bonus for evening-after-dinner. Food without `meal_type` may take lunch or dinner. Legacy POIs infer meal type from `ideal_time_start`.
- **Multi-leg trips (accommodations as legs)**: each trip day's routing "home base" is the accommodation covering that date (check_in ≤ date < check_out); a checkout or gap day inherits the previous night's accommodation (you wake up there), so no day is ever geographically baseless. POIs gravitate to the leg they're closest to via the distance shaping term — no rules needed. On top of the soft pull there is a HARD geography fence (`MAX_BASE_DIST_MINS` = 240 haversine-min ≈ 170 km line-of-sight): a POI may not be placed, and an anchor may not claim, a day whose base is farther than that. The fence exists because soft penalties lose to placement rewards under capacity pressure (scheduling beats dropping by 1M vs ~300/min), which silently spilled POIs onto the wrong leg, and because a far anchor claim flips the anchor-day base switch into a net reward for dragging its whole neighborhood cross-leg. Real day trips (Paris→Reims ~182 min) stay inside the fence; cross-leg placement (Paris→Beaune ~386) cannot happen. Fenced-out POIs fail with an explainable distance reason; days whose base has no coordinates are never fenced; children follow their parent's claimed days instead of the fence. Anchors (background POIs) get the same pull: each candidate claim day is charged −300/haversine-min from that day's accommodation to the anchor, so an anchor claims days inside its own leg (a Riviera anchor never claims Paris-hotel nights). On flexible-date drafts the UI shows accommodation stays as trip-day numbers only ("Day 2", numeric day inputs in the edit dialog) — the mock calendar dates behind them must never be shown to users; real dates appear only once the trip has real dates. Accommodation cards render sorted by check-in (chronological leg order), one card per stay/booking; return stays to the same hotel stay separate cards (each has its own dates, price, live pricing, edit/delete) but get "Stay N of M" badges so the repeat reads as a return visit, not a duplicate. The agent expresses legs through `add_trip_accommodation` / `edit_trip_accommodation`, which accept absolute `check_in_date`/`check_out_date` or 1-indexed trip-night ordinals (`check_in_night`, `nights`; night 1 = first night — preferred for drafts since their mock dates are an implementation detail). Legs must be contiguous and non-overlapping (leg N+1 checks in when leg N checks out); omitting dates spans the whole trip. The plan-generation prompts (`generate_trip_plan`, `generate_trip_accommodations`) are instructed to emit one accommodation per described leg in the user's stated order with contiguous dates. For hard leg fences, add a `day_restriction` TripRule with `trip_days`. The trip map mirrors the solver's day→base semantics: a day's commute routes originate from the stay covering that night (check_in ≤ date < check_out); the checked-out stay is only a fallback for final/gap days. On a switch day the map draws a dashed commute transfer old stay → new stay (drop the bags), then routes the day's POIs from the new stay. Commute routes are direction-aware at the trip's edges: on an arrival day (check-in == that date with no prior stay checked out that morning) no morning stay→first-activity line is drawn (the day doesn't start at the hotel), and on a checkout-only (departure/gap) day no evening last-activity→stay return is drawn (the travelers leave). Commute lines are also only drawn to activities with known coordinates (a POI or accommodation match) — geocoding a bare label would dead-end the line at a spot with no marker. The map's route cache is pruned/re-homed on every itinerary render: routes whose activity pair was deleted, reordered, or moved to another day are evicted (or re-tagged to the new day) instead of lingering as phantom lines, and route layer redraws retry once the Mapbox style finishes loading instead of silently dropping/leaking lines.
- **Accommodation-switch days (transfer windows)**: on a day whose stay differs from the previous night's, the travelers pack, check out at `CHECKOUT_TIME` (11:00), and travel — so `_build_day_grid` clips that day's blocks to start no earlier than checkout + `_transfer_mins(old, new)`. Transfer pacing: haversine driving minutes up to `LONG_HAUL_KM` (350); beyond that, rail/air pacing (`LONG_HAUL_OVERHEAD_MINS` 150 + 0.12 min/km ≈ 500 km/h) — raw driving pace would wrongly write off the whole day (Riviera→Paris ≈ 16 h by road, ~4 h door-to-door by TGV). Blocks with under `MIN_BLOCK_USABLE_MINS` (30) of usable time are dropped; clipped starts round UP to :05 (Level 2 snaps starts DOWN, which would otherwise slip a POI before arrival); clipped activity capacities shrink to the remaining wall time. The same clipping now also applies the trip's start/end timestamps to partially-covered first/last days (no more dinner scheduled after the departure flight). This is deliberately DERIVED from the stays at solve time rather than stored as hidden "travel events": no phantom entities to exclude from the UI/calendar/dedup, and it can never go stale when leg dates change. Gap/checkout days (same stay inherited) are not clipped. The trip map's dashed old-stay→new-stay commute route (trip.html) is the user-visible face of the same transfer.
- **Anchors (background POIs)**: `is_background=true` + `days_claimed=N` makes a POI claim N full days (one POI — no more "(Day 1)/(Day 2)" clones; `claimed_dates` records the exact local dates). Claims are consecutive by default (soft), but a `valid_days_of_week` on the anchor is a HARD subset constraint (3 days + Mon/Wed/Fri = exactly Mon, Wed, Fri). At most one anchor per day. Children link via `parent_container` (background POI id) and may only be placed on the parent's claimed days. On a claimed day the distance "home base" switches from the accommodation to the anchor, so any POI is welcome on that day in proportion to its proximity to the anchor. Anchors generalize beyond theme parks (e.g. "Explore the Eiffel Tower district"). In the UI, anchors are never presented as ordinary activities: the itinerary wraps a claimed day's cards in a "🌟 Day Theme" container, and the trip map renders them as a star badge (indigo when scheduled, gray when not) with a "Day Theme" popup label instead of an activity pin. **Anchor coordinate trust hierarchy**: an anchor that kept a confirmed place identity through reconciliation (`mapbox_id`/`wikidata_id`) is a real venue — its coordinates are ground truth. Without an identity it is an *area* anchor ("Paris Classic Exploration") whose coordinates are an LLM regional guess: leg-scale accurate but not day-scale, and on a claimed day they become the home base, bending the whole day toward a place nobody visits. Area anchors are therefore re-grounded onto the centroid of their children's coordinates (`trip_validation.reground_area_anchors` — run at plan ingest, on agent `add_trip_poi`, and at the start of every solve); a *childless* area anchor snaps to its claimed day's accommodation right after claiming (a pure theme has no location of its own — it borrows the leg's). The regional guess is only consulted for the one thing it knows: which leg the anchor belongs to. **Anchors are containers, not summaries**: the generation prompts and `add_trip_poi` tool require every named sight an anchor covers (e.g. a tour "of the Eiffel Tower, Arc de Triomphe, and Champs-Élysées") to ALSO be emitted as its own child POI via `parent_container` (anchor name or id, fuzzy-resolved) — a sight living only in an anchor's description has no hours, price, map pin, or schedulability.
- **Objective tiers**: placement rewards by `priority` (must 10M / want 1M / stretch 100k) dominate; then soft-rule weights (default 50k); then shaping terms (−300/haversine-min from the day's base, −100/min between same-day pairs, day-balance −30/min beyond a 60-min deadband, claim-span −40k/day, dessert-after-dinner +20k). `ideal_time_start/end` is now a SOFT block preference (−20k off-window), never a hard failure.
- **Explainable failures**: unscheduled POIs stream a concrete `reason` ("restricted to Sat/Sun but the trip includes none of those days", "its parent 'Epcot' was not scheduled", "all eligible dinner slots were taken (N slots, M competitors)") plus `suggested_fixes` actions (`clear_days`, `disable_rule`) consumed by the failure modal in trip.html.
- **Incremental solves**: already-scheduled POIs are locked to their current day/block; adding POIs never reshuffles existing days (times within an affected day may adjust).

## Trip Rules (`TripRule` objects)
Per-trip scheduling rules stored in `TripMetadata.rules`, mirroring the driving Rule system. The AI agent creates/manages them via the `manage_trip_rules` tool (create/list/enable/disable/delete); the trip page shows a read-only Rules panel with an enable/disable toggle (`GET/PATCH /api/trip/{event_id}/rules`). Pydantic rejects unknown fields (`extra='forbid'`) — emit exactly the documented fields.
- `rule_type` values and their parameters:
  - `day_restriction` — matched POIs only on `days_of_week` (0=Mon..6=Sun) and/or `trip_days` (1-indexed). "Epcot on Tuesday".
  - `block_restriction` — matched POIs only in `blocks` (breakfast|morning|lunch|afternoon|dinner|evening). "Boat tour in the morning".
  - `budget_cap` — sum of matched POIs' `estimated_price_usd` ≤ `max_usd`. "Keep dinners under $100".
  - `day_capacity` — active minutes on matched days ≤ `max_active_mins`. "Keep Tuesday light".
  - `keep_clear` — nothing scheduled on matched `trip_days`/`days_of_week` × `blocks` (all blocks if unset). Defaults to HARD. "Leave Thursday afternoon free".
  - `spacing` — ≥ `min_gap_days` between matched POIs/anchors. "No two parks back-to-back".
  - `template_override` — trip-wide block changes: disable listed `blocks`, and/or clamp the day with `template_start`/`template_end` ('HH:MM'). "Nothing before 9am".
- Selectors: `poi_ids`, `categories`, `keywords` (name/description substring). Empty selectors match all POIs.
- `hardness`: 'soft' (weighted, default) or 'hard' (constraint). Agent-created rules default soft except `keep_clear`; escalate to hard only on emphatic user language. Soft `weight` default 50,000 (rule preferences outrank shaping terms but never placement rewards).
- POI fields (`valid_days_of_week`, `meal_type`, `dining_style`, `parent_container`, `days_claimed`, opening hours) compile into the same constraint pipeline as stored rules; the Rules panel lists them under "Derived from POI settings".

## Occasions — the context object (Occasions arc O1, v2.94.0 — `services/occasions.py`, `/occasions`)

- **`Occasion` owns nothing, and that is the design.** Errands, shopping lists, trips and plates keep their existing homes, capture paths and engines; the occasion carries an anchor date, a window, a headcount and a set of dish tags, and it is passed IN to the things that generate work. `contents()` is a QUERY across those homes, never a stored copy — which is what makes drift impossible. Named Occasion, not Holiday: "holiday" excludes birthdays and graduations (most instances) and means vacation in British English, which is `TripMetadata`.
- **Membership attaches to the coarsest wholly-owned entity**: `occasion_id` on `ShoppingList`, `Errand` and `TripMetadata`. A list made for the shark party is the party's, so an item added to it belongs to the party regardless of which page anybody was standing on — there is no per-item tagging to keep in sync. **The one documented exception is `ShoppingItem.occasion_id`**, for the standing grocery list, which the occasion owns only part of: the turkey wants to be on the normal list, bought on the normal run, because everything downstream (errand, shop day, `cart_for_list`) is keyed per-list and a second list at the same store rots. Same shape as the shipped `source_meal_id`.
- **Eligibility is not selection.** `dish_tags_for(day)` opens whichever tags the covering occasions name, and `_dish_ok` lets those `scope: occasion` dishes into the pool for the window. They still have to win on rank, and the family still chooses the night — a window that swapped the pool wholesale would propose turkey for four days running. Tags are named individually, so Thanksgiving never puts the birthday cake in play. An occasion with no explicit window covers its own anchor day, never an empty range.
- **Guests bind like family.** `OccasionGuest` carries `dietary_avoid`/`dietary_dislike` in the same grammar the composer already uses, unioned into `_eater_diet` for any day the window covers — a guest's allergy has to bind exactly like a member's or the list is decorative. `headcount` is per-row ("the Wilsons, 4") because that is how people answer. **Deliberately not an invitation system**: outbound SMS/email to non-members is a different animal and a group text already works; the list earns its place on headcount and diet alone.
- **Deleting the context never deletes the work.** `delete_occasion` clears `occasion_id` on every errand, list and item and leaves them standing. A family that believes otherwise will never delete one, so the confirm dialog says it in as many words.
- **Carryover is linked at creation** (`find_prior`), matched on kind first and title-word overlap second, only ever backwards in time. A wrong link is worse than none — it would diff Thanksgiving against a birthday — so the bar is match or nothing, never nearest. This is what O2's gap report diffs against.
- **Sourcing is the generative half**: `POST /api/occasions/{id}/source` turns "party favours for a shark party" into 8–16 concrete, buyable items scaled to the headcount, on a new list the occasion owns, feeding the shipped Walmart/Instacart cart rails unchanged.
- Surfaces: `/occasions` (create, guests, sourcing, and the derived contents), nav entry desktop + mobile + kiosk slug map, full REST, and `add_occasion` / `get_occasion` / `add_occasion_guests` / `source_for_occasion` in both agent stacks.
- Tests: `tests/test_occasions.py` — the window never empty, eligibility-not-selection across a five-day window, an unnamed tag staying shut, a guest allergy binding, list-level membership plus the documented exception, deletion preserving the work, carryover matching only on a real match, and both stacks.

## The interview and the gap report (Occasions arc O2, v2.95.0)

- **The template is an INTERVIEW, not a checklist** — this is the difference between planning help and a form. Each answer *generates* logistics rather than recording them: "how many are you feeding?" does not store a number, it calls `set_plate_hosting` on every day in the window, which scales the hands-on work and feeds the run sheet. `TEMPLATES` is deliberately **static data, never an LLM call**: a family answering the same question twice must get the same cascade, and a template that drifts cannot serve as a diff baseline.
- **Work is stamped at OFFSETS from the anchor.** `apply_template` writes real `Errand`s with `starts_on` at the offset and `window_days` carrying to the anchor — exactly how the intake arc already expresses "due by", so this is arithmetic against shipped primitives and adds nothing to the solver.
- **`Errand.occasion_key` / `ShoppingList.occasion_key`** record WHICH template line a thing satisfies. The gap report can only show an absence by matching against something, and an exact key beats keyword guessing at the one job where a false match is worse than no report at all.
- **The report is a DIFF, not an inventory.** Listing what exists cannot answer "have I forgotten anything" — the gap is invisible by construction, and nine tidy green rows manufacture confidence about the exact thing being worried about. Two baselines: the template, and `prior_occasion_id` (last year's rented tables, which no template ever knew about, carried with a "last time had this" note).
- **Sorted by SLACK against the anchor, and it carries no percentage anywhere.** Six of fourteen presents unbought is fine in October and an emergency on the 23rd; one number cannot say both. A test asserts the absence of any percentage.
- **Unanswered is not no.** A checklist line gated on an answer (`needs: 'cake'`) only counts as missing once that answer is YES — a family who has not been asked about a cake must not be told they are missing one, which is how a report becomes noise. Separately, `dismissed` records a settled decision ("no cake this year") so a waved-off line never resurfaces; a report that keeps raising a settled question stops being read.
- **A general answer never overwrites a specific one**: `_apply_headcount` skips any day the family already marked themselves.
- **Anticipation is pushed, the page is pulled.** `watchers._occasion_findings` nudges parents only inside a **21-day lead window** and only for gaps with ≤3 days of slack; the dedup key carries the date, so it is at most one nudge a day while the gap stands. A surface you must remember to open is one you do not open — but 200 days out is not a heads-up, it is nagging.
- Surfaces: the interview + gap report on `/occasions` (one question at a time, slack-coloured gap rows, per-row dismiss, "put the errands on the schedule"), `GET /interview`, `POST /answer`, `POST /apply-template`, `GET /gaps`, `POST /dismiss/{key}`, and `get_occasion_gaps` in both agent stacks.
- Tests: `tests/test_occasions.py` — the interview cascading into plates, hand-set nights surviving it, the diff against template and prior year, unanswered-is-not-no, dismissal, slack ordering with no percentage, and the watcher firing near but not far.

## The planning intelligence (Occasions arc O3 — THE ARC IS COMPLETE, v2.96.0)

Everything before this is nouns, and every noun is a logistics noun. This is what makes it *planning* help: what the app says unprompted, using what only it knows — where everyone is, who is driving, where the schedule has slack, how this family cooks. `occasions.insights()` returns five kinds, each block guarded independently so a dead schedule cache costs the one insight that needed it and never the whole panel (tested).

- **⚖️ Load distribution.** The research this arc came from is about *who carries it*, and the app has roles, assignment and a ledger. Every other product in this space ships a shared checklist and calls that equity; naming the imbalance is the actual intervention. Fires at ≥4 open errands when one person holds ≥70% (or all of them). **Stated, never scored** — the kid arc's calm-voice rule applies to adults, and a test asserts no percentage or score reaches the text. Three jobs is not a fairness problem and stays silent.
- **🤔 Open decisions with a cost that grows.** Anticipate → identify → **decide** → monitor: the first three are the interview and the gap report, and deciding is where people actually stall. Each unanswered question that GATES template work is reported with what waiting costs — "deciding now leaves 3 days for ordering the cake". The app cannot decide; making the price concrete is the value. Answering removes it.
- **📅 Schedule-aware timing.** Not "buy the presents by the 20th" but "Saturday the 13th is the clearest day between now and then". Computed from committed minutes per day in the cached schedule, against the tightest gap's deadline. Silent on a flat or unsolved week rather than inventing a recommendation.
- **🧊 Deadlines that fall out of the food.** `needs_ahead: 'thaw'` plus `serves` pushes the BUY date back from the serve date (~a day per four servings, floor of two — stated as a rule of thumb in the text because the app does not know the weight and must not pretend to); `order_lead_mins ≥ 1 day` does the same for anything ordered. Nobody types these deadlines.
- **⚠️ Clashes against the real calendar.** A driver assigned to an event inside the 10:00–19:00 cooking window on a day in the occasion's window. Trivial here, invisible to every list app.
- **Deferred, deliberately**: outcome capture ("three pies last year, one came back untouched" → suggest two). Highest compounding value, lowest urgency, and it needs a recording surface nothing has yet.
- Surfaces: a "🧭 Worth knowing" panel on `/occasions`, `GET /api/occasions/{id}/insights`, and `get_occasion_insights` in both agent stacks ("how's Thanksgiving looking?", "who's doing all the work for this?").
- Tests: `tests/test_occasions.py` (24 scenarios total) — the imbalance named not scored, a short list staying silent, decisions carrying their cost and disappearing when answered, thaw and order-lead deadlines, and insights failing one at a time.

## Find a setting — the settings registry (v2.97.0 — `services/settings_registry.py`, `/settings`)

- **The problem, measured**: `templates/config.html` had reached **5,631 lines** carrying **83 `Settings` fields**, all saved through one whole-object POST. Every arc added to it; none ever removed anything.
- **The insight**: the app had been decentralising settings for a year without calling it that — ICS feeds on the driver form, pairings on the dish row, meal rules in "How we eat", bus fields on the member card. All of those went where the family was already looking and all of them work. config.html is the residue, not the design.
- **`settings_registry.ENTRIES` declares all 83 keys** with a human label, searchable help text, a group organised by *what a person is trying to do*, and the `page` + `anchor` that OWNS each one. `audit()` returns missing/stale keys and **a test calls it**: a registry that quietly falls behind `Settings` is worse than none, because the index would claim to be complete while hiding whatever was added last.
- **`/settings` — "Find a setting"**: a search box over label, key and help, grouped, showing each setting's current value and a deep link to the surface that owns it. This is precisely the thing decentralisation destroys — somewhere to look when you half-remember a setting but not which page owns it — and it is why help text must contain the words a person would actually type ("oven", not `kitchen_ovens`). **Secrets (`token`/`password`/`api_key`) render as set/not-set and never as values**, tested: an index is a findability tool and has no business being a second place a token can leak from.
- **`audit_ui()` is the "nothing gets lost" guarantee, and it is a test.** It checks each registry claim against the owning template (following `{% include %}`, because shared editors are how this app surfaces several settings — the status-tier component is one, included by both Chores and Routines). A registry entry pointing at a page that does not actually carry the control is the silent failure the index would otherwise hide, and it would be *worse* than the old 5,631-line page, where at least everything really was on it. Run at the start of the migration it found **ten settings with no hand path anywhere** — days-to-solve, sides-per-plate, dessert, the three prep-reminder keys and the four Walmart keys. None were introduced by the move; they had simply never had one, and all ten now do. `ui_marker` is the declared exception for a control that never names its key (the tier editor is keyed by `kind` and saves through `/api/status-tiers`).
- **The whole meals group moved, not just the kitchen**: "Where this family eats", the shape of a plate (sides/dessert), planning and shopping (shop day + lead + propose-the-week + offer-a-trip, with the free-block candidate chips), prep reminders, the Walmart cart and affiliate trio, plus `kitchen_*` — all now under **⚙️ How this works** on Shopping & Meals, with anchors `#dining`, `#plate`, `#planning`, `#prep`, `#walmart`, `#kitchen`. The panel **POSTs only its own keys**, reading each one explicitly rather than spreading the settings response — hoovering up the rest is how a surface starts writing back keys it knows nothing about. No new endpoint was needed — `/api/settings` has always merged with `exclude_unset` — so what the whole-object save was missing is discipline, not machinery. config.html keeps a short pointer to where they went, because a setting that silently vanishes from where somebody last saw it is worse than one in the wrong place.
- Nav carries a 🔎 search icon beside the config gear (desktop) and a "Find a setting" row (mobile); the kiosk slug map knows the page.
- **Rule going forward**: a new setting is registered here and placed on its feature's surface, never appended to config.html. Remaining groups to move are listed in `docs/roadmap.md`.
- Tests: `tests/test_settings_registry.py` — completeness/no-drift, every entry having an owner and searchable help, search finding things by the spoken word, secrets never leaking, the kitchen pointing at Shopping & Meals, and a blank search listing everything.

## The occasion menu (Occasions arc O1b, v2.101.0 — closing a real hole in the brief)

- **The gap, in the family's words**: there was nowhere to view an occasion's menu, and no way to curate one ahead of time in isolation from the day-to-day list. The arc was complete *against the brief*; the brief was wrong here. It deferred menu SELECTION to `set_plate_lock` "one plate at a time" — right about the mechanism, wrong about the reach. By hand a plate is only editable through the week strip, which covers the next grocery window (a few days), so a Thanksgiving menu three weeks out was reachable by voice (`plan_specific_dinner`) and by nothing else. That is the hand-path rule broken in the one place it mattered most.
- **The menu stores nothing of its own — it IS the locked plate on the meal date.** That is what makes the run sheet, the shopping drain and the kitchen totals understand it for free, and why a menu chosen three weeks out survives a bulk repropose: `locked` was invented for exactly this ("this is Mom's birthday dinner"), and the occasion's title becomes the reason the night is spoken for. `meal_date()` is the anchor, because Thanksgiving week is five days and exactly one of them is the dinner everybody means.
- **The picker excludes other occasions' food.** The pool is everyday dishes plus dishes carrying THIS occasion's tags — the birthday cake has no business in the Thanksgiving menu. Anything already on the menu drops out of the picker, the same rule the meals page's dish picker follows.
- **Dishes added through an occasion are born `scope='occasion'` carrying its tags**, which is the whole point: curating a Thanksgiving menu must never put turkey and stuffing into the list a family looks at on a Tuesday. An occasion with no tags of its own adopts one (from its `kind`) at that moment — without it the new dishes would fall straight back into the everyday pool, the exact failure the surface exists to prevent. Typing dishes into an occasion also puts them straight on the menu: somebody doing that is choosing them, not filing them.
- **What it costs to cook comes back with it** — hands-on, unattended, headcount, cooks and the named oven clashes — because choosing a menu and discovering it needs two ovens are the same decision, and splitting them across two screens is how a family finds out on the day.
- Surfaces: `🍽️ The menu` on each occasion (chips, add-dishes box, a collapsed pool picker, cost line, clash line, clear), `GET`/`POST`/`DELETE /api/occasions/{id}/menu`, `POST /api/occasions/{id}/dishes`. Clearing releases the night and never touches the dishes, and the confirm says so.
- Tests: `tests/test_occasions.py` (30 scenarios) — the menu as a locked plate surviving a repropose, the cost and clash reporting, another occasion's dishes staying out of the picker, dishes born occasion-only and invisible on an ordinary night, an untagged occasion still getting its dishes marked, and clearing keeping the dishes.

## Occasion attendance (v2.103.0)

- **The defect**: "Who's coming" counted every non-helper family member automatically with no way to change it — you could only *add* guests. That is wrong the moment a household has an adult who lives elsewhere, a parent away that week, or a helper who genuinely IS invited to the party. **Attendance is a decision, not a property of the roster.**
- **`Occasion.attendance` is `{member_id: bool}` and stores only the DECISIONS.** Absent means "the default for that role", which is what lets a member added next month behave sensibly instead of silently missing from every occasion already on the books (tested). A stored attendee list would have had exactly that bug.
- **Role decides the default and nothing more**: `helper` is external by definition (hired driver/nanny, driving surfaces only) so they start OUT; everyone else starts IN. Both are one tap from the opposite. What role cannot express is who lives elsewhere — an `adult` grandparent five hundred miles away is indistinguishable from a resident adult — which is precisely why every member is individually togglable rather than derived.
- **`decided` is reported alongside `attending`**, because "we thought about it and yes" and "nobody has said" are different states, and only the second is something a report may ask about.
- **Headcount counts each person once**: attending members plus each guest row's own count, skipping guest rows that name a `member_id` — the roster already has them. Headcount drives `serving_for` on every plate in the window, so the toggle reaches the scaling and the run sheet.
- Surfaces: the household roster as togglable chips in "Who's coming" (struck through when out, helpers labelled), `GET`/`POST /api/occasions/{id}/attendance`, and `set_occasion_attendance` in both agent stacks ("Grandad isn't coming to Thanksgiving this year"). A name that is not in the family returns an error pointing at the guest path rather than silently doing nothing. The guest button reads "+ someone else" now that family members are listed above it.
- Tests: the whole roster listed, role defaults, toggling either way, a new member taking the default on occasions already booked, no double-counting, and both stacks.

## A calendar belongs to the person (v2.105.0)

- **The defect**: `calendar_ids` lived only on `Driver` and `Passenger`, so a person with neither profile could not have a calendar at all — no presence on the family calendar, no legend chip, their events never even fetched (`all_cals_to_fetch` was settings ∪ driver cals ∪ passenger cals). The only workarounds were worse than the gap: a **passenger** profile turns their events into ride demand and inbox items, a **driver** profile enters them in the assignment pool, and a *disabled* driver is filtered out before their calendars are collected, so their events vanish entirely. **Someone who drives themselves and chauffeurs nobody had no representation.**
- **`FamilyMember.calendar_ids` is now the single place calendars are set.** `Driver.calendar_ids` and `Passenger.calendar_ids` remain as **derived mirrors**, rewritten on every save by `storage.set_member_calendars` — chosen deliberately over migrating the field: `matcher.py` alone reads `passenger.calendar_ids` in ~20 places across conflict, attendance and rule resolution, and none of that had to change to fix an editing problem.

Removal still propagates, because `set_member_calendars` **rewrites** the mirrors rather than merging into them. ## The family's own history, which was being deleted daily (v2.107.0)

- **The defect**: `_persist_plate` called `prune_plates(TODAY)` on every write, from four call sites. Every night before today was deleted the moment anything touched tonight, so *"what did we eat on Tuesday"* had no answer and never would. The only trace was one `last_served_at` per dish — a single most-recent timestamp whose inadequacy the code already documents ("a cap of twice a week cannot see a third helping from last Tuesday"). A plate row is a date and a handful of dish ids; this was throwing away the only copy that will ever exist, forever, for nothing.
- **Plates ARE the record.** No second history table: a second source of truth for what was on Tuesday is how the two come to disagree. Retention is now 730 days (`PLATE_RETENTION_DAYS`). A night lands on the record once pinned, which `approve_week` does for every night it covers — so the ordinary "Looks good" flow fills it in. A night nobody ever touched leaves no trace, and that is honest: the app knows what was *agreed*, not what was eaten.
- **`arrange_week` is one primitive under two gestures**, because they are the same operation — "these dates now hold these dishes". Dragging a night onto another **swaps** them (dragging Thursday onto Tuesday is a statement about those two nights; quietly shuffling the five in between is not what anyone meant). "Again" takes a night off the record and either replaces the target or **pushes** everything after it back a day, the furthest-out proposal falling off the end. One write, so the week never renders a half-applied order.
- **Locked and past nights are refused BY NAME, not skipped.** A locked night is somebody's birthday dinner; a reorder that silently declined to move it is worse than being told, and the UI says how many stayed put. Past nights are refused because the record of what was eaten is not editable by a drag.
- **Why "Again" opens the record instead of repeating last night**: a pot of chili is not a one-night event, and the night worth repeating is often two or three back.
- Surfaces: a drag handle and an **Again** button on every night in the week strip, a dialog listing the last 21 days with their pictures, `GET /api/meals/history`, `POST /api/meals/week/arrange`.
- Tests: `tests/test_meals.py` — the past surviving a write, history being newest-first and excluding today, a refusal record not counting as a dinner, retention still pruning beyond two years, the swap, and locked/past refusals.

## A plate said in the family's own words (v2.108.0)

- **The defect**: M5's taxonomy — `meal|entree|side|dessert` plus `vegetable|starch|salad|other` — is restaurant vocabulary imposed on a household. "Entree" is not a word families use; "protein" is, for the ones who think nutritionally, and "a meat, a bread and a potato" is for the ones who don't. Worse, the fixed list actively lied: the extraction prompt asserted that starch means *"rice, potatoes, pasta, bread, **beans served as a starch**"*, so a household whose protein comes from beans got plates with no protein on them and no way to say otherwise. `MealComponent.role` had already reached this conclusion — *"deliberately NOT a controlled vocabulary… that road ends at a meal-builder"* — before M5 built one anyway.
- **`DishCategory` is the family's own vocabulary AND its composition rule**, one model rather than two, because "protein" and "one protein per plate" are the same sentence in every household that says it. Name, a description that steers the classifier, `min_per_plate`/`max_per_plate`, and `with_complete_meal`. Ids are stable and names are editable, so renaming "dessert" to "something sweet" propagates nowhere.
- **A dish belongs to several categories and fills AT MOST ONE SLOT per plate.** Multiple categories mean "can serve as any of these", never "counts as all of these at once" — black beans are the protein next to rice and the starch next to a steak, which the old `side_type` could not express at all. The first cut of this counted a dish against every category it listed, so beans filled the protein slot and silently satisfied the starch block too; assignment is now explicit (`assigned`, one block per dish) and walks the family's own order, which is why they put protein first.
- **`type: meal` stays**, deliberately, against the tidier design where categories subsume it. Tagging spaghetti & meat sauce protein+starch against a plate wanting 2-3 vegetables means every spaghetti night arrives with vegetables to delete. "It's a meal" is one word and it is what people say. A whole meal satisfies the composition; only blocks that opted in with `with_complete_meal` still apply — spaghetti night still ends with fruit, and the family says which block that is rather than the code hardcoding "dessert".
- **Minimums bend, maximums do not.** A block that cannot be filled from the repertoire is left short rather than duplicating a dish. A pairing counts against the block it belongs to (brisket bringing beans and fries fills the starch block, no third starch) but does NOT excuse the others — the vegetable the family asked for still arrives, which the old flat side count silently skipped.
- **Seeded from the repertoire, never a blank slate**: `storage.ensure_dish_categories()` maps the old taxonomy into the family's list, assigns every dish and collapses `type` to `meal|dish`. One-shot by stamp AND idempotent by name, so a deleted category is never resurrected and a re-run never creates a second "protein".
- **The hand paths that never existed**: category chips, a whole-meal toggle and `serves` on every dish row, plus `set_dish_categories` in both agent stacks. `serves` had been in the model since M4, set by the extractor, editable by nobody. An unknown category name is reported with the list of real ones rather than invented.
- `sides_per_meal` and `include_dessert` are **deleted** — model, registry, payloads and UI. Two taxonomies in parallel is worse than either; note the settings-reachability audit would have kept passing on the strength of the dead keys still appearing in an Alpine object literal, which is the limit of proving a control exists by grep.
- Tests: `tests/test_meals.py` (163) and `tests/test_occasions.py` (36) now compose through the new model rather than around it; new scenarios cover one-slot filling, a whole meal standing alone, seeding from a legacy repertoire, stable ids across a rename, the classifier being handed the family's words, and both agent stacks.

## How many people are eating, and what that makes of the leftovers (v2.109.0)

- **The defect, and it is worse than a wrong default: there was NO headcount.** `serving_for` was `None` unless somebody typed a number on a specific night for hosting, and `kitchen.scale_factor` returns exactly `1.0` for a falsy headcount — so every dish was made at whatever its own `serves` said, nothing was ever scaled, and nothing could be forecast. Occasions counted every non-helper member; meals counted nobody. `eating_plan` knew who was home and eating all along and that count reached nothing.
- **`household_headcount` is configured, with the roster as a fallback rather than an answer.** A household is not a list of profiles — people live elsewhere, a teenager eats at work, a helper is on the driving roster and never at the table — so counting profiles is a guess, and the setting is how a family stops us guessing. Resolution per night: an explicit `serving_for` (hosting) wins; otherwise the household default **less anyone away on a trip**; floor of 1.
- **`serves` decides whether there is a second night — by FLOOR, never ceiling.** A night counts only when there is enough left to feed EVERYONE again. Nine people eating a dish that serves six means making double and having three portions spare, and three portions is not dinner: proposing it again on that basis would mean cooking more of it, leaving a little spare again, forever. `leftover_nights = serves // headcount - 1` is exactly `floor((ceil(head/serves)*serves - head) / head)` — the long way round, from what is actually made — verified across every combination up to 24 servings and 14 eaters. **`serves` is a scaling input and nothing else**: it says how much to make and therefore what is left, and never makes a dish more or less likely to be proposed in its own right. A pot is made whole or not at all (`scale_factor` never scales below 1.0 — nobody peels three-quarters of a potato). Chili that serves twelve in a house of four is tonight plus two. The number had been on `Dish` since M4, set by the extractor, read only for ingredient scaling and editable by nobody.
- **A big pot comes back on its own**, which is what the family already does with Sunday's chili. `_leftover_coverage` gives a decaying bonus (20/nights) on the nights a batch still covers. Deliberately below the `+50` of an explicit `batch_cycle` rule: the family SAYING "one pot of beans at a time" outranks us inferring it from a number.
- **The pot empties.** The first cut measured only "when did we last eat it", which makes the gap permanently one day — so a big batch stayed covered forever and took every night of the week. That is precisely the bug `batch_cycle` was written to fix ("a batch is eaten EVERY day, so that gap is permanently one day and the window slid forever"), rediscovered from the other direction. Coverage now also counts the nights already eaten from it (`runs`), so a three-night pot occupies three nights and stops.
- Shopping needed no change: a dish on two nights already buys once (the cross-day consolidation), so a repeat night costs nothing extra at the shop.
- Surfaces: **Cooking for N** beside the plate blocks, a `+2 nights` badge next to `serves` on every dish row, the existing per-night hosting override, and `household_headcount` in the settings registry.
- Tests: the roster fallback and the configured number, hosting overriding and clearing back to the household, the arithmetic at several household sizes, a big pot returning the very next night and then stopping, and nothing repeating when nothing is left over.

## A tray is a tray (v2.109.2)

- **The gap**: `kitchen.scale_factor` is continuous, which is right for most food — cooking nine portions of carrots really is 1.5 pans and 1.5 times the peeling — and wrong for anything made in indivisible units. You cannot bake half a lasagna, so a family of nine eating from a tray that serves six needs TWO trays: twice the ingredients, twice the hands-on, and a real surplus rather than a rounding error. Both the timing and the shopping under-counted.
- **`Dish.whole_units`** (default false, because most food divides) rounds the factor up to the next whole unit. Never below one, for the same reason as before: scaling down is the one direction that is pure fiction.
- **It cannot change the leftover forecast, and that is pinned by a test.** Rounding up adds strictly less than one unit of surplus, and a unit smaller than the household is by definition not another dinner — so the floor rule absorbs it. Verified across every combination up to 24 servings and 14 eaters, which is worth having in writing before somebody "fixes" the forecast to account for it.
- Hand paths, both of them: a **by the tray** toggle on the dish row, and `whole_units` on `set_dish_categories` in both agent stacks ("the lasagna is made by the tray"). The extractor is asked for it too, told plainly that most food is not — a tray, a casserole, a cake, a sheet pan, a loaf; and when in doubt, false.

## The wall panel (v2.110.0 — `?panel=true`, `/home`, `services/home_board.py`)

Chauffeur alongside Home Assistant rather than inside it: a touch display bolted to a kitchen wall, running Chauffeur and nothing else. Three pieces, and the admin-overlay idea was deliberately **cut** — a browser on any other device already administers the app, and a PIN-gated config overlay on the wall would have been a second, weaker copy of that with a credential to maintain.

- **`?panel=true` is kiosk mode plus a hand.** Resolved in `ha_theme.html` (the first thing in every page's `<head>`) which *writes `kiosk=true` into the address* before anything reads the URL, so all ten pages already gated on `?kiosk=true` light up unchanged. Re-deriving panel-ness in each of them would have been seven chances to disagree. `nav.html`'s existing param propagation then carries `panel=true` across every link, so the panel stays a panel by being walked around.
- **Touch sizing is one lever: the root font size** (16px → 19px in panel mode). Tailwind's type *and* spacing scales are both in `rem`, so every button, gap and tap target grows together and nothing reflows into a layout it was never tested in. The considered alternative — blanket `min-height: 44px` on every anchor — wrecks inline links on eleven pages. Checkboxes and buttons get explicit minimums on top, because a checkbox is 13px at any root size and checking one off is the main thing a kid does at the panel.
- **The shelf replaces the top bar.** The desktop row is twelve 14px links with 16px icons, every one well under a finger's 44px, and it does not collapse to the hamburger because a 10" tablet in landscape clears the `md:` breakpoint. The shelf is bottom-edge (where a hand already is, and the one screen edge page content never fights for) with 28px icons and short labels. The wordmark goes: a wall panel does not need to be told which app it is running, so **Home stops being a logo and becomes a destination**.
- **One `NAV_ITEMS` list, three renderings.** nav.html carried the same twelve links twice, hand-copied and already drifted (v2.102.0); the shelf would have made it three. The items are now data and a new page is one entry. `data-slug` on each link replaced the old `SLUGS` path map — under HA ingress an href is a token path, and mapping it back to a page name was a second source of truth.
- **`/home` is the board.** A hero — the next drive that has not happened, with a countdown recomputed *locally every second from the start time*, because between polls a countdown that does not move is just a label. Then a grid of glances. A wall board that only tiles six lists is a worse phone; the app already knows what is next, so the panel leads with it.
- **`services/home_board.py` assembles the whole board server-side into ONE payload.** Six tiles fetching themselves would be six requests per tick on a display that runs sixteen hours a day; this is one, cached 20s so a second panel (or an HA card) costs nothing. Nine tiles available — drives, kids, meals, shopping, chores, routines, occasions, weather, moments.
- **Three rules the tiles follow**, because a wall display fails differently from a web page:
  1. **A tile with nothing to say is absent, not empty.** Every builder returns `None` on an empty day. A grid of six boxes each explaining that it is empty is the characteristic failure of every wall dashboard, and it teaches the family the panel is usually wrong.
  2. **An empty configuration means the defaults, never a blank screen.** A blank display bolted to a wall is indistinguishable from a crashed one, so "nothing selected" can never resolve to "show nothing". `?tabs=none` is the single exception and means what it says — that one marks an embedded card wanting no chrome.
  3. **Nothing computes, proposes or writes.** The meals tile reads the *pinned* plate and shows nothing when none is pinned; it deliberately does not call `get_or_compose_plate`, which would compose and persist a proposal every 60 seconds forever. A display that changes what it is displaying is not a display.
- **The panel profile** (`panel_widgets`, `panel_tabs`, `panel_idle_return_seconds`) makes a wall display need no URL at all. Precedence is **URL → stored profile → defaults**: the URL has to win because an HA dashboard card is a second panel with different needs and its only config channel is its own address; the stored profile exists for the display that has nobody to type at it. Configured on `/home` itself (`#panel-setup`, hidden in panel mode) — you pick the tiles while looking at them, per the settings-decentralisation rule.
- **Idle return** is what makes the panel an appliance rather than a browser: untouched for `panel_idle_return_seconds` (default 180), any panel page goes back to the board, so whatever somebody wandered off into, the wall goes back to being the wall. Not armed on `/home` — there is nowhere to return to, and a page reloading itself for no reason is a flicker. **`storage.get_settings()` returns the stored dict with no model defaults**, so absent is read as 180 rather than 0; reading it as 0 would have shipped the feature silently switched off on every install predating it, and an explicit 0 remains a real "leave it where it was left".
- **Tested** in `tests/test_home_board.py` (14 scenarios) and `tests/test_nav.py` (rewritten, 9): empty-config paths can never blank the board, ghost drivers never reach the wall, a drive under way outranks a later one, mixed aware/naive schedule stamps do not raise (a panel that 500s is a black rectangle in the kitchen), one failing tile does not take the board down, and every offered widget has a builder behind it.

## Decentralised settings could not actually be saved (v2.110.1)

- **The bug**: `POST /api/settings` merges with `exclude_unset=True` *precisely* so a page can send only the keys it owns — its own comment says so — but `Settings.calendar_ids` was a **required** field, so FastAPI rejected every partial body with a 422 before the merge was ever reached. The write half of settings decentralisation had never worked. The meals page's "how we eat" panel, the kitchen panel and (once built) the wall-panel setup all POST their own keys and nothing else, and every one of those saves was failing.
- **Found by building on it, not by reading it.** The panel setup posts three keys; it 422'd on the first real save. The same call shape from `/shopping` fails identically, which is how a bug this central survives — each page's save is fire-and-forget, so a rejected write looks exactly like a successful one.
- **The fix is `calendar_ids: List[str] = Field(default_factory=list)`**, and it cannot clobber anything: `exclude_unset` keys off what the client SENT, so an omitted field stays out of the merge and stored values survive. Verified live — a partial save that omits the calendar list leaves a populated list untouched — and pinned in `tests/test_settings_partial_save.py`, which checks both directions at once: a partial body validates, an omitted field never reaches the merge, and an *explicitly* emptied list still travels (clearing your calendars on purpose has to work).
- The test carries one payload per decentralised surface, named, so a future required field says which page just lost its save rather than failing anonymously.

## The wall contradicting itself, and a tile per page (v2.110.2)

- **The bug, caught by photographing the real panel**: "Everyone's home 🏠 — Nothing left to drive today" printed directly above a tile headed "the rest of the day" listing a 5:00 PM drive, at 6:34 PM. The hero treated a drive as behind us once its **end time** passed; the drives tile believed only the **manual completed flag** — and nobody ever marks drives complete.
