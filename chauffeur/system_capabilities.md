# Chauffeur Solver & AI Scheduling Assistant Capabilities

This document outlines the core logic, constraints, and weighting mechanics of the Chauffeur Scheduling Solver. It serves as the primary context layer for the AI Scheduling Assistant when parsing natural language into `Rule` JSON objects or when providing scheduling optimization advice.

## Core Solver Mechanics (CP-SAT)

The solver formulates the schedule by assigning drivers to events in a way that maximizes the global "weight" (score) while strictly adhering to hard constraints. 

### Baseline Event Weights & Penalties
When evaluating whether to assign an event to a driver or leave it unassigned:
- **Base Assignment Reward:** `1,000,000` (modified by `unassigned_penalty_multiplier` in Theme settings).
  - *Leaving an event unassigned scores `0`. If a driver's total score drops below 0 for an event, the solver will refuse to assign them and leave the event unassigned instead.*
  - *This value is deliberately large so that assigning an event at all outweighs routing preferences. Compare bonuses against each other, not against this base — it is identical for every driver on the same event and therefore cancels out when choosing between drivers.*
- **Priority Scaling Bonus:** `+150` points per rank. (e.g., Priority 1 driver gets `+1350`, Priority 10 gets `+0`).
- **Driver in Event (Attendee):** `+50,000,000` (Massive bonus if the driver is also attending the event. This is the largest term in the model apart from manual overrides, and in practice it decides the assignment on its own.)
- **Primary Driver Bonus:** `+2000` (modified by `primary_driver_bonus_multiplier`).
- **Manual Override:** `+100,000,000` (plus the override's `created_at` epoch seconds, so newer overrides win). Dominates every other objective term, including the saturated load-balancing penalty (≤1.44M at its cap). Every hard ban in the model also carries an `overridden_pairs` escape — `unavailable` rules, `required`-rule bans on other drivers, driver personal-event overlaps, the passenger-overlap constraint, and the trip-assignment bans — so a drag-and-drop override always sticks regardless of any other setting. Before creating the override, the dashboard dry-runs the pair through `POST /api/overrides/check` (`matcher.explain_assignment_conflicts`): if the solver would normally refuse it (driver away on a trip, passengers away on a trip, unavailable/avoid/required-elsewhere rules, the driver's own calendar event at that time, preferred-hours violation), a confirmation dialog lists the human-readable reasons and asks "Override anyway?" — informed consent, never a silent block. The check reads trip windows/entities from `trip_metadata` persisted in the combined schedule cache.
- **Group Bonus:** `+1000` when both events of a `group` rule go to the same driver.
- **Stickiness Bonus:** `+5` points if they drove the same event in the previous run.
- **Passenger Continuity:** Up to `+50,000` points if a driver handles consecutive events back-to-back with the same passenger. This decays linearly to `0` dynamically based on the specific travel gap threshold where a driver would typically have enough time to go home for a layover (e.g., 75+ minutes).
- **Location Continuity:** Up to `+5,000` points if a driver handles consecutive events at the exact same location, decaying linearly to `0` at a 3-hour gap.

**Penalties:**
- **Travel Time:** Scaled heavy penalty (approx `-600` points per 10 minutes) of driving from the previous event's location to the next. This penalty *only* applies if the gap between events is 1 hour or less, to avoid unfairly penalizing drivers for taking completely independent trips separated by long layovers at home.
- **Tolerance Overlap:** Heavy dynamic penalty (`-50,000`) if an event relies on a tolerance rule to be feasible for a primary driver. The penalty comfortably overcomes the primary driver bonus (`+2000`) and group bonus (`+1000`) combined, so the solver prefers a clean secondary driver over a primary driver who has to be late. It does **not** overcome the attendee bonus or a manual override, and it exactly ties the maximum passenger-continuity bonus (`+50,000`) — so at a near-zero travel gap, continuity can cancel it out.
- **Preferred Hours Violation:** `-2,000,000` points if an event falls outside the driver's preferred working hours. At default settings this drives the score below 0 (`1,000,000 - 2,000,000`) so the event stays unassigned. It does **not** hold if the driver is an attendee (`+50,000,000` swamps it) or if `unassigned_penalty_multiplier >= 2.0`.
- **Soft Buffer Violation:** `-2,000` points if an event slightly overlaps a buffer zone.

### Load Balancing Mode (optional)
Toggled by `load_balancing_enabled` in Settings (Config → Drivers tab; default **off**), with a companion `load_balancing_metric` combo box choosing what "load" means. By default the solver has **no fairness term**: per-event driver scores are independent, so the highest-scoring driver (primary group, lowest `priority_index`) absorbs every event they can physically fit ("bucket filling"), and the stickiness and continuity bonuses reinforce that concentration across runs.

When enabled, the solver subtracts a **quadratic penalty on each driver's daily load** (sum-of-squares is minimized by an even split, so each additional event on a loaded driver costs more than the same event on an idle one). The metric sets the per-event load value and penalty coefficient:
- **`events`** — 1 per event, coefficient `10,000`. Fair by count, ignores duration and distance.
- **`driving_time`** — round-trip minutes from the driver's home (falling back to the global `home_location`) to the event, clamped to 240, coefficient `5`; unknown routes cost a neutral 60 so a home-less driver never becomes a free sink. This is a **proxy**: true driving is only known after assignment, and chained events share travel, so back-to-back same-location events each count a full round trip. A driver living at the venue genuinely has zero driving load and will soak up those events — by design.
- **`occupied_time`** (default) — summed event durations in minutes (each clamped to 600), coefficient `1`.

Interaction with other weights (all metrics):
- **Overrules:** the Priority Scaling Bonus (`+150`/rank) and Primary Driver Bonus (`+2000`) — a typical one-event move gains ~10k–40k points.
- **Does not overrule:** Attendee bonus (`+50M`), Manual Overrides (`+100M`), or `required` rules. Tight passenger-continuity chains (up to `+50,000`) also survive unless the imbalance is severe.
- **Never causes unassignment:** each driver's load saturates at a per-metric cap (`AddMinEquality`), bounding the marginal penalty of one more event strictly below the `1,000,000` base assignment reward.
- Balancing counts only solver-assigned driving (including self-driven attendee events); personal calendar events that need no driver are not counted.

### Cars & Vehicle Assignment (C1, v2.47.0 — docs/car_entity_design.md)
Cars are an optional entity (Config → People tab → Cars; `/api/cars`; `Car` in `models/schemas.py`). Each car has: `seat_capacity` (passenger seats, excluding the driver), `allowed_driver_ids`, optional `allowed_passenger_ids` (car-seat restrictions; `null` = anyone fits), optional `default_driver_id` (the "usual" driver), `unavailable_ranges` (inclusive ISO date ranges — loaned out, in the shop), and `is_disabled`.

- **Inert when unconfigured**: with zero cars the solver builds no car variables or constraints — behavior is identical to the pre-car model, and `car_assignments` (4th return value of `solve_schedule`, `event_id → car_id`) is empty.
- **Implicit personal car**: a driver listed in **no** car's `allowed_driver_ids` is untouched by every car constraint. Only "pooled" drivers (listed on ≥1 car) must draw a workable car for each assigned event: the car must permit them, fit the event's passengers (count and, if restricted, identity), and not be in an unavailable range. A pooled driver with no workable car is banned from the event — escapable by manual override like every other hard ban.
- **Contention & handoffs**: a car is never in two places at once. Two different drivers may reuse the same car for nearby events only if the gap covers `travel(e1 → home) + travel(home → e2)` — handoffs happen at home; midday non-home handoffs are deliberately unmodeled. A driver chaining back-to-back events keeps the same physical car (and cannot chain into an event their current car can't serve without time to swap at home).
- **Swap penalty `−2500`**: using a car whose `default_driver_id` is someone else. Above priority deltas (≤ ~1,500) so priority alone never forces a key swap; below a `preferred` rule (`+10,000`) so rules can. Car chips render everywhere driver assignments do: calendar week/day badges (short ≤40-min events use a compact single-row layout: title + pax dots + car + driver, no time line), the calendar Agenda view, admin dashboard schedule columns, PWA family cards, the PWA driver view ("Take the {car}" per drive), and the kid lens ("Dad is driving you in the Minivan" — rides and legs carry a `car` object in `/api/member_day`). Swaps get an amber `⇄` accent.
- **`Driver.max_passengers`** (optional): driver-level passenger cap independent of cars (teen graduated-licensing laws). Applies even with zero cars configured; override-escapable.
- **Diagnostics**: unassignment reasons of type `"car"` — "No car this driver may drive works for this event: …", per-car failure detail (seats, car-seat restriction, unavailable + reason), and the `max_passengers` cap. Static bans only; a car merely claimed by another driver at that hour falls through to the generic conflict/optimization reasons.
- **Agent tool** `manage_car` (v1 registry, bridged to the chat widget): create/update/delete cars and `set_unavailable`/`clear_unavailable` date ranges ("the minivan is loaned to Aunt Sarah through Friday"). Cars also appear in `get_current_state`.
- **Photos** (v2.48.0): cars and family members can carry an `image` — a ~128px square data-URL photo, client-side cropped/resized on upload (Config → People / Cars), stored in the entity document (no file hosting). Photos win over emoji/initials wherever the surface has room: config lists, PWA member switcher and driver header, kid-lens driver chips and the "in the {car}" line, the driver-view Take-the-car chip, family-map markers, chores/routines tiles. Tiny calendar/dashboard chips stay icon+name.
- **Not modeled in the solver**: live car location, cars consumed by a pooled driver's personal (non-solver) events, mileage-based energy math.

Fields added to the model. Lesson: any new setting needs THREE touches — config.html load/save, the reader, AND `models/schemas.py:Settings` — or saves vanish without error.

- **Evening digest**: tomorrow's drive digest lines include per-driver car notes ("⛽ Minivan at 15% — see the fuel-stop proposal"), built in `build_drive_digests` so the `get_drive_digest` agent tool matches.
- Settings live in Config → Cars → "Car alerts". HA entity mapping is config-UI only (not exposed through `manage_car`).

## Travel Time Data & Caching
Travel times come from Mapbox's Matrix API using the free-flow `driving` profile (no traffic-aware profile is requested anywhere, and cached reads always report a traffic delay of `0`). Durations are therefore treated as **static**: a cached value for a pair of fixed addresses does not go stale, and the solver reads them without an age check.
- **Priming**: each schedule refresh primes only the location pairs it does not already have. Stale-but-valid pairs are never re-purchased — doing so previously exceeded the 100,000 element/month Matrix allowance.
- **`route_cache_duration_mins`**: defaults to `43200` (30 days). It only needs shortening if a traffic-aware profile is introduced.
- **Unroutable pairs**: when a location cannot be geocoded or the routing APIs fail, the pair is cached as `-1` and reported to the solver as `900` minutes (effectively unreachable). This suppresses retry storms against the API quota, but expires after **24 hours** so that a transient outage cannot permanently poison the cache.
- **Geocode precision & self-healing (v2.56.4)**: geocode-cache rows carry `precision` (`exact` | `city` | `failed`) + `ts`. Exact street-level hits are final; city-fallback and failed entries retry daily (`maps._usable_cached`, `GEOCODE_RETRY_SECS`) — a single bad geocode can never weld an address to the city center permanently (the old code cached the city fallback under the full address forever). Legacy pre-precision rows are sniffed on read (address starts with a house number the display_name doesn't echo → treated as city, retried immediately). Re-saving Home Location purges a non-exact home entry (a user-visible fresh-lookup lever); a *changed* home always purges.
- **The amputation bug (fixed v2.56.4)**: `extract_street_address` dropped the FIRST comma part of any >3-part address as a "business name" even when it was the street line itself — so Mapbox-canonical addresses ("123 St, City, State ZIP, United States") geocoded to the city center, poisoning home, event locations, and every Matrix travel time derived from them. Fixed (a digit-leading first part is kept whole) + one-time startup migration (`migrations.migrate_geocode_amputation_v2564`, app_state-gated): purges sniffably-wrong geocode rows and resets distance/route/schedule caches so durations re-derive from healed coordinates. Tests: `tests/test_geocode_cache.py`.
- **Home-pin transparency**: `/api/cars/stations/nearby` returns `home_label` + `home_precision`; the Config station map's 🏠 pin popup and caption show exactly what the home address resolved to, with an amber warning when it's only city-level — a wrong home pin is VISIBLE, never silent.
- **Travel-time forensics (v2.56.5)**: `GET /api/debug/travel?event=<title substring>` (or `?destination=`, `&origin=` override, `&fresh=true`) answers "why does the app think X is N minutes away": both addresses' cleaned form, geocode result (display name + precision — a wrong venue match is visible), straight-line km, the cached Matrix duration the solver uses, and with `fresh=true` a free-flow vs **driving-traffic** Directions comparison — separating "geocoded the wrong place" from "free-flow profile vs rush hour". Location-less events are reported as the problem instead of routed. v2.56.6 adds a `drivers` section: each driver's ACTUAL routing origin — a driver record's own `home_location` OVERRIDES the global home in the solver's initial edges (matcher.py `driver_default_home`), so a stale per-driver address produces leave-at chips that disagree with the global-home pair; `uses_own_address: true` with a different `resolved_to` is the smoking gun. Remember the standing design choice this tool exposes: Matrix durations are static free-flow (no traffic), so rush-hour drives read optimistic by design.

## Storage Engine
All persistence goes through `services/storage.py`, backed by **SQLite** (`data/chauffeur.sqlite3` locally, `/data/chauffeur.sqlite3` on the HA add-on) as of 2026-07-16. It is a document store — one table per legacy TinyDB table, each row `(doc_id, JSON data)` — accessed via a TinyDB-compatible table API (`services/storage_sqlite.py`), so callers still pass `tinydb.Query` objects. WAL mode; writes are single-row and take ~1 ms (previously TinyDB rewrote the entire 4.8 MB JSON file per write, ~275 ms).
- **Toggle**: `CHAUFFEUR_STORAGE=tinydb` env var is a one-release escape hatch back to the legacy engine; `CHAUFFEUR_DATA_DIR` redirects the data directory (used by tests, which must never touch `data/`).
- **Migration**: first sqlite boot auto-migrates `db.json` + `routes_cache.json` (route geometry now lives in the same SQLite file), preserving doc_ids and deduplicating the distance/geocode caches; originals are kept as `*.pre-sqlite.bak`. Restore-from-JSON = delete the `.sqlite3` file, place a `db.json`, restart.
- **Backups**: `/api/download_db` zips the data dir, snapshotting the SQLite file via the backup API (safe under WAL).
- **`db_lock`**: the coarse process-wide lock in storage.py is still in place (cheap now); removing it is a separate planned cleanup.

## Rule Attributes & Filters
Every rule (Routing Rule or Priority Rule) can filter events using any combination of the following criteria. The solver evaluates these using AND logic across different criteria types.
- **Keywords**: Match substrings in the event title or description. (Match Any or Match All).
- **Passengers**: Match specific passengers who are attending the event. (Match Any or Match All).
- **Days of Week**: Restrict rules to specific days (0=Monday, 6=Sunday).
- **Date Window (`start_date`, `end_date`)**: Restrict a rule to only apply on or after a specific start date (YYYY-MM-DD), and/or on or before an end date. Useful for driver vacations, summer schedules, or holiday-specific rules.
- **Time Window (`time_start`, `time_end`)**: Restrict a rule to a specific time of day window.
- **Location**: Match a substring in the event location.

## Supported Constraints (`constraint_type`)

When generating JSON for the frontend to digest, use the following `constraint_type` mappings.

### 1. Driver Assignment
Controls how the solver treats a specific driver for an event. Each of these is its own top-level `constraint_type` value — there is **no** `"assignment"` constraint_type and **no** `assignment_type` property. `Rule` has no such field, so a rule shaped that way is silently discarded by the schema and does nothing.

All four require `driver_id` to name the driver the rule applies to.

* `constraint_type: "required"` (Hard Constraint)
  * The selected driver MUST be assigned. All other drivers are strictly prohibited. The named driver also receives a `+500` weight bonus.
* `constraint_type: "preferred"` (Weight Bonus)
  * Grants a massive `+10000` weight bonus to the selected driver. They will almost certainly get the assignment unless physically impossible.
* `constraint_type: "unavailable"` (Hard Constraint)
  * The selected driver is strictly forbidden from taking the event.
* `constraint_type: "avoid"` (Soft Penalty)
  * Caps the driver's score at `1` — above `0` (the score of leaving the event unassigned) but below every viable driver. The driver is pushed to the absolute bottom of the priority list yet is still chosen as a "last resort" rather than leaving the event unassigned. A driver already excluded for another reason (e.g. a preferred-hours violation, which yields a negative score) stays excluded; `avoid` never resurrects them.

### 2. Duplicate Event Handling (`constraint_type: "duplicate"`)
For recurring events or overlapping schedules.
* `duplicate_action: "schedule_one"`: The solver will only schedule *one* matching event per `grouping_period` (daily, weekly, monthly, all).
* `duplicate_action: "schedule_all"`: Schedule all occurrences as normal.

### 3. Tolerance - Late Arrival / Early Departure (`constraint_type: "tolerance"`)
Allows an event to be "fudged" to make an otherwise impossible schedule fit.
* `tolerance_mins`: Integer. How many minutes the solver is allowed to overlap.
* `tolerance_type`: `"arrival"`, `"departure"`, or `"both"`.

### 4. Group Events (`constraint_type: "group"`)
Forces the solver to assign the exact same driver to a set of different events.
* Uses the `filter_sets` array instead of standard keyword/passenger filters. Each element in the array represents a distinct event match (e.g., grouping Lily's 8:00am swim practice with James's 9:00am tennis practice).

### 5. Buffer Time (`constraint_type: "buffer"`)
Enforces artificial padding around an event for a driver.
* `buffer_before_mins`: Integer.
* `buffer_after_mins`: Integer.

### 6. Event Attendance (`constraint_type: "attendance"`)
* `attendance_action: "stay"`: The driver must stay at the event for its entire duration.
* `attendance_action: "dropoff_pickup"`: The driver will split the event into a distinct Drop-off (at the start time) and a Pickup (at the end time). The driver is free to do other things during the event duration. The Drop-off and Pick-up are treated as independent events and are NOT grouped together, meaning they can be freely assigned to different drivers.

## Priority Rules (`PriorityRule` objects)
Distinct from standard rules, priority rules allow dynamic modification of the `Base Assignment Reward` (`1,000,000`) on an event-by-event basis. The `weight_modifier` is added to that base verbatim — there is no rescaling or remapping.
- **Why use this?** If the user says "Doctor appointments are the most important thing to schedule," you create a Priority Rule with `keywords: ["Doctor"]` and `weight_modifier: 100000`. This ensures the solver prioritizes finding *any* driver for the doctor appointment before solving other low-priority events.
- **Choosing a magnitude.** The modifier only matters relative to the *other* terms it competes with, since the base is identical across events. Useful reference points: `1000` is a mild nudge (enough to break a tie, roughly 17 minutes of travel penalty); `100,000` outranks the maximum passenger-continuity bonus (`+50,000`); `500,000` is effectively "schedule this before anything else." Negative values deprioritize. Nothing outranks the attendee bonus or a manual override.

## Matching Logic
- **AND vs OR:** Across different criteria types in a single rule (e.g., Keywords AND Passengers AND Days), the solver uses `AND` logic. An event must meet all configured criteria types.
- **Match Any vs Match All:** For criteria that support multiple selections (Keywords, Passengers), the solver defaults to "Match Any" (OR logic). 
  - For example, if two passengers are selected, the rule matches if *either* is an attendee.
  - This behavior can be toggled using the `keywords_match_all` and `passengers_match_all` boolean flags. When set to `true`, the solver switches to "Match All" (AND logic) for that specific criterion, requiring all listed keywords or passengers to be present on the event for the rule to match.
- **Filter Sets (Groups):** For grouped rules with multiple `filter_sets`, the evaluation across sets is an `OR` logic (matches if it hits Group A OR Group B).

## Best Practices for AI Recommendations
1. **Never use "Avoid" to completely block a driver.** If the driver absolutely cannot do it, use `unavailable`. Only use `avoid` if the driver should be a last resort.
2. **Use Group Events sparingly.** Grouping large chains of events can drastically reduce solver feasibility (making it "too sticky").
3. **Recommend Tolerance for tight schedules.** If the user complains that events are going unassigned due to 5-10 minute overlaps, recommend adding a `tolerance` rule to allow minor late arrivals.


## User Interface Architecture
- The Rules tab is divided into two sub-tabs: 'Routing Rules' and 'Priority Rules', controlled by Alpine.js state.
- Rule creation forms are located at the top of each sub-tab, before the respective rule lists.
- **Kiosk Mode (`?kiosk=true`)**: A streamlined display state that hides the triage inbox and header chrome while maximizing schedule visibility. In kiosk/read-only mode, driver columns with no real events for a day are hidden; background-trip banners (which are injected into every column for context) do NOT count as real events, so rule-unavailable or trip-absent drivers stay hidden on trip days. The regular editable dashboard always shows every real driver column so events can be dragged onto them. Ghost columns are identified by the exact `ghost_` id prefix (a bare `g` prefix check once hid real drivers whose ids start with "g" on their empty days). Driver columns are ordered: primary group first, then secondary, then `priority_index` within each group (1 = highest, first), alphabetically by name within the same priority; ghost columns always sort last. The event modal shows details only — the Matched Rules / Diagnostics tabs (including unassigned-reason diagnostics and suggestion actions) are suppressed in kiosk mode. The standard bottom-center Argyle chat box remains the single chat entry point (the old floating chat FAB/popup was removed from the dashboard — it survives only in the PWA `app.html`, where it is the mobile chat surface).
- **HA Theme (`?theme=ha`)**: Supports Home Assistant integrations via CSS variable propagation without overwriting the core Tailwind configuration palette. State is persisted across navigation views.
- **Identity colors (single source of truth)**: a person's color everywhere (event bars, passenger pills, driver columns/chips) is the family member's `color_code`. Historically calendar/pill colors were a deterministic hash of the Google calendar id (`calendar.get_calendar_metadata` PALETTE) — nobody chose them, so a member could show a color unrelated to their configured one. `main._apply_identity_colors` overlays member colors onto `calendar_metadata` (both the calendar-id keys and injected passenger-id keys) and `main._identity_driver_colors` does the same for the served drivers list; both run at SERVE time on every schedule response path (fresh, daily-cache combine, custom-schedule cache) plus `/api/calendars/metadata`, so a color edit shows immediately without cache rebuilds. Editing a member's color also syncs the legacy driver record's `color_code` (`storage.update_driver_fields`, no cache invalidation). One-time migration `storage.ensure_member_colors()` seeded child members (all at the default `#3b82f6`) with the hash color they were already displaying, stamped `color_seeded` so it never re-fires; adult colors were never touched. Calendars owned by no member (e.g. a shared family calendar) keep the hash color.
- **Voice via Home Assistant Assist ("Hey Argyle")**: `POST /api/v2/converse` accepts `{text, language, conversation_id?}` and returns HA conversation-agent JSON. When HA supplies a `conversation_id` (stable across follow-up turns of one voice session), the endpoint threads history through the same conversation store as `/api/chat` (ids prefixed `voice-`, titled 🎙️ from the first utterance — no LLM naming call), giving voice multi-turn memory; replies also mirror onto the `/api/v2/chat/stream` SSE bubbles. ## Free-Tier LLM Model Pools (services/model_pools.py, v2.30.0)

Every Gemini call in the app routes through quota-bucket pools so same-ability models combine their free-tier daily limits (each MODEL has its own quota; caps as of 2026-08-02):

- **lite** — `gemini-3.5-flash-lite` (500/day), `gemini-3.1-flash-lite` (500/day), `gemini-2.5-flash-lite` (20/day tail) → ~1,020 fast requests/day.
- **flash** — `gemini-3.6-flash`, `gemini-3.5-flash`, `gemini-3.1-flash`, `gemini-3-flash`, `gemini-2.5-flash` (20/day each) → ~100 quality requests/day.
- **gemma** — `gemma-4-31b-it`, `gemma-4-26b-it` (14,400/day each) → ~28,800/day, but 44-180s per call.

Tiers map work onto pool chains: **interactive** (chat widget, @argyle, PWA driver chat, HA voice, prep-kit suggest, refine button, v1 loop, conversation auto-naming) = lite → gemma — the user is waiting, and scarce flash is never burned on chat; **background** (email ingest, chat-suggestion classifier) = gemma → lite — nobody is waiting, burn the huge gemma quota first; **heavy** (massive trip generation incl. accommodations/flights/date suggestions, philosophy → rules, override-pattern analysis) = flash → lite → gemma — rare, quality-critical. A 429 puts the model on cooldown (until midnight Pacific when the error body names a per-day quota, else 2 min for per-minute limits; unknown-model 404s cool 6h and log loudly) so subsequent calls skip straight to a model with quota left — this is what makes pooling additive instead of retrying a dead model. `call_pool_json` walks up to 4 candidates per request; `pooled_or_direct` is the drop-in at provider-branched call sites (ollama keeps its single configured model, untouched by pools); `resolve_model(tier)` serves call sites with their own request code (v1 `agentic_chat_loop`, which feeds 429s back via `note_failure`). Pools are overridable without a code change via `model_pool_lite`/`model_pool_flash`/`model_pool_gemma` comma-separated settings keys (no UI). The `llm_gemini_model` setting now only affects the config-page connection test and ollama-parity defaults; the old `agent_primary_model`/`agent_fallback_model` keys are retired. Cooldown state is in-memory (resets on add-on restart — worst case one wasted 429 round-trip per model).

## PWA Driver Chat (driver-context agent)
The driver PWA (`app.html`) chat posts to `/api/chat` with `source: 'pwa'` and the logged-in `driver_id`; `handle_chat` forwards both into `agent_router.process_agent_request`. When the driver id resolves to a real driver, the Gemma router switches into **driver mode**:
- **Prompt**: identifies the driver by name, mandates brief mobile-friendly replies, and injects the driver's TODAY schedule (titles, locations, times, drive statuses) directly into the system prompt — zero extra LLM requests.
- **Driver tools** (registered only in driver mode; `driver_id` is injected server-side at dispatch, never taken from the LLM):
  - `get_my_route(target_date)` — the driver's assigned events (real + ghost assignments from the combined schedule cache) with per-event drive status.
  - `start_route(event_name)` — fuzzy-matches an event on the driver's day and marks its drive legs `in_progress` (same `drive_status` store as the PWA's Start Drive button).
  - `complete_route(event_name, action)` — records a TelemetryEvent (`picked up`/`dropped off`/`arrived`/`completed`, mirroring the Mark Completed button) and marks the legs `completed`.
- **Leg-id convention**: the PWA constructs drive-leg ids client-side (`init_{ev}[_1|_2]`, `route_{ev}_1..3`, `final_{ev}`); the tools mark the whole id family so timeline pills light up regardless of route layout. Unused ids are inert.
- The admin/dashboard chat (`source: 'admin'`) never sees driver tools. The v1 stack (`agentic_chat_loop`) has its own PWA prompt branch but is NOT the live path for the chat widget or PWA — both go through agent_router/agent_tools_v2.
- **v1→v2 tool bridge** (`agent_tools_v2.get_bridged_v1_tools` / `BRIDGED_V1_TOOLS`): the v2 pipeline natively covers messaging, chores, trips and driver overrides, but the scheduling-core (`add/delete_routing_rule`, `add/delete_priority_rule`, `run_solver`, `get_current_state`), the errand domain (`add/update/delete/get_errand`, `add/delete_errand_rule`), `update_memory`, `search_places`, and deep trip planning (`generate_trip_plan`, `add/edit_trip_accommodation`, `edit_trip_poi`) live only in the v1 handler table. The bridge reshapes those v1 Pydantic schemas into v2's format (single source of truth) and delegates execution to `agent_tools.execute_tool`. It is added **only in admin/family-hub context, never PWA driver mode** (a driver must not reconfigure global scheduling), and the dispatch carries a matching `not driver` guard. Schedule-mutating bridge tools (`SCHEDULE_MUTATING_V1_TOOLS`) flag `schedule_dirty` so the client re-solves, exactly like the override tools. Renamed/consolidated v1 tools (`add_override`→`assign_driver_to_event_fuzzy`, the `*_trip_flight` handlers→`manage_trip_flights`) are intentionally NOT bridged to avoid double-offering the model duplicate tools.

## Family Chat Agent (`@argyle`)
The family chat (chat_channels/chat_messages) is a vector of action, not just messaging. When a member posts a message containing `@argyle` (case-insensitive) to `/api/channels/{id}/messages`, `send_message` fires a background task (`_run_argyle_mention`) that routes the message to `agent_router.process_agent_request(source='family', acting_member=<sender>)` and posts the reply back into the same channel as the **Argyle system member** (`storage.ensure_argyle_member`, fixed id `argyle`, `role='assistant'`, `system=True` — excluded from the human roster and the agent's family-name list, but resolvable as a sender name for rendering).
- **Known identity, no asking**: `acting_member` injects the speaker's name/role into the system prompt so the agent resolves "me/my/I" and passes `from_member`/`member_name` automatically — the authenticated in-app member IS the identity layer (no PIN/DM guessing).
- **Role scoping**: `bridge_ok = (not driver) and (acting_member is None or _is_admin_member)`; only parents/adults get the admin scheduling tools (routing/priority rules, solver, errands). Children and helpers keep the everyday family-hub tools (reads, messaging, their own chores) but the admin tools are withheld both from the offered toolset AND the dispatch guard (a hallucinated tool name can't execute). Legacy callers (admin dashboard, HA voice) pass no `acting_member` and are unchanged.
- Argyle never re-triggers on its own posts (guarded by `sender != ARGYLE_MEMBER_ID`). Runs off-request because an agent turn can take tens of seconds; the reply arrives via the same SSE/push fan-out as any message.

### Interactive action cards (propose → approve)
Schedule-changing requests in the family chat are not executed silently — the agent proposes them as an interactive card a parent approves with one tap (`services/chat_actions.py`, `agent_action_proposals` table).
- **Agent tool** `propose_family_action(action_type, summary, payload)` (offered to the family chat): creates a typed proposal and returns a `card` the router surfaces onto Argyle's reply (`ChatMessage.card`). The family-chat prompt steers all mutations (reassign driver, mark unavailable / routing/priority rules, add errand) through this tool; reads/messages/chore claims stay direct.
- **Typed actions** (`ADMIN_ACTIONS`, each executed via the same tested handler the agent would call directly): `reassign_driver` (→ `assign_driver_to_event_fuzzy`), `clear_assignment` (→ `remove_override_for_event_fuzzy`), `add_routing_rule`/`delete_routing_rule`, `add_priority_rule`/`delete_priority_rule`, `add_errand`/`update_errand`/`delete_errand`/`add_errand_rule`, and `create_event` (→ `calendar.insert_event` on `settings.default_calendar_id`). Cards carry a human `action_label` (`ACTION_LABELS`) rendered as a badge. **`create_event` normalizes the LLM's datetimes (v2.28.7)**: the model reliably emits NAIVE ISO strings and Google 400s any `dateTime` without a zone ("Missing time zone definition") — which surfaced as a bare "the calendar rejected the event" AFTER the parent approved. `_create_event` now attaches the server's local offset to naive datetimes (zoned ones pass through), bumps a same-day all-day end to Google's exclusive convention, and returns specific messages for unparseable times / end-before-start / the calendar-rejection fallback (which now names the target calendar). **Named timezone stamping (v2.28.8)**: an offset-only `dateTime` is a correct instant but Google pins the event to a fixed "GMT-05:00" pseudo-zone, which looks broken in the Calendar edit UI — `calendar.get_calendar_timezone(calendar_id)` (calendars.get, process-lifetime cache, None on failure → field omitted) supplies the calendar's real IANA zone, stamped as `start/end.timeZone` on timed inserts in BOTH creation paths (intake `approve_proposal` and chat `_create_event`). Tests: `tests/test_chat_actions.py::scenario_create_event_normalizes_datetimes`.
- **Approval is the gate**: `POST /api/action-proposals/{id}/act` with `{act: approve|dismiss, member_id}`. Approve enforces the parent/adult scope (a child's tap is refused, the proposal stays open), executes the action, flags `schedule_dirty`, and Argyle posts the outcome + updated card back into the origin channel. Proposals are single-use (re-approving a resolved one errors).
- **Card lifecycle**: `proposed` (Approve/Dismiss buttons) → `approved` (✓, static) or `dismissed`. Frontend renders `m.card` in `app.html`; the Argyle system member is filtered out of member pickers/passenger lists but resolved as a sender name in-thread.

### Implicit detection funnel (opt-in)
When `settings.chat_suggestions_enabled` is on (toggle: Config → **Family Chat Assistant → Proactive Chat Suggestions**, off by default), a non-`@argyle` family-chat message runs a tiered funnel (`chat_actions.run_suggestion_funnel`) so the bot can *offer* help without being asked — but never butts in:
- **Tier 1 — keyword pre-filter** (`suggests_action`, deterministic, in `send_message`): high-precision phrases only ("can't drive", "we're out of", "reschedule", …). Ordinary chatter never reaches the agent. High-recall by design; precision comes from the next tiers.
- **Tier 2 — fail-closed classifier** (`classify_actionable`): one cheap single-shot LLM call returning `{actionable, confidence}`; any error / missing key → `actionable:false`. Must clear `SUGGESTION_CONFIDENCE_THRESHOLD` (0.6).
- **Tier 3 — agent + card gate**: runs the agent as the sender and posts a suggestion **only if it produced a concrete proposal card**; otherwise stays silent (never posts plain chatter). The surfaced card is an ordinary Layer-2 `action_proposal` — nothing executes until a parent approves. Suggestion, never action. Start narrow and expand `SUGGESTION_PATTERNS` as real `@argyle` usage reveals the intent distribution.

## Household Status Days (Presence & Status arc P1–P3b, v2.53.0–v2.56.0)
Family day-types ("Chemo Day", "Night Shift", "Trip Day") that answer a kid's scariest question — what state will home be in — BEFORE they walk through the door. Design: `docs/presence_status_design.md`; service: `services/status_protocols.py`; tests: `tests/test_status_protocols.py`.
- **StatusProtocol** (authored once, Config → People → Status Days): `name`/`emoji` (the family's label), `member_id` (the affected member), `need` (`cover` | `help` | `clear_deck` | `give_space`), `kid_message` + `adult_message` (**the family's own words, delivered verbatim** — the system schedules and delivers, it never composes kid copy), `keywords` (calendar trigger words). **StatusDay** is one dated instance (`date`, `protocol_id`, `note` = the one-tap "today's different" nudge, `set_by`, `source` `manual`|`calendar` + `source_detail`). Date-bound BY DESIGN: staleness is structurally impossible — yesterday's status never lingers.
- **The calendar knows (P2 sweep)**: every 30 min (quiet-hours gated, marker-first), `status_protocols.auto_set_from_calendar` scans the cached schedule window (7 days, errands excluded) for protocol keywords in event title/description and AUTO-SETS matching days (`source='calendar'`) — the set-burden lands on nobody, which is the point (the affected parent is least able to tap on their worst day). Safety is the beat design, not a permission prompt: the family authored the keywords deliberately, adults are DM'd immediately naming the matched event and how to undo, and kids only ever hear today/tomorrow — an advance auto-set has a built-in adult review window. Clearing a calendar-set day writes a 30-day tombstone (`app_state.status_auto_dismissed`) — a parent's dismissal is final, the sweep never re-sets it. Same protocol+date is idempotent.
- **Solver needs (P2)**: in `refresh_schedule_logic`, status days with `need` `cover` (they're resting/at treatment) or `help` (they're being cared for) become synthetic one-day `constraint_type='unavailable'` Rules for the affected member's driver (`status_protocols.unavailable_driver_dates`, today→+14d) — the existing matcher bans + "marked unavailable" diagnostics do the rest. Immune to the standard/AI rule enable toggles (a chemo day is not a routing preference). `clear_deck`/`give_space` never touch driving. Status-day/protocol mutations truncate the schedule caches like rule mutations, so the solver always sees current days.
- **Setting a day** (`POST /api/status/days`, the My Day quick-set for parents/adults, or the `set_household_status` agent tool in BOTH stacks — v1 handler bridged to the v2 router): kids get an Argyle DM with the family's words (today/tomorrow only — announcing Thursday's chemo day on Monday just moves the dread up; further-out days wait for the D-1 digest; kid quiet hours SKIP), and the other adults ALWAYS hear it (logistics message + need + who set it; the setter is excluded). Same protocol + same date refreshes note/setter instead of stacking. **Clearing announces too** — "never guessing" runs both directions (kids get the relief for today/tomorrow; adults always).
- **Surfaces**: status lines LEAD the kid evening digest and kiosk strip (`_build_kid_digests` — and a status day includes EVERY kid, overriding the "nothing means nothing" omission), a banner tops My Day (`member_day` returns `status_days`; kids see `kid_message`, adults see `adult_message` + need + ✕ clear armed two-tap), and the K4c dismissal push carries the status line on the SAME push (one push, not two) — and on a status day fires even with no ride/bus ("💙 About today"), breaking the silence rule for that day only.
- **Trip timeline (P3 spans)**: `StatusDay.end_date` turns an instance into a multi-day span (a trip, a hospital stay) — set via Config (date "to" date), the agent (`end_date` on `set_household_status`: "Dad's away Tuesday through Friday"), or the sweep (which collapses cached `_slice_N` trip slices back to their real event so a 5-day trip becomes ONE span, exclusive-midnight ends handled). Surfaces are day-position aware (`day_pos`/`day_count`/`is_home_day`): day 1 speaks the family's full message, middle days go light ("🧳 Work Trip — day 2 of 4"), the last day is the excited home beat ("🏠 Dad — home day! 🎉"); the set-announcement gives kids the whole span up front (home day + call ritual — "never guessing" includes when it ends). `StatusProtocol.call_time` adds a SOFT nightly call window on away nights ("📞 Around 7:30 PM — call with Dad") — worded "around", never on the home day, never a streak; a missed call reads as "catch you tomorrow". The mid-span clear announces as the home-early moment. Solver: one `unavailable` Rule spans the whole range.
- **Beat timelines (P3b, v2.56.0 — the general model)**: `StatusProtocol.beats` is a list of family-authored `(when, who, what)` beats — `anchor` (`start`|`end`) + `offset_days` (negative = before), `audience` (`kids`|`adults`|`affected`|`everyone`), `message` (verbatim), optional `need` override. This is what the fixed positional model couldn't express: **a one-day chemo event whose hard days come AFTER it** — day+1 rest-day words with `need=cover`, day+3 recovery words with `give_space`, care logistics to the co-parent, a "the schedule's covered, don't look at it 💙" note to the affected member. Resolution: a date is a status day if the span covers it OR a beat reaches it (`MAX_BEAT_REACH_DAYS` 45 bounds the query); an authored beat's words REPLACE the default line for that day per audience; a beat's `need` wins for that date (relaxing a span's cover mid-trip, or extending a ban past a one-day event — but a message-only beat outside the span never silently extends a driver ban). The solver feed is therefore per-date (`unavailable_driver_dates` emits one-day rules). Delivery: kids beats ride the existing surfaces ONLY (digest previews tomorrow's beat, My Day banner, dismissal push — no new pings); adults/affected beats DM once per (instance, beat, date) via `send_beat_dms` in the 30-min sweep, `adults` excluding the affected member. Beat-less protocols keep the P3 positional behavior byte-identical. Authoring: Config → Status Days → Timeline beats rows — the offset renders as an explicit [N] × [day(s) before | on the day of | day(s) after] × [the start | the end] control (v2.56.1; storage stays a signed `offset_days`, negative = before — prep days like start−2 were always expressible, the signed-number UI just hid it). The agent still never authors protocols.
- **Coverage report (P3 plan-assist — the arc's crown jewel)**: for every upcoming/ongoing `cover`/`help` instance, the OTHER adults get one Argyle DM showing the span's schedule as the solver re-solved it without the affected driver — every event with its resolved driver, "⚠️ needs a driver" flags, and an open-count footer. `status_protocols.send_coverage_reports` runs in the 30-min sweep; it SKIPS while the post-invalidation re-solve is pending (marker set only after a successful build, so it retries instead of going silent) and sends once per instance (60-day pruned marker). Never sent to the traveler; give_space/clear_deck days generate none.
- Rules of calm: never nag/streak, quiet hours gate all kid sends (skip, never defer), the correction path is mandatory, and protocol authoring belongs to the family — the agent can set/read/clear days but never creates day types.

## Errands Scheduling Logic
- **Errands Inbox**: A dynamic management UI allows users to add errands using natural language.
- **Errand Rules Engine & Routing Rules Integration**: Errands intelligently respect global Routing Rules (Event Rules) dynamically. If a driver is marked "Unavailable" or "Avoid" for a specific time window or day, the global errand solver evaluates these constraints against the exact proposed `start_time` of each scheduled gap to accurately prevent assignment. Furthermore, errands support advanced native options (Driver Assignment, Passenger Constraints, Time of Day, Day of Week Restrictions, Buffer & Tolerance, Grouping) configured via the Errand Rules Engine or directly on the Errand.
- **Global Heuristic Errands Solver**: `matcher.py` intelligently places errands into gaps across the entire 7-day schedule, including **intra-event gaps** inside scheduled events (e.g., between a drop-off and pickup). It targets a specific scheduling window based on the errand's `created_at` date and its `recurrence_rule` to prevent over-scheduling. It then finds the single gap across all valid dates that requires the least detour time without violating the master route structure or any Errand Rules constraints.
- **Past Due State**: Errands that exceed their estimated scheduled time without being completed are placed in a `past_due` state. The solver safely ignores them so they stop auto-scheduling and wait for manual intervention.
- **Recurrence**: Errands can be set to recur Daily, Weekly, or Monthly upon completion. When marked complete, a new pending errand is generated automatically, which will reset the `created_at` anchor date, starting the cycle anew.
- **AI Agent POI / Category Search**: The AI agent is capable of looking up Points of Interest (POIs) such as gas stations, coffee shops, and groceries, and routing them based on the proximity of a driver's existing route stops. It leverages Mapbox's Category Search and Forward API with independent rate limiting.
- **Place search relevance** (`maps.search_places`): the source of every POI/accommodation address, coords, and OSM extratags (wikidata, opening_hours, website, phone, cuisine). **Mapbox Search Box is authoritative** for name/address/coords — it is proximity-biased and won't return the vacation-rental listings that OSM free-text search surfaces for landmark queries (an Airbnb whose name embeds "…near Disney, Magic Kingdom…" must never outrank the actual park). Nominatim (OpenStreetMap) runs alongside purely to supply extratags, which are backfilled onto the matching Mapbox result by coordinate proximity (≤300 m — same place, so a landmark keeps its real wikidata/hours while shedding the junk). Nominatim results are also junk-filtered (`_looks_like_rental_listing`: rental OSM types apartment/chalet/guest_house/hostel/caravan, names >70 chars, or ≥2 listing keywords like "2BR", "free wifi", "gated community") so the Nominatim-only fallback (Mapbox disabled/unavailable) stays clean too. Real hotels (`type=hotel`) are NOT filtered, so accommodation search is unaffected.
- **Scheduling ownership (CRITICAL)**: the trip **itinerary's** scheduled state (`pois[].is_scheduled/scheduled_start/scheduled_end/event_id`) is owned SOLELY by the trip page's CP-SAT scheduler (`trip_scheduler.schedule_pois_bulk`), triggered explicitly by the user (Schedule / Rebuild). The daily **family** solver must NEVER reset or write back trip-POI scheduled state — it used to reset every trip POI to unscheduled on each live schedule and reschedule them via the errand matcher, which clobbered the user's itinerary (and, once calendar-backed reservations existed, dropped them) on every background refresh / page revisit. The daily solver's bounded-errand placement of trip POIs is now display-only (family dashboard, in-memory), never persisted. Calendar-backed reservations are re-anchored to their real event time by the get_trip_api sync if anything wipes them.
- **Trip POIs as Bounded Errands**: Trip Points of Interest (POIs) act as specialized dynamic errands. They are automatically constrained strictly to the date range of the Trip event and can enforce Day of Week Restrictions to schedule around crowds or closures. The solver schedules them opportunistically within the trip's time window, correctly adapting and localizing logic to the trip's destination timezone. It uses intelligent slot-scoring to prefer geographically close POIs on the same day (using Mapbox travel times), and applies strict Meal Block constraints for `food` POIs (Max 1 Lunch from 11-14, Max 1 Dinner from 17-21 per day), while intelligently treating desserts/sweets as flexible, highly-scored adjacent events. The bulk scheduler uses **hard day-of-week filtering** when clustering regular POIs to background anchors: if a regular POI has `valid_days_of_week` set, it will never be assigned to a background anchor whose `valid_days_of_week` doesn't overlap, preventing mismatches when multiple background POIs exist at the same location on different days (e.g. EPCOT Day 1 vs Day 3).
- **Live Pricing Integration**: The UI can fetch real-time "Live Prices" for flights and accommodations within a trip using the SerpApi via the `/api/trip/{trip_id}/live_pricing` endpoint. These fetched prices are marked with `is_live_price = True` to render a "Live" badge and provide accurate trip budgeting without repeatedly depleting free-tier API quotas. If the user hits their 250 requests/month SerpApi limit, the system gracefully falls back to Deep Links to Google Flights and Hotels.

## Background Trip Events
- **Trip Passenger Constraint**: If an event overlaps with a background trip and **ALL** passengers on the event are also on the background trip, the solver enforces that non-trip drivers cannot be assigned to it. (Conversely, if at least one passenger on the local event is NOT on the background trip, the event is allowed to be scheduled locally). It also ensures that if a trip driver *is* assigned, the event must be geographically close (within 60 minutes) to the trip's location. A manual override on the exact pair beats both bans (see Manual Override above). The pre-solve passenger filter (main.py) drops away passengers from overlapping events using the SAME 60-minute near-trip radius, and only applies the near-trip escape when the trip has at least one driver (or is 'global') — a kid away alone (camp bus) has no on-trip driver to shuttle them, so their home events are suppressed regardless of distance. The filter resolves each event cid to passenger entities the same way `compute_event_trip_entities` does (cid may be a passenger id OR a raw Google calendar id): events bound by a rule whose `passenger_ids` hold calendar ids used to keep raw cids (the rule-matched branch found no passengers to rewrite them with), leaving the filter blind while the solver still banned every driver. The rule-matched branch now also resolves `passenger_ids` bidirectionally (passenger id or calendar id, mirroring `does_event_match_rule`), so matched events get real passenger ids. Keep the two radii in sync: a passenger kept by the filter but unassignable by the solver renders as a bogus red "Needs driver".
- **Passenger double-booking auto-resolution (v2.46.0, `matcher.resolve_passenger_double_bookings`)**: the passenger-overlap hard constraint (2b) makes two overlapping different-location events sharing ANY passenger mutually exclusive **as wholes** — so a kid's solo recurring event (e.g. Tuesday class) used to knock a co-attended sibling event fully off the schedule every week. A pre-solve pass (main.py, right after the trip filter) resolves the one deterministic case: a kid double-booked between an event where they are the ONLY attendee and one with co-attendees is dropped from the co-attended event (it then schedules for the remaining kids; the solo event needs them or it has nobody to drive). This is default behavior — no setting, no rule type — because no priority concept is needed. Conservative by design, mirroring exactly when 2b bites: both events timed (all-day presence ≠ physical occupation), true time overlap, two different KNOWN locations, exactly one shared kid, resolved via `get_event_passenger_ids` (handles raw calendar-id cids). Two multi-passenger events, or two solo events, are left alone — the unassigned event's diagnostics still offer the manual `prompt_drop_passenger` action, and per-event config attendance / manual overrides remain the escape hatches. Drops are logged server-side and visible as the kid's pill missing from that instance. Tests: `tests/test_pax_conflict_drop.py` (8 scenarios incl. end-to-end solve).
- **Trip window semantics (INTENTIONAL)**: the suppression/ban window is the trip event's own times **padded with home→destination travel time on both sides** — people in transit cannot attend home events, so events overlapping the padded window are deliberately conflicted. Consequently the background trip's calendar times should be the **at-destination window** (arrival to departure), NOT include the travel: the padding re-adds it. Send-off/pickup logistics (camp-bus drop-off) then fall before/after the padded window and schedule normally. An **all-day** trip event starts at midnight, which swallows same-day logistics regardless of padding — give trips real times when boundary-day driving matters.
- **Suppressed events stay visible** (`Event.trip_suppressed`): an event whose passengers are all away is excluded from solving but NOT removed from the UI payload. It renders gray on the Calendar view with an explanatory banner in its details dialog ("Ignored for the driving schedule — everyone attending is away on a trip") — which is also how a mis-timed trip window gets noticed instead of events silently vanishing. The Agenda view renders suppressed events dimmed (50% opacity, gray bar) with a gray "✈️ Trip conflict" chip instead of the red "⚠️ Needs driver" badge. More generally, the calendar feed distinguishes **unassignable vs. merely unassigned**: `compute_diagnostics` now takes `trip_metadata` and emits `trip_conflict` reasons (mirroring the solver's trip-assignment bans), and when EVERY driver has a hard-block reason (any type other than `optimization`) the event is flagged `isConflict` — rendered amber ("⚠️ Conflict" chip on the Agenda, amber modal banner "assigning a driver won't fix it") instead of the actionable red "Needs driver". For split legs, one assignable leg keeps the red badge. The calendar details dialog also carries an **Event Configuration** button that opens an in-page config modal (calendar.html) — a sibling of the dashboard's edit mode using the same `api/events/config/{google_id}` + `api/events` PATCH contracts (passengers with per-passenger times, driver attendees, attendance mode, trip link, time/location overrides, Ignore Event); keep the two forms in sync when config fields change.

## Draft Trips & AI Scheduling
- **Draft-First Creation**: All newly generated trips (whether Exact Dates or Flexible Dates) are securely stored locally as Draft Trips in the backend JSON database, protecting the user's primary Google Calendar from unconfirmed events while iterating.
- **Smart Calendar Analysis**: The agent queries Google Calendar for upcoming free/busy schedules and intelligently cross-references this with destination-specific seasonal heuristics (e.g. avoiding hurricanes) to suggest an optimal booking window via the `/api/trip/{event_id}/suggest_dates` endpoint.
- **Budget Compliance**: For trip plan generation, the backend enforces the `budget_max_usd` property automatically. It intercepts the LLM output, sums the `estimated_price_usd` for all generated POIs, accommodations, and flights, and forcibly injects a warning payload to the chat context if the total exceeds the budget, preventing the LLM from silently ignoring constraints.
- **Strict Day-of-Week Mapping**: The background LLM mapping `valid_days_of_week` uses an absolute Monday=0 index, rejecting relative "Day X" labels to ensure POIs correctly map to absolute dates when solving in a mock calendar future environment.
- **POI counts & request economy** (`generate_trip_plan`): open-ended requests ask for ~3 POIs/night with a stated floor of 90% of that in the prompt's final instruction (10 nights → aim 30, floor 27). The healthy path costs exactly ONE LLM request; top-up CONTINUATION calls (max 2) fire only when the response comes back below the floor. User-specified quantities are always honored exactly and skip top-ups.
- **Flights**: plan generation (`generate_trip_plan`) MUST emit round-trip flights whenever an origin is known — the global `home_location` setting or a departure city stated in the request — unless the user isn't flying (driving/train/cruise) or the destination is within ~4 hours' drive; the per-trip `flight_preferences` field only shapes airline/seat choices, it does not gate whether flights are generated. When no origin exists and the LLM returns no flights, a visible actionable note ("set your Home Location in Settings...") is appended to `budget_warning` instead of silently omitting flights. The agent also has direct flight tools: `generate_trip_flights` / `add_trip_flight` / `edit_trip_flight` / `delete_trip_flight`. A bare "add flights to the trip" request must NOT turn into an interrogation: the agent calls `generate_trip_flights`, a dedicated one-LLM-request generator (`trip_planner.generate_trip_flights`) that uses the home location as origin and the trip's destination/dates to produce round-trip flights (outbound arriving day 1, return departing the last day; flight_number left null — never invented), deduplicates against existing flights by route+departure-date, and adds them as editable estimates. The Smart Planner (planner-mode) intent classifier routes flight requests to the same generator ('flights' intent) instead of misfiling them as POIs. `add_trip_flight` is only for a specific flight whose details the user provided. CRITICAL WIRING NOTE: the main chat widget (`/api/chat`) does NOT use the v1 agent loop — it goes through `services/agent_router.py` (Gemma) with the separate `agent_tools_v2` registry; flights there are exposed as ONE tool, `manage_trip_flights` (action generate|add|edit|delete), a thin wrapper delegating to the v1 handlers, with the router's CRITICAL instruction #3 mandating action 'generate' for detail-less flight requests (never interrogate the user). Any new trip capability must be wired into BOTH stacks or the chat widget won't have it. Times are 1-indexed trip-day ordinals + 'HH:MM' (day 0 = the day before the trip, for overnight outbound legs) — mandatory phrasing on drafts, where mock calendar dates must never surface; absolute ISO datetimes only when the user gave real dates. Guards: arrival must be after departure (rejects with overnight-flight guidance), duplicates (same flight number, or same route with no number, on the same departure date) are rejected toward edit_trip_flight, edit/delete identify by flight_id → flight_number → origin/destination with ambiguity errors instead of guesses, and a hand-edited price clears `is_live_price`.
- **Trip data ingest gate** (`services/trip_validation.py`): everything the LLM or agent produces is UNTRUSTED INPUT — every path that persists trip POIs or accommodations (plan generation, `generate_trip_accommodations`, agent tools `add/edit_trip_poi`, `add/edit_trip_accommodation`, any future importer) must pass through this module before storage. Zero extra LLM requests anywhere. Layers: (1) `reconcile_coords` — every generated POI **and accommodation** carries `approx_lat`/`approx_lng` from the LLM/agent; if the geocode lands more than `COORD_MISMATCH_KM` (60) away, the fuzzy match is bogus ("Burgundy Wine Trail" once matched a spot in Paris): the LLM's regional coordinates win and the matched place's identity fields (hours, website, wikidata, mapbox_id) are dropped. Agreeing geocodes are kept — they're more precise. Accommodation coordinates are the keystone: the scheduler's day→home-base map and geography fence trust them outright. Location *edits* re-ground coordinates the same way (stale coords are never kept for a new location). (2) `anchor_fields` — a single-day `is_background` entry under `ANCHOR_MIN_DURATION_MINS` (180) is demoted to a regular POI; anchors with `days_claimed > 1` or no stated duration keep their flag; the agent gets a note when demotion happens. (3) `repair_accommodation_overlaps` (batch, plan generation) — overlapping stay **date ranges** poison the day→home-base map: zero-night stays dropped, stays overlapping saved stays dropped, "umbrella" stays spanning ≥2 others dropped, remaining overlaps clipped forward. Same-location/same-hotel repeats with non-overlapping dates (return stays) always pass; the name dedup is date-aware. **Stay-night coverage** (`shift_stays_to_trip_start` + `uncovered_nights`, wired via `trip_planner._ensure_stay_coverage` — ZERO extra LLM requests): every trip night in [start, end) needs a stay; `mock_start_date` is already the ARRIVAL timestamp (draft creation computes it from the flight lookup). The generation LLM's persistent bias is starting the stay chain a day late ("overnight flight, arrive next morning"). The original multi-leg prompt pinned BOTH chain ends (first check_in = start AND last check_out = end), which converted that benign off-by-one into forced compression of a middle leg — a real trip's 2-night Riviera leg silently became 1 night. The fix keeps the chain anchored only at the START: the prompts say give every leg EXACTLY the user's nights (a correct allocation ends at the trip end by itself — never stretch or shrink a leg to hit it), and the gate TRANSLATES a late-starting chain back to the arrival day. Leg lengths are user intent and are never resized by code; the anchor is system truth, so translation preserves intent exactly and costs nothing. Translation is skipped when any existing stay is dated (a shift could collide). Nights still uncovered after translation are surfaced as a visible warning appended to `budget_warning` — never silently repaired and never worth a second request. A day-1 gap is uniquely bad: mid-trip gap days inherit the previous night's stay as home base; day 1 has nothing to inherit, leaving it baseless and unfenced. (4) Agent tool stay integrity — `add_trip_accommodation` REJECTS an overlapping or zero-night stay with guidance phrased in trip nights (mock dates never surface); `edit_trip_accommodation` treats the edit as fresh intent and CLIPS neighboring stays to make room (rejecting would deadlock two full-span stays), but refuses an edit that would fully swallow another stay — deleting is never a side effect. (5) `is_misplaced_accommodation` — a POI is reclassified as lodging only when it has a lodging-flavored name ('hotel', 'villa', 'inn', ...) AND no attraction signals (anchor flag, parent link, or category sightseeing/activity/shopping/food). Keyword match alone once hijacked 'Villa Ephrussi de Rothschild' (a garden-estate attraction) into an undated accommodation, silently deleting it from the itinerary; the asymmetry is deliberate — wrongly keeping a hotel as a POI is visible and recoverable, wrongly moving an attraction is silent data loss. (6) `reground_area_anchors` — area-anchor coordinates are re-centered on their children (see the anchor coordinate trust hierarchy under Trip Itinerary Scheduling); works on POI objects and plain dicts so plan ingest, agent tools, and the scheduler share one implementation.
- **Itinerary clear / rebuild / delete semantics** (trip.html + main.py): the trip page separates *planning* items from *fixed* items. A **calendar-backed POI** is one whose `event_id` is a real `cal::id` (committed by Chauffeur, or — planned — a linked external event), versus a fuzzy `draft_poi_` placeholder; `_is_calendar_backed_poi` is the shared test. **Rebuild** (`POST /api/trip/{id}/rebuild`, and the trip-page button) un-schedules only the fuzzy POIs and re-solves them through the trip's own CP-SAT scheduler (`schedule_pois_bulk`) — NOT the daily errand matcher (`schedule/refresh`) the old button wrongly called, which was the source of POIs scheduled with no `draft_poi_` id. Calendar-backed POIs stay put and the solver routes around them via its existing `locked` mechanism. **Per-day Clear** (`clearDay` → `POST /api/trip/{id}/unschedule`) and the **unschedule** endpoint remove items from the timeline WITHOUT deleting anything from the calendar; calendar-backed anchors are never auto-unscheduled. **Delete-from-calendar safety** (`clear_itinerary_api` + `_is_chauffeur_calendar_event`): "Delete from Calendar" only deletes events Chauffeur created, verified by the `poi_id`/`trip_id` stamp in the Google event's `extendedProperties.private` ([calendar.py](services/calendar.py) `create_event` sets these); externally-authored linked events (e.g. a family member's reservation) are ONLY ever unlinked, never deleted, and unknown-provenance events are refused. **POI-centric linked events** (implemented): a Google Calendar event is linked to a trip either from the Schedule page (event config `trip_id`) or from the trip page's **Add Attraction → "Link Existing Event"** tab — a multiselect searchable picker: it lists calendar events within the trip's own date range (±1 day, minus background trips and any already on the trip) — not a fixed days-from-today window. The list is sourced from **raw Google Calendar events** (`/api/calendar/events` → `calendar.fetch_upcoming_events`), NOT the solved/cached daily schedule: the latter's per-day cache can be stale and omit an event booked after that day was last solved (the bug where one dinner was absent from the picker while every other day's dinner showed), filters as you type, each pick becomes a removable pill, and "Link Events" posts all selections to `/api/trip/{id}/link_events` which sets every event config's `trip_id` and runs the POI sync ONCE (`/api/trip/{id}/activity` remains for single link / create-new). Add Activity (itinerary "Add") is create-new-only; its old Link Existing tab moved to Add Attraction. A linked event is reconciled into a **calendar-backed POI** (`is_external_event=True`, `source_event_id` = the `cal::id`, `event_id` = the same real id, `is_scheduled` at the event's real time) by `_sync_linked_events_to_pois` on every `get_trip_api` — created on link, removed on unlink, committed POIs never duplicated. It then renders in the Attractions grid (with a "From Calendar" badge) and the itinerary exactly like any attraction, and the solver's `locked` mechanism routes planning POIs around it (so a fuzzy lunch won't collide with a real reservation). The legacy `meta["activities"]` list is retired.  Calendar-backed POIs are FIXED anchors locked to their real event time: the daily errand solver's write-back never reschedules them or clobbers their cal:: event_id (it skips `is_external_event`/`source_event_id` POIs), the get_trip_api sync re-anchors any that were clobbered (event_id != source_event_id → refetch the event and restore its real time), and `_layout_one_day` keeps their exact time instead of snapping them to a meal anchor. Crucially, Level 2 layout also bumps every flexible POI PAST any fixed reservation's time window (a day-wide check, because the block skeleton's windows overlap — an 11:10 reservation lands in the morning block yet must not collide with a lunch-block POI), so a regular POI can never be laid out on top of a real reservation. Level 1 also counts food reservations via `_is_meal`, so a second meal is never assigned to a meal-block reservation's slot. A locked meal reservation is filed under its MEAL block (breakfast/lunch/dinner by time-of-day) even when its clock time sits just outside the block window (an 11:10 lunch is before the 11:30 lunch block; a 17:25 dinner before 17:30) — otherwise it lands in an activity block, leaves the meal slot open, and a fuzzy meal doubles up next to it. A linked reservation with an opaque name ('Chef Mickey', 'Maria and Enzo') and no enrichment cuisine is recognized as a meal from its start TIME (`_meal_from_iso`: breakfast [6:30,10:45), lunch [10:45,15:00), dinner [16:00,21:00); gaps → not a meal), setting category='food' + meal_type so it reserves its block. Applied at creation and healed for existing external POIs mis-tagged 'other' (one fetch, then it stops). Removing a calendar-backed POI (attractions or itinerary card) UNLINKS it via `POST /unlink_event` (clears the event config's `trip_id`, drops the POI) and never deletes the Google event; `delete_activity_api`'s calendar-delete branch is likewise gated by `_is_chauffeur_calendar_event`.
- **Post-solve sanity audit** (`trip_scheduler.audit_solve`): the last line of the data-integrity defense, run at the end of every `schedule_pois_bulk`. Deterministic haversine checks over the FINAL schedule state (including previously locked placements): any scheduled POI or anchor claim farther than `MAX_BASE_DIST_MINS` from its day's home base, and any day left empty while unscheduled POIs sit near its base (hard keep_clear days excluded), produce warnings. Warnings are printed as `[TRIP AUDIT]` server-side and streamed as a `{"type": "audit", "warnings": [...]}` NDJSON line; trip.html shows them in a "Schedule Warnings" modal so a geographically incoherent result is never presented as clean. Labels use 1-indexed trip days, never (mock) calendar dates.

## Trip Itinerary Scheduling (CP-SAT, services/trip_scheduler.py)
The trip itinerary is built by a two-level scheduler (design: `docs/trip_scheduler_design.md`), replacing the old greedy slot-scanner:
- **Level 1 (global assignment)**: A CP-SAT model assigns every POI to a `(day, block)` slot simultaneously. Each trip day has a block skeleton: `breakfast` 07:30–09:30, `morning` 09:00–12:00 (≤180 active mins), `lunch` 11:30–13:30, `afternoon` 13:00–17:30 (≤270), `dinner` 17:30–20:30, `evening` 20:00–23:00 (≤150). Distances for clustering use haversine on stored `lat`/`lng` — zero Mapbox calls during solving.
- **Level 2 (timing)**: Deterministic code lays concrete clock times onto each day (nearest-neighbor order within blocks, real cached travel times between consecutive stops, meals anchored toward 08:00/12:00/18:30, 5-minute snapping).
- **Meal intelligence**: `meal_type` ('breakfast'|'brunch'|'lunch'|'dinner'|'dessert'|'snack') and `dining_style` ('quick'|'casual'|'fine') on TripPOI drive placement. Fine dining → dinner block. At most one non-dessert meal per meal block per day. Desserts/snacks go in activity blocks, with a bonus for evening-after-dinner. Food without `meal_type` may take lunch or dinner. Legacy POIs infer meal type from `ideal_time_start`.
- **Multi-leg trips (accommodations as legs)**: each trip day's routing "home base" is the accommodation covering that date (check_in ≤ date < check_out); a checkout or gap day inherits the previous night's accommodation (you wake up there), so no day is ever geographically baseless. POIs gravitate to the leg they're closest to via the distance shaping term — no rules needed. On top of the soft pull there is a HARD geography fence (`MAX_BASE_DIST_MINS` = 240 haversine-min ≈ 170 km line-of-sight): a POI may not be placed, and an anchor may not claim, a day whose base is farther than that. The fence exists because soft penalties lose to placement rewards under capacity pressure (scheduling beats dropping by 1M vs ~300/min), which silently spilled POIs onto the wrong leg, and because a far anchor claim flips the anchor-day base switch into a net reward for dragging its whole neighborhood cross-leg. Real day trips (Paris→Reims ~182 min) stay inside the fence; cross-leg placement (Paris→Beaune ~386) cannot happen. Fenced-out POIs fail with an explainable distance reason; days whose base has no coordinates are never fenced; children follow their parent's claimed days instead of the fence. Anchors (background POIs) get the same pull: each candidate claim day is charged −300/haversine-min from that day's accommodation to the anchor, so an anchor claims days inside its own leg (a Riviera anchor never claims Paris-hotel nights). On flexible-date drafts the UI shows accommodation stays as trip-day numbers only ("Day 2", numeric day inputs in the edit dialog) — the mock calendar dates behind them must never be shown to users; real dates appear only once the trip has real dates. Accommodation cards render sorted by check-in (chronological leg order), one card per stay/booking; return stays to the same hotel stay separate cards (each has its own dates, price, live pricing, edit/delete) but get "Stay N of M" badges so the repeat reads as a return visit, not a duplicate. The agent expresses legs through `add_trip_accommodation` / `edit_trip_accommodation`, which accept absolute `check_in_date`/`check_out_date` or 1-indexed trip-night ordinals (`check_in_night`, `nights`; night 1 = first night — preferred for drafts since their mock dates are an implementation detail). Legs must be contiguous and non-overlapping (leg N+1 checks in when leg N checks out); omitting dates spans the whole trip. The plan-generation prompts (`generate_trip_plan`, `generate_trip_accommodations`) are instructed to emit one accommodation per described leg in the user's stated order with contiguous dates. For hard leg fences, add a `day_restriction` TripRule with `trip_days`. The trip map mirrors the solver's day→base semantics: a day's commute routes originate from the stay covering that night (check_in ≤ date < check_out); the checked-out stay is only a fallback for final/gap days. On a switch day the map draws a dashed commute transfer old stay → new stay (drop the bags), then routes the day's POIs from the new stay. Commute routes are direction-aware at the trip's edges: on an arrival day (check-in == that date with no prior stay checked out that morning) no morning stay→first-activity line is drawn (the day doesn't start at the hotel), and on a checkout-only (departure/gap) day no evening last-activity→stay return is drawn (the travelers leave). Commute lines are also only drawn to activities with known coordinates (a POI or accommodation match) — geocoding a bare label would dead-end the line at a spot with no marker. The map's route cache is pruned/re-homed on every itinerary render: routes whose activity pair was deleted, reordered, or moved to another day are evicted (or re-tagged to the new day) instead of lingering as phantom lines, and route layer redraws retry once the Mapbox style finishes loading instead of silently dropping/leaking lines.
- **Accommodation-switch days (transfer windows)**: on a day whose stay differs from the previous night's, the travelers pack, check out at `CHECKOUT_TIME` (11:00), and travel — so `_build_day_grid` clips that day's blocks to start no earlier than checkout + `_transfer_mins(old, new)`. Transfer pacing: haversine driving minutes up to `LONG_HAUL_KM` (350); beyond that, rail/air pacing (`LONG_HAUL_OVERHEAD_MINS` 150 + 0.12 min/km ≈ 500 km/h) — raw driving pace would wrongly write off the whole day (Riviera→Paris ≈ 16 h by road, ~4 h door-to-door by TGV). Blocks with under `MIN_BLOCK_USABLE_MINS` (30) of usable time are dropped; clipped starts round UP to :05 (Level 2 snaps starts DOWN, which would otherwise slip a POI before arrival); clipped activity capacities shrink to the remaining wall time. The same clipping now also applies the trip's start/end timestamps to partially-covered first/last days (no more dinner scheduled after the departure flight). This is deliberately DERIVED from the stays at solve time rather than stored as hidden "travel events": no phantom entities to exclude from the UI/calendar/dedup, and it can never go stale when leg dates change. Gap/checkout days (same stay inherited) are not clipped. The trip map's dashed old-stay→new-stay commute route (trip.html) is the user-visible face of the same transfer.
- **Anchors (background POIs)**: `is_background=true` + `days_claimed=N` makes a POI claim N full days (one POI — no more "(Day 1)/(Day 2)" clones; `claimed_dates` records the exact local dates). Claims are consecutive by default (soft), but a `valid_days_of_week` on the anchor is a HARD subset constraint (3 days + Mon/Wed/Fri = exactly Mon, Wed, Fri). At most one anchor per day. Children link via `parent_container` (background POI id) and may only be placed on the parent's claimed days. On a claimed day the distance "home base" switches from the accommodation to the anchor, so any POI is welcome on that day in proportion to its proximity to the anchor. Anchors generalize beyond theme parks (e.g. "Explore the Eiffel Tower district"). In the UI, anchors are never presented as ordinary activities: the itinerary wraps a claimed day's cards in a "🌟 Day Theme" container, and the trip map renders them as a star badge (indigo when scheduled, gray when not) with a "Day Theme" popup label instead of an activity pin. **Anchor coordinate trust hierarchy**: an anchor that kept a confirmed place identity through reconciliation (`mapbox_id`/`wikidata_id`) is a real venue — its coordinates are ground truth. Without an identity it is an *area* anchor ("Paris Classic Exploration") whose coordinates are an LLM regional guess: leg-scale accurate but not day-scale, and on a claimed day they become the home base, bending the whole day toward a place nobody visits. Area anchors are therefore re-grounded onto the centroid of their children's coordinates (`trip_validation.reground_area_anchors` — run at plan ingest, on agent `add_trip_poi`, and at the start of every solve); a *childless* area anchor snaps to its claimed day's accommodation right after claiming (a pure theme has no location of its own — it borrows the leg's). The regional guess is only consulted for the one thing it knows: which leg the anchor belongs to. **Anchors are containers, not summaries**: the generation prompts and `add_trip_poi` tool require every named sight an anchor covers (e.g. a tour "of the Eiffel Tower, Arc de Triomphe, and Champs-Élysées") to ALSO be emitted as its own child POI via `parent_container` (anchor name or id, fuzzy-resolved) — a sight living only in an anchor's description has no hours, price, map pin, or schedulability.
- **Objective tiers**: placement rewards by `priority` (must 10M / want 1M / stretch 100k) dominate; then soft-rule weights (default 50k); then shaping terms (−300/haversine-min from the day's base, −100/min between same-day pairs, day-balance −30/min beyond a 60-min deadband, claim-span −40k/day, dessert-after-dinner +20k). `ideal_time_start/end` is now a SOFT block preference (−20k off-window), never a hard failure.
- **Explainable failures**: unscheduled POIs stream a concrete `reason` ("restricted to Sat/Sun but the trip includes none of those days", "its parent 'Epcot' was not scheduled", "all eligible dinner slots were taken (N slots, M competitors)") plus `suggested_fixes` actions (`clear_days`, `disable_rule`) consumed by the failure modal in trip.html.
- **Incremental solves**: already-scheduled POIs are locked to their current day/block; adding POIs never reshuffles existing days (times within an affected day may adjust).

## Trip Rules (`TripRule` objects)
Per-trip scheduling rules stored in `TripMetadata.rules`, mirroring the driving Rule system. The AI agent creates/manages them via the `manage_trip_rules` tool (create/list/enable/disable/delete); the trip page shows a read-only Rules panel with an enable/disable toggle (`GET/PATCH /api/trip/{event_id}/rules`). Pydantic rejects unknown fields (`extra='forbid'`) — emit exactly the documented fields.
- `rule_type` values and their parameters:
  - `day_restriction` — matched POIs only on `days_of_week` (0=Mon..6=Sun) and/or `trip_days` (1-indexed). "Epcot on Tuesday".
  - `block_restriction` — matched POIs only in `blocks` (breakfast|morning|lunch|afternoon|dinner|evening). "Boat tour in the morning".
  - `budget_cap` — sum of matched POIs' `estimated_price_usd` ≤ `max_usd`. "Keep dinners under $100".
  - `day_capacity` — active minutes on matched days ≤ `max_active_mins`. "Keep Tuesday light".
  - `keep_clear` — nothing scheduled on matched `trip_days`/`days_of_week` × `blocks` (all blocks if unset). Defaults to HARD. "Leave Thursday afternoon free".
  - `spacing` — ≥ `min_gap_days` between matched POIs/anchors. "No two parks back-to-back".
  - `template_override` — trip-wide block changes: disable listed `blocks`, and/or clamp the day with `template_start`/`template_end` ('HH:MM'). "Nothing before 9am".
- Selectors: `poi_ids`, `categories`, `keywords` (name/description substring). Empty selectors match all POIs.
- `hardness`: 'soft' (weighted, default) or 'hard' (constraint). Agent-created rules default soft except `keep_clear`; escalate to hard only on emphatic user language. Soft `weight` default 50,000 (rule preferences outrank shaping terms but never placement rewards).
- POI fields (`valid_days_of_week`, `meal_type`, `dining_style`, `parent_container`, `days_claimed`, opening hours) compile into the same constraint pipeline as stored rules; the Rules panel lists them under "Derived from POI settings".
